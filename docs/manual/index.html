The command reference for h5i, in the order an application lives: build it and prove its kernel, test the running application for what the proofs do not cover, give the agent doing either a box, and watch all of it from one dashboard. What h5i is gives that shape in a page.

h5i <command> --help is authoritative for flags. This manual explains what the commands are for.

What h5i is

h5i (pronounced high-five) is an Axum-based Rust web framework built around application kernels that can be formally verified with Lean 4 and executed on servers, bare-metal embedded devices, and GPUs. The same binary carries the development infrastructure around such an application: a red-teaming workbench, security regression tests, confined boxes for AI agents, and one dashboard over all of it.

The manual follows the life of an application through four parts:

Part You h5i Chapters
Build and verify Write the application's logic as a kernel and say what it must guarantee Extracts the kernel to Lean 4, gates the proofs, states the framework's obligations for it, and tries to break the spec with mutants h5i app
Test the running application Drive the deployed application, change what it sends, judge what comes back Captures every request, replays it under your edits, records each decision, and replays the whole flow in CI The security workflow, h5i browser, h5i recon, h5i websec, h5i project, h5i test
Contain the agent Let an agent write the code or run the attack Runs it in a disposable box with a pinned base, an egress allowlist and a human-operated output gate Containment, Policy, Receipts
Watch Read, decide, take over One read-only dashboard over proofs, engagements, sessions and boxes h5i ui

An h5i-app application keeps the logic that decides what each command does in a kernel crate. Charon and Aeneas translate that crate to Lean 4, h5i app gates the proofs, and the same kernel is served by Axum on a server, by a heap-free HTTP/1.1 server on a microcontroller, or in batches on a GPU. The shell around the kernel is trusted infrastructure, and the kernel is what the proofs are about.

The proofs stop at the kernel, and around it sit Axum, PostgreSQL, the embedded I/O, the GPU launch shell, your configuration, your deployment, and the spec itself, which may have left something out. The remaining bugs live there, and you find them by testing the running application: a browser session whose traffic goes through a capture proxy h5i starts for it, and the tools that read, replay, inventory and judge that traffic. A bug found this way becomes an h5i test that runs in CI beside h5i app extract --check, so the proof gate and the regression gate guard the same application from two sides. This part works against any web application, including ones built on another stack, and it has the most commands, so it takes up most of this manual.

Both halves are done by agents as much as by people: an agent writes kernels and proofs, and an agent drives the browser and sends mutated requests. A box is where that agent runs when its code is untrusted, when its target may answer with something hostile, or when its network has to be decided outside it. The dashboard is one read-only view over all three.

Who does what

h5i does the deterministic work; you or your agent judge the result.

h5i owns you or the agent own
extraction to Lean, the proof gate, the framework's stated obligations the kernel, and which theorems it should satisfy
the mutants, and whether each one broke a proof whether a surviving mutant is a gap in the spec
exact capture, stable message ids which request matters
session, cookie and identity state which parameter to change
structured edit, resend, diff, timing what a difference means
scope, rate, budget, and the refusal what to try next
the record, and refusing to act without one whether any of it is a vulnerability

h5i ships no payloads, no wordlists and no verdicts. A finding is what the agent writes with h5i websec finding create; h5i stores it and checks that the ids it cites exist. h5i writes no theorems for you beyond the framework's own obligations and generated authorization proofs, so a property you never stated is not proved.

What is recorded, and what is safe to paste

h5i keeps two things apart. The request log, the action log, the receipts and the endpoint ledger say what was asked for, decided and returned, and are safe to paste into a bug report. The stored messages themselves, Authorization and cookies included, are owner-only, kept for every session, and in no export unless named. Every row says which lane observed it. A session's lane is proxy-observed; records from an older h5i that had its own engine may say engine-claimed or host-observed, and a lane is never upgraded.

The proofs have the same two layers. The Lean kernel's verdict on the current sources is the evidence. A passed run under .h5i/app/runs and the report h5i app report derives from the sources are records of an earlier verdict, and rerunning h5i app check refreshes them.

What it is not

  • A proof of the whole application. The proofs are about the kernel. Axum, PostgreSQL, the embedded I/O and the GPU launch shell are trusted infrastructure, GPU execution is tested against the CPU path, and what the proofs assume is written down.
  • A scanner. There is no crawl-and-flag mode, no payload generation and no severity score. The verdict is yours.
  • A browser. The browser is Chromium. h5i owns the policy, the record and the messages that pass through its proxy.
  • A sandbox by default. A session's Chromium is an ordinary host process, and h5i browser status says so. Containment is a box you ask for.
  • A content filter. A box bounds what a persuaded agent can reach. It does not classify what a page says.
  • A defence against a targeted kernel exploit. See Limits.

Install

terminal
curl -fsSL https://h5i.dev/install.sh | sh                                # prebuilt binary
curl -fsSL https://h5i.dev/install.sh | sh -s -- --websec --recon --test  # with the plugins
cargo install --path .                                                    # from source
cargo add h5i-app                                                         # the framework, in your application

The plugins are separate archives registered with h5i plugin install, so h5i plugin list is the whole truth about what is present. h5i.dev/install.sh and raw.githubusercontent.com/h5i-dev/h5i/main/install.sh are the same file, and CI fails if they diverge.

Then give your agent the skill:

terminal
h5i skill install           # writes ~/.claude/skills/h5i (or ~/.codex)
npx skills add h5i-dev/h5i  # the same bytes, without the binary

h5i app

An h5i-app application keeps its logic in a kernel crate: pure Rust functions that decide what each command does. Charon and Aeneas translate the kernel to Lean 4, and you prove properties about it there. The shell around the kernel is ordinary infrastructure: Axum and PostgreSQL on a server, the no_std HTTP/1.1 server of h5i-app-embedded on a device, and the batch adapters of h5i-app-gpu where a workload fits a GPU. The framework ships its own extracted and proven components (SQL compilation, the reply JSON writer, bearer tokens, HTTP/1.1 parsing), so a kernel crate depends only on what it uses and extraction never pulls in Axum or a database driver. The tutorials under examples/app/ build seven applications this way.

h5i app runs the proof loop. A project is the kernel crate, a Lake project of proofs under proofs/, and an h5i-app.toml that says what to extract, which theorems must exist, and which bugs the proofs must reject.

terminal
h5i app new counter            # a kernel, proofs that already pass, h5i-app.toml
cd counter
h5i app doctor                 # Charon, Aeneas and Lean at the versions this h5i pins
h5i app prove                  # extract to proofs/generated/, lake build, then the gate
h5i app lint                   # routes take an Actor; no client-set identity in Command
h5i app report                 # per route: commands, covering theorems, assumptions (--json)
h5i app mutate                 # each [[mutant]] must break a proof
h5i app mutate --auto --list   # mutants generated from the kernel's syntax
h5i app mutate --security      # authorization bugs; each line names the proofs that broke

h5i app new fetches the h5i-app Lean library from git at this binary's release tag; --h5i-path <checkout> uses a local checkout instead. For CI, h5i app extract --check changes nothing and fails if proofs/generated/ is stale, and --all runs a verb on every project under a directory.

The proof gate

check (and so prove) fails on sorry or native_decide in hand-written Lean, on any axiom declaration, and on any theorem of a hand-written module that depends on an axiom other than propext, Classical.choice and Quot.sound. Hand-written modules may not use initialize, implemented_by, extern, unsafe, term syntax, or macros and elaborators outside the tactic category.

check also states the framework's obligations (H5iAppLib.Obligation: read-only soundness, panic freedom, tenant isolation, storage, authorization, and the spec of a schema! policy) for the extracted functions. A theorem named under [obligations] must have exactly that statement, or check prints the expected type and fails. An obligation with no named theorem is tried by automation and reported open if that fails. The verdict is the Lean kernel's, elaborated without the project's hand-written Lean. A passed run under .h5i/app/runs is a local record; rerun check to establish it.

Mutants

mutate runs each mutant in a copy of the project: it edits the kernel, re-extracts and rebuilds the proofs. A mutant is caught when the proofs stop building. One that survives is behaviour the spec does not pin down, such as a theorem that holds because the kernel refuses everything. --auto generates mutants from the kernel's syntax: comparison boundaries, flipped == and !=, swapped && and ||, dropped !, and if conditions forced to true or false. --security adds authorization bugs: a conjunct of Policy::permits dropped, visible or stored made true, a comparison with the actor made true, the guard removed, every principal put in tenant 0, and the same changes made to a schema! policy's generator. Each caught mutant's line names the declarations whose proofs broke.

Framework-proven authorization

[authz] guarded opts a kernel into authorization the framework proves for it (docs/design/design-app-authz.md). The kernel invokes h5i_app_std::authz_kernel!, which writes guarded_transition and an App type whose Kernel::transition is the guard, and the server runs App on the store its mapping macro generates. extract then writes proofs/generated/Authz.lean, which proves <fn>.authorized, <fn>.kernel_apply_eq and Committed.pg_stored from the framework's theorems with no hand-written Lean. If sql_write is more than a plain list of schema! table writes, [authz] storage must name a hand-written storage proof. lint flags a hand-written impl Kernel, impl Store or impl AuthzKernel, and lint and check both fail unless every h5i_app_* dependency is the framework's own package.

[obligations] principal opts in to one more theorem: TenantOfToken, that the tenant of the principal built from a token is the token's tenant. h5i app report then says whether the server is linked, meaning every HmacAuth::new is given that function by path. Linked is a syn source check and no proof. Each route is reported as proven, linked, proven, not linked, open or not_stated, and every or_anonymous and Actor::assume_authenticated is listed for review.

The report

report lists, for each HTTP route of each project, the kernel commands it may build and which run on the read-only path, whether its handler takes an Actor, the theorems that cover it and what the latest recorded check run observed for each, the assumption ids (A1 to A11) it rests on, and what nothing verifies. It is derived from the sources, h5i-app.toml and .h5i/app/runs, and runs no proof. --json prints the versioned form. Routes it cannot read, such as a nest, are listed under errors. docs/design/design-app-trust.md says what the report does not establish.

toml
# h5i-app.toml
[extract]
crate = "kernel"
start-from = ["transition"]   # Charon start points, inside the crate
include = ["h5i_app_sql"]     # crates extracted with the kernel
schema = true                 # also start from what schema! generates
std-specs = true              # copy h5i-app-std's specs next to the extraction

[authz]
guarded = ["guarded_transition"]   # written by h5i_app_std::authz_kernel!
# storage = "my_kernel.Storage.db_inv"   # only if the storage proof cannot be generated

[check]
theorems = ["my_kernel.inv_preserved"]   # must exist and pass the gate

[obligations]                            # each must state exactly H5iAppLib.Obligation.<X>
read-only = "my_kernel.ReadOnly.sound"   # ReadOnlySound: required when a Kernel overrides read_only
panic-free = "my_kernel.panic_free"      # PanicFree
# authorized = "..."                     # Authorized, with the app's own allowed/visible
# principal = "principal"                # opt in to tenant-of-token ([authz] only)
# tenant-of-token = "my_kernel.Tenant.t" # TenantOfToken; default: automation

[mutate]
targets = ["Theorems"]        # Lake targets a mutant must break (default: all)

[[mutant]]
name = "off_by_one"
old = "if s.count >= s.limit {"
new = "if s.count > s.limit {"

What the proofs cover, and what they assume

The theorems are about the extracted kernel and the framework's extracted components. Everything else is an assumption, listed as A1 to A11 in docs/design/design-app-trust.md: the authenticator returns the principal that sent the request, PostgreSQL runs the rendered SQL as the model says, SERIALIZABLE commits equal some serial order, the engine meets its contract, Charon, Aeneas and Lean translate faithfully, and for an [authz] app the reviewed surface is what the author meant. h5i app report names the assumptions each route rests on. GPU execution is tested rather than proven: h5i-app-gpu runs the same kernel source on both backends and checks that the outputs agree, and a GPU batch never commits application state on its own.

Those assumptions, and everything outside the kernel, are tested against the running application, which the next part covers.

The security workflow

The proofs say what the kernel does; this part tests the running application for everything else: the shell around the kernel, the deployment, the configuration, and the properties the spec never stated. It runs in phases, in the order of the chapters below, and each phase hands the next a message id.

Phase What you are doing Section
Scope Say what is in bounds, and make the proxy enforce it Scope and identity
Recon Find what the target exposes, and record how you know h5i recon
Drive Open a page, act on it, capture what it fetched h5i browser
Test Change one thing, send it again, compare the answers h5i websec
Evidence Write the claim down against the ids that support it Findings
Regression Commit the flow so the bug cannot come back h5i test
terminal
h5i browser open https://target.example --project acme
h5i recon extract                            # what the pages and bundles disclosed
h5i recon known                              # robots.txt, sitemap.xml, security.txt
h5i recon crawl --max-requests 200 --rate 4  # walk it under this session's login
h5i recon triage --calibrate                 # fold the noise, confirm what is real
h5i websec requests                          # the captured messages, by id
h5i websec replay req_42 --set query.id=456
h5i websec diff res_42 res_43
h5i websec finding create --title '...' --evidence req_42,res_43

Recon says what exists and websec tests it. Neither needs the other, so you can enter at any phase. The last phase turns a finding into a test that runs in CI beside the proof gate. None of it needs a box; see Containment for when one helps.

Scope and identity

Before anything is sent, say what is in bounds. Scope is three separate things:

Layer What it answers Where
Engagement scope What the target's owner authorised --project, and Scope
Origin grant What this session may reach at all --allow, on open
Identity Who the session says it is the account signed in to its browser

The first two are enforced before the wire, and a refusal is a row in the log with no bytes behind it. Identity is what the target sees, and changing it is how a two-account test is run.

--project: grouping sessions by engagement

A name addresses one session. A project names the engagement many sessions belong to, and since names are reused and projects are not, the project is what survives the work:

terminal
h5i browser open https://api.acme.com --project acme --session auth --new
h5i browser list --all --json | jq 'group_by(.project)'

Every fold across an engagement (the union ledger, every finding, every origin reached under any identity) is a jq pass over the directories in Files. When ~/.config/h5i/projects/<name>.toml exists, --project also resolves it as the session's engagement scope, and the same name is the durable project that h5i project keeps.

Refusals

text
$ h5i browser navigate https://blog.acme.com/ --session acme1
$ h5i browser requests --denied-only --session acme1
—          DENIED GET https://blog.acme.com/ — `blog.acme.com` is refused by the deny rule `blog.acme.com`

The request gets an allowed: false row in requests.jsonl, a response record describing the refusal, and no bytes between them. The browser is answered 403 with the same reason. Change scope only with authorisation, and never from inside a box.

h5i browser

A session is the whole agent-facing surface. h5i browser open makes one, every verb that follows acts on it, and h5i browser close ends it. The agent does not have to learn about the proxy, its port, or the Chromium process.

terminal
h5i browser open https://example.com
h5i browser snapshot            # the page as a model should read it
h5i browser click @e3
h5i browser screenshot          # a PNG, into the session's artifacts
h5i browser reload
h5i browser requests            # what it asked for, and what was refused
h5i browser close

What a session is

A session is two processes under one record. h5i's half is a capture proxy with the session's control channel beside it. The browser half is Chromium, run by agent-browser (0.25 or newer) and pointed at that proxy:

terminal
npm install -g agent-browser && agent-browser install   # once per machine

open checks that agent-browser runs before it creates anything. A missing or old one stops there, prints the install command, and leaves no session behind. The proxy writes a per-session CA (0600) and uses it to decrypt HTTPS; agent-browser is launched with --ignore-https-errors, so Chromium accepts the proxy's certificates for that session. status repeats that line, and session.json records it as proxy.chromium_tls.

Every message is kept in both directions, headers and bodies, in the session's owner-only store. The status line names the lane and what it does not cover:

text
requests : proxy-observed (captured at h5i's proxy; the external browser itself is not confined)

The server's Set-Cookie answers land in the session's own jar. A replay of a request the browser sent carries that request's own Cookie; a request carried in from another session (resend --as) has its credentials dropped and takes this session's from the jar.

Where Chromium's own sandbox cannot start, which is common without root, set AGENT_BROWSER_ARGS=--no-sandbox. That turns the sandbox off, so use it only for a target you trust.

Page verbs and workbench verbs

Page verbs go to the session's Chromium through agent-browser, with the launch flags the session started with on every call, so a relaunched browser is still captured. Each command is passed on stdin, so a value shaped like a flag stays a value and a credential never appears in the process table:

verb what it does
snapshot [-i] [--delta] [--url U] the accessibility outline, with @ref handles
navigate <url> go there, http(s) or about:blank only (proxy-open is the same verb)
reload load the current page again
click <@ref\|css> click it
type <target> <text> clear the field and fill it
press <key> Enter, Tab, Control+a
select <target> <value> choose an option by its value
set-checked <target> <true\|false> a state, not a toggle
scroll <px> negative scrolls up
wait-for --selector S / --text T until it is on the page
wait-for-script <expr> until a page expression is true
eval <js> run JavaScript in the page and print the result
console [--clear] what the page logged
screenshot [--out P] [--full] [--url U] a PNG

Each is recorded in the session's action log, and its output is kept under the session's artifacts/, so a DOM or console observation is evidence the session holds. screenshot writes into artifacts/ under a name h5i chooses; --out names a file instead.

Workbench verbs go to the proxy's control channel and act on its network layer: requests, resend, sequence, socket, grpc and rpc --stdio. See h5i websec for what they are for. env lists, by name, the credentials type can resolve from the environment h5i runs in.

Driving agent-browser yourself is where capture can silently stop: its daemon restarts when idle, and a later bare agent-browser open starts a browser with no proxy. h5i browser proxy prints the command line and the env to export so every launch from that shell is proxied, and status warns after five quiet minutes.

proxy: a session without a page

terminal
h5i browser proxy https://app.example --session chrome
agent-browser dashboard start          # a human signs in
h5i browser proxy https://api.example --no-browser --session api

proxy starts the session and prints how to point a browser at it. --no-browser skips the agent-browser check and gives you the proxy and its control channel alone, for a session driven only by resend, sequence and the plugins. h5i test starts its actors this way.

Which session a verb acts on

Every session has an opaque id (br_7k2xqa) that appears in the record, in --json and in the receipts, because a durable reference has to survive a rename. A verb resolves its session in three steps, most explicit first:

  1. --session <name> (-s), a name someone chose, or an id pasted from --json
  2. $H5I_BROWSER_SESSION
  3. the session open last made
terminal
h5i browser open https://example.com/login --session auth   --new
h5i browser open https://example.com/      --session public --new
h5i browser snapshot --session auth
h5i browser list                       # the default is the row marked `*`

A name can be reused once the session it named has ended. The id cannot, which is why the id is what gets written down.

open on an existing session

Opening a URL in a browser that is already up means go there. open navigates the session it finds, and --new asks for a second one. The flags that only make sense at creation (--allow, --project, --no-loopback, --expires-in, --dom-instrument) are refused when a session is reused, because a session's policy is fixed when its proxy starts and a silently ignored grant would be one the caller believes it made.

A session reaches the URL it was opened on and nothing else remote. --allow adds origins beyond it: an API the page calls, a CDN it pulls from. Loopback is reachable by default because it is the dev server; --no-loopback takes that back. Anything else the browser asks for is refused at the proxy with a 403, and the refusal is a row in the log.

Logging in

The best login is a human's: agent-browser dashboard start, then sign in in the session's browser. For an agent login, name the credential rather than typing it:

terminal
export H5I_SECRET_ACME_PASS=…
h5i browser env                                        # names only, never values
h5i browser type '#password' '$H5I_SECRET_ACME_PASS'

The placeholder is resolved on the way to the browser. The reply, the artifact and the action log carry the placeholder, and a placeholder whose variable is unset is refused rather than typed as written.

The control lock

Two parties can drive one page: the agent, and a human. The agent holds control by default. A human takes it with h5i browser take <session>, after which the agent's mutating verbs are refused with a typed message while read-only verbs keep working. release hands control back and invalidates what the agent knew: the page moved, so every @ref from its last snapshot may point elsewhere, and it must re-snapshot before its next page action. Workbench verbs carry no @ref and are never held up by the lock. On this machine the lock is advisory: it pauses h5i browser and nothing else.

Ending a session

Closing a session stops its proxy and its Chromium and writes the ending into its record instead of deleting it.

state what happened
live started, and the proxy answered the last time anyone looked
closed ended by h5i browser close; the record is complete
died the proxy stopped without being asked; the record has a gap and says so
expired outlived --expires-in
evicted the box holding it was removed

A verb sent to a session that is not live is refused with exit code 69 (EX_UNAVAILABLE) and never restarts it:

terminal
$ h5i browser requests
browser session `br_7k2xqa` was closed: closed by the user. It will not be
restarted automatically. Start a new one with `h5i browser open <url>`.
$ echo $?
69

The distinct code lets an agent's retry tell "the session is gone" from "the click did not work". Records written by an older h5i, whose sessions ran its own engine, are still read by status, audit and the plugins; a verb that needs that engine refuses on them and says so.

Page output is untrusted

The page composed the title, the link text, the error message and the URL. Every answer h5i relays is scrubbed before it reaches a terminal or a model: escape sequences never survive, other control characters are removed, and strings, arrays and nesting are capped with the truncation stated in the value. ESC in a relayed string is a page rewriting the terminal it is printed into, and nothing a browser has to say needs it. Files a session produces are named by the host, never by the page, and land under the session's artifacts/.

Where sessions live

$H5I_BROWSER_HOME, else the box's own /tmp when h5i runs inside one, else $XDG_STATE_HOME/h5i/browser, else ~/.local/state/h5i/browser. Sessions live outside any git repository because a browser is about a target rather than a checkout; h5i browser open in an empty directory is the ordinary case.

The default session is per registry, so two agents sharing a $HOME share it. Give each its own $H5I_BROWSER_HOME, or give each session a --session <name>.

variable what it names
H5I_BROWSER_HOME the session registry's directory
H5I_BROWSER_SESSION which session a verb acts on, when --session is absent
AGENT_BROWSER_ARGS extra Chromium launch flags, merged into every launch

audit

requests is the network layer on its own, and the verb to reach for in a loop. h5i browser audit is the one to read afterwards: what the agent asked for, what the proxy decided about every request, who was driving, and how the session ended, merged and ordered.

terminal
$ h5i browser audit
  sources  : actions read · requests read · control read
  note     session rows are ordered by the clock of the process that wrote them

  host    session opened  (http://localhost:3000/ — on this machine, unconfined…)
  proxy   verb   navigate http://localhost:3000/
  proxy   #0 GET http://localhost:3000/
  proxy   #0 200  153 bytes
  proxy   verb   snapshot
  host    control -> human  (taken by a human)
  host    control -> agent  (handed back; the agent must re-snapshot)
  proxy   verb   snapshot
  proxy   #1 DENIED GET https://tracker.example/px  (origin is not in the allowlist)
  proxy   verb   resend
  host    session closed  (closed by the user)

Action and request rows are the session's own account, written by its proxy and its verbs. Handovers and lifecycle are h5i's, written from outside. Every row says which, and the timeline orders across both, so "was a human at the controls when that request was sent" has an answer. sources reports each log as read, empty or unavailable, because an empty timeline over a log h5i cannot see looks the same as a session that did nothing. Rows carry caused_by only where the source recorded the link; nothing is inferred from timing. --json gives the whole thing, including the session record.

h5i recon

Recon is discovery, kept apart from testing. It records what a target exposes and how it knows. Calling a difference a vulnerability stays the agent's claim. Design: docs/design/design-recon.md.

terminal
h5i recon extract                             # read what the session already fetched
h5i recon known                               # robots.txt, sitemap.xml, security.txt
h5i recon crawl --max-requests 200 --rate 4   # walk it under this session's login
h5i recon paths --wordlist ./words.txt        # ask for what was never disclosed
h5i recon triage --calibrate                  # fold the noise, confirm what is real
h5i recon endpoints --state confirmed --json  # the inventory, with evidence

Every endpoint carries a state:

State What it means
candidate Something disclosed it. No request was ever sent.
observed A request answered, and the row names the message.
confirmed The answer differs from what that directory says about a path that is absent.
refused Policy declined it. Kept, because it is a fact about the scope.
gone Confirmed once, and now answering like a missing path.

Only triage --calibrate confirms, by learning what a missing path looks like in each directory. Against an application that answers 200 for everything, nothing is confirmed without it.

h5i ships no wordlist. paths --wordlist takes a list you bring, --reuse-words uses the words the session has already seen, and recon import --format urls|katana|subfinder|httpx|openapi reads another tool's output as candidates, which stay candidates until an h5i request answers. recon export writes the inventory as JSONL, and recon merge --from <session> folds another session's ledger in, keeping each identity's observations apart.

Runs that spend requests are jobs: h5i recon jobs list, jobs show, and jobs resume, which re-runs the same parameters and skips what the ledger has already answered. The ledger is written as a run goes, so a killed run keeps what it found.

h5i websec

The HTTP workbench: read what a session sent, change part of it, send it again, and compare the answers. Design: docs/design/design-websec.md.

terminal
h5i browser open https://target.example
h5i websec requests                              # captured messages
h5i websec show req_42                           # one message, body bounded
h5i websec show req_42 --raw                     # one message, exactly
h5i websec replay req_42 --set query.id=456      # edit and resend
h5i websec replay req_42 --set query.id=456 --body   # print the response body
h5i websec replay req_42 --set-each query.id=./ids.txt --body   # sweep, each body
h5i websec diff res_42 res_43                    # compare two answers
h5i websec match res_43 --status 200 --contains ok
h5i websec experiment ./plan.json                # many sends, folded to clusters
h5i websec finding create --title … --evidence req_42
h5i websec import-nuclei template.yaml           # print an h5i test; sends nothing

Every verb prints text by default: the HTTP message under one line of ids, status, size and time, with the body cut at 4 KiB and control characters made inert.

output
res_43 ← req_43 · 200 · 31 bytes · 4 ms
sent  GET https://target.example/api/invoice?id=456
set   query.id=456 (was 42)

HTTP/1.1 200
content-type: application/json

{"id":456,"owner":"bob"}

--repeat, --race and --set-each print one row per send. --json on any verb gives the JSON envelope with the same exit codes. --body prints the decoded, untruncated response body (the curl view) and --raw prints status line, headers and body (the curl -i view); both work with --set-each and --repeat. The message store holds bodies and credentials in full, which is why it is owner-only and in no export unless named.

h5i browser rpc --stdio is the same verbs over one process: one JSON object per line in, one per line out, ids matched. A loop that sends hundreds of requests pays process startup once.

Experiments

One request sent many ways, with the answers folded into clusters. The plan names what varies; the values are yours.

json
{"request": "req_42",
 "positions": [
   {"name": "user", "target": "query.user", "values_file": "users.txt"},
   {"name": "role", "target": "json.role", "values": ["user", "admin"]}],
 "strategy": "product",
 "baseline": "res_42",
 "extract": {"error": "regex:SQL error: (\\w+)"},
 "rate": 4}

product sends every combination and zip takes the nth value of each position together. Responses group by status, type, redirect target, size and what the body says, so five hundred sends come back as a handful of rows, each naming every message it folded. "as": "other-session" sends under another identity and reads the results from that session's store.

The report counts planned, answered and read separately, and ok is true only when all three agree. A step with no answer is a request the session did not make, usually because the session's allowance of 500 self-sent requests ran out: add "reset_budget": true, or split the plan. The ceiling is 1000 sends per experiment, and --rate caps what the target sees, between one an hour and wire speed. Both are also on h5i browser resend, as --walk and --rate.

Findings

terminal
h5i websec finding create --title "cross-tenant invoice read" \
    --state "verified once" --evidence req_42,res_43 --repro ./exploit.json
h5i websec finding update finding_1 --note "only on the JSON endpoint"
h5i websec finding list

The log is append-only, so what was believed at turn 30 is still readable at turn 300. Title, state and repro replace; notes and evidence accumulate. --state is free text that h5i does not read. h5i asserts one thing here: every message id cited is a message this session holds. Whether the claim is true is the agent's to say.

A session finding lives beside that session and goes when the session does. To keep it, promote it into a project, which copies the finding and the messages it cites with credentials removed.

The capture store

The capture store holds Authorization headers and session cookies in full. It is the one artifact h5i keeps that is unsafe to paste: owner-only, in no export unless named, never rendered by the console. The request log is the part you can paste. See Receipts for which lane observed what, and Files for what is on disk.

h5i project

A browser session is disposable; a project is the durable side of an engagement: notes, findings, the evidence they rest on, the checklists you were asked to cover, and the reports issued from them. It lives under ~/.local/share/h5i/projects, owner-only, and h5i browser rm never touches it.

terminal
h5i project init acme --title "ACME web" --target https://acme.test
h5i browser open https://acme.test --project acme
# ... find something, write a session finding, then keep it:
h5i project finding promote --all -p acme --session <name>

Promoting copies each cited request and response into the project as evidence, with Authorization, Cookie, secret-looking query parameters and JSON or form fields replaced by [removed]. The raw capture is never copied. h5i browser rm refuses to remove a session whose findings are not yet in a project, and names the promote command.

A finding keeps severity, the assessor's confidence and the fix status as three separate fields, because "high but unconfirmed" and "low but confirmed" are different facts, as are "fix claimed" and "fix verified".

terminal
h5i project finding create -p acme --title "Users list readable by any account" \
    --severity high --severity-reason "any authenticated user reads all users" \
    --summary "A normal login can read the full user list." \
    --remediation "Add a role check on /admin/users." --evidence E-1
h5i project note add -p acme "admin panel is at /admin, owner confirmed"

Checklists

A checklist is any Markdown list you import: an internal standard, a client's list, last round's notes. Its items become tracked, and a --required list has to end each item with an outcome (recorded, blocked, not-applicable) and a reason. Coverage is reported as counts: "18 of 24 items have an outcome; 4 open; 2 blocked" says what was looked at, and nothing about the rest being safe.

terminal
h5i project checklist import -p acme checks.md --required
h5i project checklist mark -p acme C1 --status recorded --note "role check present" --link F-2
h5i project checklist coverage -p acme

The report

The report is a free Markdown document you write. h5i fills the counts, ids and evidence through directives it resolves against the project, so the prose cannot drift from the data:

directive renders
{{finding F-3}} the finding in full: severity, status, impact, remediation, evidence
{{findings}} a table of every finding
{{evidence E-2}} the redacted request and response
{{coverage}} coverage counts for every checklist
{{term IDOR}} mark a term for the glossary and a definition panel
{{glossary}} define every term the report used
terminal
h5i project report new -p acme          # a starting template
h5i project report set -p acme report.md   # or write the draft yourself
h5i project report check -p acme        # dangling ids and missing outcomes are errors
h5i project report issue -p acme        # freeze it as a versioned snapshot
h5i project report export -p acme --version 1 --format pdf

check is deterministic: an unknown directive, an id that names nothing, and a required item with no outcome are errors; a finding with no evidence or no remediation is advice. issue freezes the draft with a snapshot of everything it referenced, so a later change to a finding never rewrites a report already handed over. PDF export uses a local Chromium when one is found ($H5I_CHROME names it); otherwise export HTML and print from a browser.

The same report renders in h5i ui under the project's Report tab, where a marked term opens its plain-language definition with a link to OWASP, MDN or Wikipedia. h5i project glossary <term> prints a definition on the command line, and a project's own glossary.toml adds or overrides terms.

h5i test

A finding that is fixed and never tested again comes back. h5i test replays a flow you wrote and checks that a property you stated still holds.

terminal
h5i plugin install test
h5i test --target https://staging.example --openapi openapi.json

Run it in CI beside h5i app extract --check. One gate says the proofs still describe the kernel; the other says the bug you found has not come back.

A test needs a verdict, and there are two. A step may carry expect, data over that step's response: one of status, body, header, headers, response or dsl, combined with all, any and not. A text value is a literal substring, or a regular expression written regex:. When the file names no oracle, exit 0 means every step expect held, 1 means one did not, and anything else means the test could not decide. That third answer is never a pass.

expect reads the responses in the flow and does not call out. For a property it cannot express, name an oracle: jq, grep, diff, or the application's own test client. If the file names an oracle, the oracle decides. A file with neither is refused.

yaml
flow:
  - send: probe
    expect:
      all:
        - status: 200
        - body: "regex:role.*admin"

Where tests live

Tests are strict YAML or JSON with version: h5i.test/v1, under .h5i-tests/tests, committed with .h5i-tests/oracles. That directory sits outside .h5i/, which is local state and gitignored.

A request template carries a method, a target-relative path, headers and a body. ${name} uses a value an earlier step extracted; ${env.NAME} reads a CI variable. Unknown and missing fields are errors. Actors name isolated sessions and cookie jars, which is what makes a two-identity authorisation test portable. A step sends a template as an actor, may apply the websec edit language, saves its response under a stable name, and may extract a regex, JSON field, header or status for later steps. Cleanup runs after the verdict even when it fails, and a passing verdict with a failed cleanup is an error.

Importing a Nuclei template

h5i websec import-nuclei template.yaml reads one Nuclei template and prints an h5i.test/v1 document. It sends nothing. Matchers become expect, and the command never writes an oracle. Save the document under .h5i-tests/tests and run it with h5i test on the target and under the policy you would use for a test you wrote.

A template that cannot be said as data is refused, and the refusal is the result. A code, javascript, headless or flow block runs code, so the command will not keep its HTTP requests and drop the rest. An unsafe raw request, an out-of-band matcher such as interactsh, a payload list stored in a file, and a path that is not relative to {{BaseURL}} are refused the same way. An inline payload list becomes a sweep on that step, which passes if expect held for one combination.

What the oracle is given

The oracle runs with its working directory set to the test file's directory.

Variable What it holds
H5I_TEST_RESULT The structured JSON evidence bundle.
H5I_TEST_ARTIFACTS Its owner-only artifact directory.
H5I_TEST_INPUTS The saved response names the test declared, comma separated.

Coverage

A send may declare the OpenAPI operation and mutation class it exercises. It counts only when the flow completed and the verdict decided. Setup and cleanup sends without covers never count, and an error is never a covered operation. With --openapi, h5i reports that coverage, report-only unless --min-coverage is given. Without an OpenAPI denominator it reports no percentage and refuses a minimum.

Every run writes result.json, junit.xml and per-response artifacts into an owner-only directory, because response bodies are evidence. Credential request headers are redacted from exported request JSON; response bodies stay exact and are never uploaded.

Containment (optional)

Nothing above this line needs a box. A box is for the agent that writes the kernel or drives the attack, and for what it produces, when you want that held at arm's length. Without one, a session's Chromium runs on this machine as an ordinary process, and its status line says so:

text
placed : on this machine, unconfined — agent-browser and Chromium run as ordinary host processes

The proxy decides what the browser may reach and writes every decision down. The browser itself is unconfined. Reach for a box when:

  • The code under test is untrusted, or an agent wrote it.
  • A target's response might be hostile, and a parser bug should land somewhere disposable.
  • You want the browser confined and its network decided outside it. A box's browser profile runs Chromium through agent-browser under the box's tier and egress allowlist.

An agent inside a box opens a session the ordinary way, and the session runs beside the agent in the same box.

Boxes

A box is a disposable environment holding a checkout, a toolchain, a dev server and, with the browser profile, a Chromium. Nothing of your machine is inside it, egress is an allowlist enforced at its boundary, and the only way out is the output gate.

terminal
h5i box .                       # snapshot this repository at HEAD
h5i box --pr 1234               # a pull request (number, #number, or URL)
h5i box https://github.com/o/r  # clone an external repository
h5i box --new                   # an empty box; the agent builds from nothing

h5i box [SOURCE] is shorthand for h5i box create and takes the same flags. Where the code comes from decides the shape of the box. This repository becomes a real git worktree on its own branch, sharing the object store, so h5i box apply can land it back locally. A URL, a PR or --new makes a detached box: it gets a repository of its own inside its directory, this repository is neither read nor written after creation, and the inherited origin remote is dropped. apply and rebase refuse on a detached box and point at export. External code should always arrive in this shape.

h5i box create

text
h5i box create <NAME> [--from <rev>] [--pr <n>] [--clone <url>] [--new]
                      [--profile <p>] [--isolation <tier>] [--image <img>]
                      [--engine <chromium|lightpanda>]

The base revision is frozen at creation and pinned immutably. The policy is resolved, digested and stored before any state is created on disk, so an unsatisfiable request fails closed and leaves nothing behind.

Flag Meaning
--from <rev> Base revision (default HEAD).
--pr <n\|url> Fetch refs/pull/<n>/head and pin it as the base. Needs only git.
--clone <url> Copy an external repository in. Detached.
--new Empty box (a fresh repository with one empty commit). Detached.
--profile <p> See Profiles.
--isolation <tier> See Isolation tiers.
--image <img> Base image for isolation=container and isolation=microvm. Pre-pulled; runs never pull.
--engine <e> Browser engine for the browser profile: chromium (default) or lightpanda. Pinned in the digest; never falls back.

A profile can also refuse individual browser actions, enforced by h5i on the daemon's control socket:

toml
[profile.browser.browser]
deny = ["evaluate", "state"]   # a bare family name covers state_save/state_load

evaluate is arbitrary code in the page; state_* and credentials_* reach the browser's stored secrets. A denied verb never reaches the browser, and the refusal lands in the receipt's browser-proxy lane. This is enforcement against an agent using the documented path. The daemon runs inside the box, and a box has no internal privilege boundary.

Working in a box

terminal
h5i box ls                            # every box on this clone
h5i box status <name>                 # policy actually enforced, evidence, base drift
h5i box run <name> -- cargo test      # one command; the exit code passes through
h5i box shell <name>                  # interactive confined session
h5i box diff <name>                   # what changed against the pinned base
h5i box log <name>                    # the box's event log

h5i box shell is the agent-in-box: stdio is inherited, so every command the session spawns is contained by the box rather than by the agent choosing to wrap each call.

Services and ports

terminal
h5i box service start <name> <service>   # a declared long-lived process
h5i box service status <name>
h5i box service logs <name> <service>
h5i box ports <name>                     # the per-box dynamic port map

Services are declared in .h5i/env.toml:

toml
[service.web]
command = "npm run dev"
port = 3000

Services work at the workspace and process tiers. At supervised and container the network namespace belongs to a single session, so run the dev server inside the same h5i box shell as everything else.

h5i box export

export is the output gate. A box has no write access outside itself, and this is the only way out, taken by a human.

terminal
h5i box export <name> --out ./review
git apply --3way ./review/patch.diff
File What it is
patch.diff The tree diff against the pinned base, path-validated: no symlink escapes, no nested .git, no agent-introduced gitlinks.
report.md What ran, what the browser saw, who was at the controls, and the agent's own proposal.
receipt.json Every observed execution, with the policy digest that was enforced.

It refuses to overwrite a non-empty directory (--force to replace). Secret redaction and size caps apply throughout. Read report.md before applying, in this order: denied egress attempts, every command with its lane and exit code, what the browser saw (console errors, uncaught exceptions, failed requests, all observed by h5i), viewer sessions including whether a human took the controls, and the agent's proposal.

h5i box apply <name> lands a proposed box onto its parent branch in this repository instead. It refuses for a detached box.

h5i box cache

Cold dependency install is the difference between a 20-second box and a four-minute one.

terminal
h5i box cache ls              # caches for this project, and whether they are stale
h5i box cache mounts          # exactly what a box would get
h5i box cache refresh <eco>   # populate one, in a dedicated box with no agent in it
h5i box cache rm <eco>

One cache per project and ecosystem, keyed by a digest of that ecosystem's lockfiles. A cache whose key no longer matches is listed stale and never handed to a box. Caches are mounted read-only into an agent box; every package manager falls back to fetching what it cannot find, so this costs no correctness. Only h5i box cache refresh writes a cache, in a box with egress narrowed to the registry hosts and no agent inside. It needs a project-declared profile for that, and refuses with the profile printed ready to paste rather than creating a box whose fetch could not work. No mutable surface is ever shared between an agent box and anything else.

h5i box view

terminal
h5i box view mybox
h5i box view mybox --web

The viewer combines the rendered page with action, network, console and policy events. Each row keeps its observation source and evidence grade separate, and h5i infers no causal link the event stream did not record.

Choosing the engine

--engine selects the browser engine for a box's browser profile and records the choice in the policy digest. Both engines are driven by agent-browser.

engine use
chromium Default; broadest web compatibility.
lightpanda Third-party lightweight headless engine; still runs script.

Chromium runs with an isolated profile under the box's policy. Its requests are seen at the box's boundary and by h5i's mediator on the agent-browser socket, so inspect the box-level network evidence. An older profile that pins --engine h5i is refused by name: h5i's own engine now lives in h5i-browser.

Inspecting a box

terminal
h5i box probe                       # what this host can enforce at all
h5i box capabilities <name> --json  # what this box actually got
h5i box doctor <name>               # can it still enforce its claim? are its refs intact?
h5i box secrets <name>              # declared grants, dry-run resolution, never values
h5i box inspect <name> --capture <id>
h5i box compare <a> <b>             # boxes side by side

h5i box watch is the tail of the receipt: no viewport, no panes, no control lock. Pipe it, grep it, leave it in a second pane. Every row names the lane that observed it and the grade of that evidence in words. --json emits the same event envelope the console reads, one object per line.

Lifecycle

terminal
h5i box rebase <name>       # re-pin onto the parent branch's current tip
h5i box abort <name>        # stop; manifest and workspace preserved for forensics
h5i box rm <name> [--force] # remove entirely

h5i box allow

terminal
h5i box allow                 # list the current entries
h5i box allow api.example.com

A persistent, user-level egress allowlist merged into every container- or microvm-tier box whose profile already sets net.egress. A deny-all profile is never widened. It is stored under ~/.config/h5i/, outside every box-granted path, and refuses to run inside a box.

Policy

A policy says what a box may read, write and reach. It is resolved at creation, serialized to policy.resolved.toml, and digested. Every receipt records the digest that was in force, so "what was enforced" never rests on trust.

Profiles

Built-ins need no file:

Profile What it grants
default Fail-closed build/test confinement: system paths read-only, $WORK read-write, no network.
agent The agent-in-box surface, scoped to $H5I_AGENT's runtime.
agent-claude / agent-codex Pin one runtime: only that agent's HOME state and API egress.
browser The agent profile plus headless Chrome and the agent-browser daemon.

Runtime scoping matters: a Claude box must not get Codex's credentials or egress to OpenAI, because a prompt-injected agent could otherwise read the other runtime's token and use it against an allowlisted host.

The built-in read set carries the paths /etc/resolv.conf is a symlink to (/mnt/wsl/resolv.conf on WSL, the systemd-resolved and resolvconf locations under /run). /etc alone is not enough: Landlock follows the link to a path the box was never granted, getaddrinfo answers "Temporary failure in name resolution", and a net.mode = "host" box reads as a machine with no network. The entries are the same on every host, so a profile gets one digest everywhere. A custom profile that sets fs.read replaces that list, so add what readlink -f /etc/resolv.conf names on your host.

Custom profiles live in .h5i/env.toml:

toml
[profile.review]
isolation = "supervised"

[profile.review.fs]
read  = ["/usr", "/etc"]
write = ["$WORK"]

[profile.review.net]
mode     = "deny"
egress   = ["api.github.com"]
unix     = false          # AF_UNIX sockets; see below
loopback = [3000]         # macOS only; see below

[profile.review.resources]
mem   = "4G"
procs = 256
wall  = "30m"

Isolation tiers

Tier Boundary Network
workspace Separate worktree only none
process Landlock, seccomp, namespaces, and resource limits deny or host
supervised Process tier plus private network and socket supervision L3/L4 allowlist
container Rootless Podman proxy-based L7 allowlist
microvm Hardware-isolated guest via microsandbox guest L3/L4 allowlist

auto chooses the strongest available tier. An explicitly requested tier fails rather than silently downgrading. The microVM tier needs msb 0.6 or newer, host virtualization, and a pre-pulled OCI image. It protects the host kernel boundary, and it has no per-request egress tally or authenticated-egress grants yet. h5i box probe reports missing requirements.

AF_UNIX sockets

[profile.X.net] unix = true lets the box create AF_UNIX sockets. It is off by default because SCM_RIGHTS passes file descriptors, which is authority smuggling. Abstract sockets are scoped by the box's private netns, filesystem sockets by Landlock, and /tmp is a per-box scratch at the kernel tiers, so what the grant opens is a host socket sitting inside a granted path. The browser profile sets it, because the agent-browser daemon's control socket is a filesystem-bound AF_UNIX listener.

Credentials

The model API key stays on the host. A reverse proxy injects it into outbound requests from the box, scoped per runtime, so a Claude box cannot reach the OpenAI credential. Any other service uses the same mechanism, declared as policy:

toml
[[profile.review.auth]]
host           = "api.github.com"
credential_env = "GITHUB_TOKEN"   # read on the host, never in the box
base_url_var   = "GH_HOST"        # what the client reads
token_var      = "GH_TOKEN"       # where the box gets its per-run dummy

token_var is required: the proxy gates every request on a per-run token, handed to the box in whatever variable its client already sends as a credential. The real credential stays on the host. This binds only clients you can point at another origin, so a plain curl https://api.github.com still goes nowhere; a TLS-terminating forward proxy would lift that at the cost of a CA the box trusts, and it is not built. What the box may do with a credential is authorization, and belongs in a fine-grained token scoped to one repository and the operations you meant.

Per-box HOME state is a copy of the host agent's config, seeded once and never written back, with credential-shaped entries stripped at any depth (credentials*, .netrc, ssh keys, *.pem/*.key/*.p12). Only the runtime's own token is kept, because it cannot function without it.

Secrets

Declared per profile, brokered host-side, injected for the life of one run:

toml
[profile.review]
secrets = ["DEPLOY_KEY"]

[profile.review.secret.DEPLOY_KEY]
source = "env:H5I_SECRET_DEPLOY_KEY"   # the default for a bare name
inject = "env"                          # `file` is workspace-tier only in v1

The value never appears in the policy, the digest, or any receipt. h5i box secrets <name> dry-runs the resolution and reports a fingerprint. A grant that cannot be resolved fails the run closed.

Two limits on what a source may be, because a profile lives in the repository. source = "command:…" runs host-side code outside the sandbox, as you, so it needs both the profile's allow_command_extractors = true and H5I_ALLOW_COMMAND_EXTRACTORS=1 in your environment: the profile flag pins the decision in the digest and cannot also be the authority for it. source = "file:…" is a host-side read handed to the box, so it may not point inside the profile's fs.deny.

An [[auth]] grant is the one place h5i attaches a credential you hold to a request it originates. The destination must be a bare hostname, and every run prints which variable is attached and where it goes. ttl is advisory and shown as ttl=<value>(advisory): h5i resolves a grant once and never expires it.

Engagement scope

A profile says what this machine will permit, and a scope says what the target's owner authorised. Both are enforced, and each has its own digest. A scope is one TOML file per project, at ~/.config/h5i/projects/<name>.toml:

toml
allow      = ["*.acme.com", "api-staging.acme.io"]
deny       = ["blog.acme.com"]
deny_paths = ["/admin/*", "/account/*/delete"]

h5i browser open --project acme resolves it. allow joins the origin grant. deny and deny_paths are checked before the wire, ahead of the loopback exemption and the instrument mode, and nothing can grant past them. An unknown key is an error.

The file's location does three things. ~/.config/h5i is in every profile's fs.deny, so a box cannot widen the scope confining it. The capture proxy never reads it: h5i browser resolves it and passes the rules as arguments. And it works outside a repository, because an engagement is not a checkout. The digest goes on the session record as scope_digest, beside policy_digest, so a reviewer can see which document changed. A project with no scope file is allowed; --project is then only a label.

Receipts

A receipt is the record of what ran in a box: one append-only JSONL log per box, plus the raw payload of each record. It is generated from observation, never from the agent's account of itself, and it is what the dashboard, h5i box export and h5i box watch read.

The log is append-only and sealed. The box's write window under its own directory is exactly <box>/spool; the receipt log and the stored payloads are siblings of that spool, outside every grant. The box stages a record and the host ingests it, so there is no path from inside to a record the host has already written. Secrets are scrubbed from the command and the payload before either is written, and the scrub is recorded by rule id, never by value.

Every record carries the lane that observed it:

Lane Who observed it
host-env-run h5i, host-side. Exits and resource usage come from the supervisor's wait4; egress from the allowlist proxy's own log.
viewer h5i's own viewer forward. The box supplies none of it.
tee-shim The box's shell shim. Box-claimed.
inbox-capture Staged by the box. Box-claimed.

A run that drove the browser also carries what the page said back: console errors, uncaught exceptions, and requests that failed. h5i collects these itself right after the command, in the same box under the same policy, so the timing is never the agent's to choose. A browser command with no browser to ask is recorded as unavailable, because "nothing was looked at" is a different claim from "nothing was wrong".

An agent can stage extra records, or stop writing. Both are visible: a gap between host-observed exits and box-reported commands is itself a finding. h5i claims no more than that.

The console

terminal
h5i ui
h5i ui --port 0
h5i ui --open

h5i ui opens the dashboard: one read-only web screen over the three parts above, from the proofs behind an application to the traffic of a browser session and the receipts of a box. Every route it calls is a GET, and every next step it suggests is a command it copies to the clipboard. The rail has six sections:

section shows
Overview what wants a person, and what is running
Projects every engagement, its findings by severity, checklists, notes and the report
Apps each h5i-app project: its guarantees, the conditions they rest on, and the mutants its proofs caught
Sessions the browser sessions on this machine
Boxes the boxes of the repository the dashboard was started in
Host what this machine can enforce

Apps is the review surface for the framework side. Select a project and follow a guarantee from its specification to the code, the conditions it relies on, and the bugs its proofs detect. The page lists promises and conditions per route, marks a condition that drifted since the last recorded check, draws the application flow as a map, and keeps a catalog of the recorded Lean declarations with their source. The mutation view shows each h5i app mutate experiment and which mutants survived. It reads h5i-app.toml, the sources and .h5i/app/runs, and runs no proof itself.

Sessions are listed loudest first and searched by name, id or target. Selecting one opens six tabs:

tab shows
History every fetch: the agent verb that spent it, method, host, path, status, size, time, initiator. A filter bar (host:api status:4xx -path:/static verb:click refused), sortable columns, and an inspector that draws why the fetch exists and the command that reads its bytes
Sitemap what the session reached as a tree of origins and paths, counts folded upward, refusals kept apart
Actions h5i browser audit as a timeline: each verb, whether it succeeded, and the receipts it spent
Findings what the agent concluded with h5i websec finding, each with the message ids it rests on
Recon the endpoint ledger by state, and the runs that spent requests
About the record: placement, confinement, engine, identity, policy digest, capture

Boxes show each box's tier, status and one signal, and for a selected box its findings, a flight recorder of one row per receipt across five lanes (files, egress, exit, limits, page), the policy that was enforced, and the diff against the pinned base. A browser box has a second tab with the live in-box browser terminal.

The dashboard never renders a stored message. Bodies, cookies and Authorization headers stay in the capture store on disk, owner-only, and each request row prints the h5i websec show that reads it. It binds loopback and uses a random bearer token in the URL; any local process or page that obtains the URL can read it, so keep it private. Untrusted box and page strings are rendered as text, never HTML. It can stop a browser or take its control lock. It cannot edit a box or widen its policy, and it never runs a proof.

Reclaiming space

A session's record, logs and ledger are small; its capture store is the part worth reclaiming.

terminal
h5i browser rm <session>...          # erase sessions entirely (--force for a live one)
h5i browser rm --ended               # every session that has ended
h5i browser rm --older-than 30 --dry-run
h5i browser gc                       # reclaim stored messages older than a week
h5i browser gc --older-than 0 --dry-run

rm takes the whole directory: record, logs, jar and store. gc takes only the stored messages of ended sessions and leaves a capture-reclaimed.json where they were, so "kept and later reclaimed" stays a different fact from "never kept". close keeps a session's record, so rm is the verb that shortens a long list. Without names it selects by shape: --ended, --all (a live one still needs --force), or --older-than DAYS. --dry-run says what would go and removes nothing.

Session states

Every session gets one of five states, each carrying the evidence that produced it:

State What it means
waiting on you A human holds the control lock, or a run stopped for a reason a person has to answer.
finished, unread The session ended, or its last run finished, and this browser has not looked.
working Live, and something happened in the last minute.
idle Live and quiet.
unclassified The record says live and the session's control file is gone.

The bar at the top counts them and filters the list. finished, unread clears when you open that session, and the memory of what you have read is this browser's alone: the console never writes it back, which is what keeps a passive view passive. Boxes keep their own words in the same bar (refused egress, with failures), because a refusal is the boundary working.

h5i skill

skills/h5i/ is embedded in the binary at build time, so the skill cannot document flags the installed binary lacks.

terminal
h5i skill install [--target <dir>]   # write it out
h5i skill show [<page>]              # print SKILL.md or one reference page
h5i skill path                       # where an install would write

This is also how the in-box agent gets the skill: nothing is baked into an image, and nothing is copied from host to box.

h5i plugin

A plugin is a separate executable h5i runs by name, installed by hand.

terminal
h5i plugin install websec --from ./h5i-websec   # from a release archive or a build
h5i plugin install recon --from ./h5i-recon
h5i plugin list                                 # what is installed, and what exists
h5i plugin remove recon

Only names h5i knows can be installed, and they live in h5i's own state directory rather than on $PATH, so h5i plugin list is the whole truth about what h5i <name> can become. A plugin holds no privilege of its own: it reaches a session through the same verbs a person types, so its requests are the session's, checked by its policy and written into its receipts. A build without a plugin still knows the name, so h5i recon on a plain install says what the capability is and how to get it.

Limits

h5i states these limits because its claims are security-sensitive.

  • Containment cannot stop an agent from sending source code to an allowed model API. Use a trusted model endpoint or deny model egress when that matters.
  • Workspace, process, supervised, and container tiers share the host kernel and are no defence against a targeted kernel exploit. The microVM tier adds a hypervisor boundary.
  • Container egress is proxy-based and applies only to software that honours the proxy. Supervised and microVM tiers enforce network rules lower in the stack.
  • Interactive workspace, process, and supervised shells share a terminal with the operator. Depending on the OS and kernel, a process may inject input, keep reading an inherited terminal, or leave terminal settings changed. h5i box probe reports input-injection exposure. Container and microVM terminals are separate.
  • Chrome's own Linux sandbox is disabled inside a box because h5i's seccomp policy blocks the namespace operations it needs. The box boundary remains; one browser defence layer is absent.
  • On macOS, a box shares the host's loopback. Declared service ports are reachable locally, and manually started services must list allowed loopback ports. Linux boxes use a private network namespace.
  • macOS Seatbelt has no seccomp equivalent, cgroup memory ceiling, or per-box process-count ceiling. Status and probe output mark those gaps. Use a container or microVM when hard resource ceilings are required.
  • Chromium placement on macOS relies on the tier's egress boundary rather than agent-browser's in-process domain list. Chrome may restart when its proxy route changes, losing its temporary browser profile.
  • Browser viewing covers the rendered tab, not browser chrome, native dialogs, or the desktop.
  • Chrome consumes substantial memory and CPU. Browser support is opt-in per box, and Chromium driving depends on the pinned external agent-browser tool.
  • A browser session records what its Chromium sends through the session's loopback proxy. agent-browser and Chromium run as ordinary host processes and are launched with --ignore-https-errors, so Chromium accepts every certificate error for that session.
  • A request the browser sends without the proxy (a Chromium relaunched by hand without the proxy settings) is absent from the session's record. status warns after five minutes with nothing captured.
  • GPU execution of a kernel is checked by differential tests against the CPU path. Those tests are evidence for the executions they ran, and no proof about the GPU.

A browser session's directory

Sessions live under $XDG_STATE_HOME/h5i/browser (~/.local/state/h5i/browser by default, 0700), one directory per session id. The layout is a contract: everything h5i knows about a session is a file here, in a shape jq can read.

Path What it is
sessions/<id>/session.json The record: what h5i browser status --json prints.
sessions/<id>/requests.jsonl The request log, one JSON object per line, written before the wire.
sessions/<id>/actions.jsonl The verbs the agent asked for, page verbs and workbench verbs both.
sessions/<id>/messages/ The capture store: headers and bodies both directions. 0700.
sessions/<id>/findings/findings.jsonl What h5i websec finding wrote.
sessions/<id>/recon/ledger.jsonl The endpoint ledger.
sessions/<id>/recon/jobs/ One record per recon run that spent requests.
sessions/<id>/artifacts/ Files the session produced: screenshots, and the output of every page verb.
sessions/<id>/dom-report.jsonl What the DOM instrument reported, for a session opened with --dom-instrument.
sessions/<id>/control, control.jsonl Where the session's control channel listens, and the handover journal.
sessions/<id>/proxy The session's loopback proxy URL.
sessions/<id>/proxy-ca.pem, proxy-ca-key.pem That session's interception CA and its private key, both 0600.
sessions/<id>/proxy.log The proxy process's stdout and stderr.
default The id every verb acts on when nobody says which.

Two rules for scripts that read these. The capture store holds Authorization and session cookies in full, so a script that copies out of messages/ is copying credentials, and proxy-ca-key.pem signs the certificates the proxy presents. A session's name can be reused once that session has ended, so group by project or id, never by name.

Environment variables

All optional; h5i ships with working defaults.

Set by you

Variable Purpose
H5I_AGENT Which runtime a box is scoped to (claude, codex). Decides the box's branch namespace and the agent profile's credentials and egress. The namespace takes 1 to 64 ASCII letters, digits, hyphens or underscores; unset is human silently, anything else warns on stderr and namespaces the box under human.
H5I_DEFAULT_ISOLATION Pin this clone's default tier when --isolation is absent. --isolation auto re-probes past it.
H5I_SECRET_<NAME> Default source for a secret grant <NAME>. Injected for one run, redacted from evidence, audited by fingerprint. For a browser session, the value h5i browser type puts in place of $H5I_SECRET_<NAME>.
H5I_BROWSER_HOME, H5I_BROWSER_SESSION Where browser sessions live, and which one a verb acts on. See Where sessions live.
AGENT_BROWSER_ARGS Extra launch flags for a browser session's Chromium, such as --no-sandbox.
H5I_CHROME The Chromium h5i project report export --format pdf renders with.
H5I_SKILL_DIR Where h5i skill install writes.
H5I_CREDENTIAL_PROXY Turn the credential proxy off (0) for a box that must reach the model API directly.
H5I_LOG tracing_subscriber filter for h5i's own diagnostics, e.g. h5i_core=debug. Goes to stderr. RUST_LOG is honoured as a fallback.
H5I_NO_PROBE_CACHE Re-probe host capabilities instead of reusing the cached answer.

Set by h5i, inside a box

Read these to detect that you are in one; do not set them yourself.

Variable Meaning
H5I_ENV_ID The box's id. Its presence is how the skill decides you are inside.
H5I_ENV_POLICY_DIGEST The digest of the policy enforced.
H5I_ENV_CAPTURE_SPOOL The box's only write window: staged receipt records.
H5I_ENV_BASE_TREE, H5I_ENV_AUDIT_CAPTURE Box plumbing.
