# What h5i-app proves, and what it assumes

Assumption IDs (A1 to A11) come from the ledger in
[design-app-roadmap.md](design-app-roadmap.md); code and other docs cite
them.

## Proven in Lean

Every theorem is about the Rust as Charon and Aeneas extract it: the
kernel's `transition` and `apply`, the token parser and encoder, the JSON
writer, and the storage path.

| Code | Proven | Where |
|---|---|---|
| `sql_writes`, generated table operations | store what `apply` computes | `Storage.lean`, `H5iAppLib.Store` |
| `h5i_app_sql::plan` | computes `planA` | `crates/h5i-app-sql/proofs` |
| `h5i_app_pgsql::valid`, `create`, `select`, `compile`, `render` | under `H5iAppLib.Pg`, a compiled statement does to the tenant's rows what `H5iAppLib.Sql.exec` says and touches no other tenant or table (`Pg.compile_sound`); a compiled `SELECT` returns the tenant's matching rows once each (`Pg.select_sound`); a quoted name reads back as itself (`Pg.lexName_quote`) | `crates/h5i-app-pgsql/proofs` |
| `H5iAppLib.Query` | the meaning of declarative reads, and slice lemmas for frame theorems | `crates/h5i-app-core/proofs/H5iAppLib/Query.lean` |
| generated `PgServed`, `pg_loaded_inv` | an invariant kept by accepted write sets holds in every state of a multi-tenant database and every snapshot loaded from it | `generated/Schema.lean` |
| `h5i_app_std::authz::guard`, `guard_viewed` | for every kernel and policy: a committed command's writes are permitted, each in the state the writes before it leave; its disclosed rows are stored as disclosed and visible; read-only commands under `guard_viewed` are noninterfering with what the view hides, and `ReadOnly.Sound` | `crates/h5i-app-std/proofs/AuthzSpecs.lean`, `generated/Authz.lean` |

Each server app with hand-written proofs applies `pg_loaded_inv` to its
extracted `transition`, `sql_writes` and `decode` as `db_inv`: for the
server's schema and any tenant, every database reached by loading with the
compiled `SELECT`s, running a successful `transition` and storing its
compiled writes, among other tenants' compiled statements, holds a state
satisfying `Inv`, and every later load decodes to a snapshot satisfying
`Inv`. An `[authz]` app instead gets `Committed.pg_stored` generated, with no
invariant beyond it; its store is generated by `schema!`, and that the
server runs it is trusted ([design-app-authz.md](design-app-authz.md)).

### Declarative reads: tested, not proven

`h5i_app_pgsql::compile_read` is not extracted. It is checked against
`h5i_app_sql::eval`, a reference evaluator that follows the Lean
definitions: 3,200 random reads on PostgreSQL (`crates/h5i-app-pg/src/reads_test.rs`:
nested `IN`, windows both ways, `NULL`s, a second tenant's rows), and 200
evaluator answers checked as `#guard`s in the Lean build
(`crates/h5i-app-sql/tests/query_cases.rs`). `compile_read` rejects `IN` on
a nullable column and windows over text or bytes keys (collation-dependent
order). Trusted: PostgreSQL evaluates `SELECT`, `IN`, scalar subqueries and
`ORDER BY ... LIMIT ... OFFSET` as documented, and the tests' coverage.

The opt-in `ReadSqlMode::ScalarWhenUnique` (set on the pool before serving)
replaces `IN` by scalar `=` when the subquery fixes the whole primary key.
An empty lookup gives SQL UNKNOWN, which selects the same rows as FALSE only
because the language has no negation; adding negation needs this reviewed
again. It is tested by 120 more PostgreSQL cases per mode and adds no formal
guarantee.

## Enforced by structure

| Property | How |
|---|---|
| Handlers go through the kernel (A8) | App code gets `H5iApp::respond` / `Engine::execute`, never a DB handle. A `Store` gets an opaque `h5i_app_pg::Tx` with only `load_table`, `load_read`, `count_read` and `store_writes`. `cargo deny check bans` rejects database crates outside `h5i-app-pg`. `h5i_app_pg::lockdown` gives the tables to a NOLOGIN owner and row access only to the engine's role. Not confined: `H5iApp::engine()` executes as any principal, and `Engine::snapshot`/`snapshot_for` and `Engine::migrate` act outside commands (`h5i app lint` flags the first two for `[authz]` apps). A superuser bypasses all of this. |
| Tenant isolation | Every compiled statement filters on or writes its tenant, `tenant_id` is in every primary key, and `Pg.compile_sound` proves other tenants' rows stay as they were. The engine and each `Store` must pass `K::tenant(actor)` consistently. |
| Every column is persisted | `table!` must list every field to compile. |
| Running code is the extracted code (A9) | CI re-extracts every kernel and extracted crate with pinned tools and fails on a diff. |

## Assumed

| ID | Assumption | Mitigation |
|---|---|---|
| A1 | The `Authenticator` returns the principal that sent the request. | An accepted token's signed payload is proven to be exactly `enc(tenant, user, exp)`. HMAC-SHA256 from libcrux 0.0.8 (HACL*-verified, pre-1.0). Trusted: the key and its storage, the expiry clock, `ct_eq`. |
| A2 | The JSON codec decodes the command the client meant. | Theorems cover every command, so this affects correctness, not security. `deny_unknown_fields`; tagged enum. |
| A3 | Reply rendering shows the kernel's reply. | Bytes come from the proven `h5i-app-json` writer. Trusted: the app's reply-to-`Value` mapping and `Value` flattening (tested against serde_json). |
| A4 | PostgreSQL runs the rendered subset (`CREATE TABLE IF NOT EXISTS`, `INSERT ... ON CONFLICT`, `DELETE ... WHERE`, `SELECT ... WHERE`) as `H5iAppLib.Pg` says: `=` only for equal non-`NULL` values, `IS NOT DISTINCT FROM` also for `NULL`, a statement fails or has the modeled effect, text compares byte by byte, the driver converts `Val` losslessly, and existing tables came from the same schema. `schema_spec()` describes the tables correctly. | The path up to the model is proven. Each server's `tests/postgres.rs` runs against PostgreSQL. Every compile checks `h5i_app_pgsql::valid`; `schema_is_valid` checks numbering and key lengths. |
| A5 | SERIALIZABLE commits equal some serial order. | Documented PostgreSQL guarantee. Theorems over `H5iAppLib.Run` cover concurrency only through this. |
| A6 | `crates/h5i-app-pg` meets the engine contract below. | App code cannot reach its pool or transaction. Integration tests cover concurrency, retries, idempotency, connection loss, scoped reads and the outbox. |
| A7 | Charon, Aeneas and Lean translate faithfully and check soundly. | Axiom gate; Rust-vs-Lean differential test. |
| A8 | The engine role is not a superuser and no other service has its credentials. | h5i-app cannot stop a superuser. |
| A11 | For `[authz]` apps, the reviewed surface (`Policy`, `View`, `Disclose`, the `authz_kernel!` call, the `h5i-app-*` dependencies, the engine line) is what the author meant, and the author does not deceive their reviewer. `Disclose` lists every row a reply carries; `View` hides what `visible` hides; a write command's handler does not copy hidden rows into its writes or derived reply values; replayed idempotent replies were shown to the same user before. | The surface is Rust extracted with the kernel, with no generator between it and the theorem. Read-only commands under `guard_viewed` do not rely on `Disclose`. |
| | Shell inputs in the principal are true: slugs (Wastebin), GitHub teams and download counts (crates.io), password checks (Atuin, Wastebin, Conduit), time in Conduit's commands. | Theorems hold for every value; each app's README lists them. |
| | The clock (`Clock::System`, or `Clock::Database` via `transaction_timestamp()`) is right; `HmacAuth` expiry uses the system clock. | A wrong time only leads to decisions on that time. `H5iAppLib.ReachableT` proofs hold for database runs only under `monotonic`. |
| | axum, hyper and tokio deliver requests and responses intact. | Widely used. |

## Deployment

1. As admin: `CREATE ROLE app_engine LOGIN PASSWORD '...'` (not a superuser, not the table owner).
2. As admin: `Engine::install_schema`, then `h5i_app_pg::lockdown::<App, Store>(admin_url, "h5i_owner", "app_engine")`. Idempotent; rerun after adding tables. With `with_schema`, use the schema in both URLs.
3. Run the server with `DATABASE_URL` for `app_engine`. Other roles get `permission denied` (`tests/lockdown.rs`).

## Trusted engine contract (A6)

- One attempt loads one tenant, calls `transition`, writes and commits in one SERIALIZABLE transaction. Prepared-statement caching and pipelined reads change neither the text, the parameters nor the snapshot.
- Each retry opens a new transaction, reloads, reads a new time and reruns `transition`.
- A refused transition rolls back and writes no app or framework rows.
- App writes, the idempotency reply, `h5i_clock` and outbox rows commit in the same transaction.
- Keys are stored per `(tenant, ReplyCodec::scope(actor), key)`; reuse with another fingerprint is rejected.
- A connection lost before COMMIT aborts or retries from BEGIN. If lost during COMMIT, a keyed request retries; an unkeyed one returns `DbError::CommitUnknown`, and the caller must assume neither outcome.
- Advisory locks (`Store::lock_for`) are taken before BEGIN in one global order and released before the connection returns to the pool. No proof depends on them.
- A `Kernel::read_only` command runs in one `SERIALIZABLE READ ONLY DEFERRABLE` transaction, without locks or an idempotency key (a keyed request takes the write path), retried only on connection loss. A non-empty write set fails the request instead of being dropped.
- Outbox deliveries may repeat, keep a stable key, and go only through the destination registry.

Also trusted: the `ReplyCodec` fingerprint and scope, the clock source, the
registry, pool cancellation, and the code implementing the contract. If all
this holds, each tenant's committed state comes from a serial sequence of
successful transitions, so `db_inv` applies to it and every later load.

A read-only kernel proves `H5iAppLib.ReadOnly.Sound` for its extracted
`read_only` (`h5i app lint` fails a server that overrides `read_only`
without it; `guard_viewed` provides it as `<fn>.read_only_sound`). Because
such a request writes nothing and PostgreSQL's deferrable read-only snapshot
shows a prefix of the serial order, the reply is `transition` of a reachable
state. Trusted: the safe-snapshot guarantee, and that `Kernel::read_only`
delegates to the proven function (the lint checks a proof exists, not the
delegation).

## Not covered

- Refusals are not stored under idempotency keys; a retried refusal runs again on the new state.
- Migrations are checked, not proven, and do not establish reachability: `Engine::migrate` commits only if every tenant passes the proven-exact checker. Cost grows with data.
- Effects arrive at least once; receivers dedupe by delivery key. The dispatcher, its registry and `Deliver` are trusted; endpoint address checks belong there.
- The RAM executor and the CUDA experiment add no kernel theorem; their trusted parts are in [design-app-executors.md](design-app-executors.md). Lean says nothing about GPU execution.
