Why the sandbox policy is a file, not flags

Every sandbox starts as flags, because flags are how you experiment. The move to a checked-in file is not tidying up. It changes who can review the boundary, when it can be refused, and whether the record means anything.

By Koukyosyumei Reading time 7 min Tags Design · Policy · Review
The argument. A flag describes one invocation and lives in somebody's shell history. A checked-in .h5i/env.toml describes an intent, sits in review next to the code it governs, gets hashed into every box's manifest, and can be refused as self-contradictory before anything runs. The last of those is the one flags structurally cannot do.

Nobody designs a sandbox as a config file first. You start with flags, because you are experimenting and flags are how you find out what the boundary needs to be. That is the correct order.

The interesting question is what changes when it stops being flags, and the answer is more than convenience.

A boundary is a claim, and claims belong in review

"This project's agents may reach registry.npmjs.org and nothing else" is a security decision about a repository. As a flag it is a decision one person made once at a shell prompt, invisible to everyone else, reproduced by whoever remembers.

As a checked-in file it is a diff. Someone widening the egress allowlist changes a line that shows up in review, next to the code that motivated it, with the reviewer who cares about that question already subscribed to the path. That is not a workflow nicety. It is the difference between a policy your team has agreed to and a policy your team has heard about.

A file can be refused; a flag can only be applied

This is the structural part, and it is why the lints matter more than the syntax.

A flag arrives one at a time at the moment of use, so a tool has to do something with each one. A file arrives whole, before anything runs, which means it can be checked for internal contradiction and rejected.

Two lints h5i applies, both of which reject a profile outright:

A net.egress allowlist below the supervised tier is refused. The process tier's network namespace is all-or-nothing; it can do deny or host and cannot honour a domain list. A flags-based tool would take the flag and either ignore it silently or apply an advisory version, and the manifest would then attest to an allowlist that never existed. Refusing is the only honest option, and it is only available because the whole policy was visible at once.

A denied path under a granted parent is refused. Landlock is allowlist-only and cannot subtract a child from a granted parent, so the deny would not be enforced. The fix is to narrow the grant, and h5i says so rather than accepting a rule it cannot hold.

Both of these are the same shape: reject a policy that says something the enforcement layer cannot do. That check needs the whole policy in hand.

Resolved, serialized, hashed, then used

The file is not what gets enforced. It is resolved against the host into policy.resolved.toml, which is hashed, and both are written before any state exists on disk.

That ordering means an unsatisfiable request fails with nothing to clean up, and it means every receipt record can carry the digest of what was actually in force. "What was enforced" stops being a matter of anyone's word, because the resolved file sits beside the log to be verified against the digest.

A flag cannot participate in that. There is nothing to hash and nothing to compare against later.

The file is not the whole story, and should not be

Being clear about what stays outside the file matters as much as what goes in.

Secret values never appear. A grant names a secret and how to source it (env:VAR, file:/abs/path, or a host-side command: extractor that is gated off by default because it runs arbitrary host code). The value never enters the policy, the digest, or any receipt. h5i box secrets dry-runs the resolution and reports a fingerprint.

Credentials are declared, not carried. A [[profile.X.auth]] grant names a host, a host-side credential environment variable, and the base-URL variable the client reads. The credential stays on the host and a proxy injects it.

Host-specific widening lives elsewhere. h5i box allow keeps a user-level egress allowlist under ~/.config/h5i/, outside every box-granted path, merged only into boxes whose profile already sets net.egress. A deny-all profile is never widened by it, and it refuses to run inside a box.

That last rule is the interesting one. It lets one person add a host their machine needs without editing a file the whole team reviews, and it cannot be used to turn a closed profile into an open one.

Where a file is worse than flags

  • Iterating. Editing a file to try one thing is slower than typing a flag, which is why --isolation, --profile and --image exist as overrides.
  • Machine-specific paths. A grant that is an absolute path differs between machines, which changes the policy digest for the same profile. Harmless when both files are written together at create time, and a real problem for a box carried between machines.
  • A file implies agreement it may not have. Checked in is not the same as reviewed. A profile nobody read is exactly as strong as a flag nobody saw.

FAQ

Why put the sandbox policy in a checked-in file?

So the boundary is reviewable next to the code it governs, versioned with it, and hashed into every box's manifest. A flag describes one invocation and lives in someone's shell history; a file arrives whole before anything runs, which is what lets it be refused as self-contradictory.

What does h5i refuse in a profile?

Two contradictions in particular. A net.egress allowlist below the supervised tier, because the process tier's network namespace is all-or-nothing and could not honour it. And a denied path sitting under a granted parent, because Landlock is allowlist-only and cannot subtract a child from a grant.

Do secret values go in the policy file?

No. A grant names a secret and how to source it, and the value never enters the policy, the digest, or any receipt. h5i box secrets dry-runs the resolution and reports a fingerprint rather than a value.

How do I add a host my machine needs without editing the shared file?

h5i box allow keeps a user-level egress allowlist under ~/.config/h5i/, outside every box-granted path. It is merged only into boxes whose profile already sets net.egress, so a deny-all profile is never widened, and it refuses to run inside a box.
