The agent sandbox with an output gate

A coding agent left alone is two bets at once: that it cannot reach anything it shouldn't, and that you can tell afterwards what it actually did. An h5i box makes those one object. The code, the agent, the toolchain, the dev server and a browser sit inside one boundary, and the only thing that comes out is a patch you have read.

By Koukyosyumei Reading time 11 min Tags Sandbox · Autonomy · Review
In one paragraph. An h5i box is a disposable, confined development environment for a coding agent. The code is copied in, the policy is resolved and hashed before any state exists on disk, and everything the agent starts (its shell, its package manager, its build, its tests, its dev server, its Chrome) is confined by the same boundary. The box has no write path to your machine. h5i box export is the only way out, and it produces three files: the patch, a report of what ran, and a receipt of every observed execution stamped with the policy digest that was in force.

A coding agent crossed a line that autocomplete never did: it runs unattended. It installs packages, edits files across a tree, starts servers and reaches the network, for minutes or hours, with whatever access your shell has, while you do something else. When you come back the question is no longer whether a line is correct. It is two harder questions at once. What could that process have touched that was not the task, your ~/.ssh, your tokens, some host it decided to call, if a poisoned dependency or a prompt-injected README nudged it off course? And can you tell, after the fact, what it did touch?

Blast radius and reviewability usually get handled by two tools that know nothing about each other. A git worktree isolates the checkout. A container isolates the process. Neither on its own gives you what autonomy actually needs: one unit you can hand an agent that confines it, records what it did, and then makes its output reach your machine only through a step a human takes. That unit is what h5i calls a box.

What is inside the boundary

The thing that makes a box different from a sandbox you wrap around one command is how much of the work it holds. Five parts, all inside:

  • The workspace. The code is copied in, along with everything it pulls. No host directory is mounted read-write into the agent's reach.
  • The agent. Claude Code or Codex, its child processes, its MCP servers, package managers, builds, tests and dev server all run under the same policy. A runaway agent stays in the box.
  • The credential and network broker. No SSH key, GitHub token, model API key, cloud credential or personal browser profile enters the box. A host-side proxy authenticates the calls the policy allows, and egress is an allowlist.
  • A browser. Chrome and a fresh profile live inside. The agent drives it through agent-browser; you can watch the same viewport with h5i box view and take the controls.
  • The output gate. A patch, a report and an execution receipt, after inspection. Nothing else leaves.

None of those is the point on its own. The point is that they share one boundary, so the dev server the agent starts is confined by the same rules as the shell that started it, and the browser that opens the app is confined by the same egress allowlist as the build that fetched its dependencies.

The loop, on one screen

~/my-project
$ h5i box .                          # a box from this repository, base pinned at HEAD
  created box fix-auth · isolation: supervised · profile: agent-claude

$ h5i box shell fix-auth             # this is where the agent runs
box$ claude                          # edit, build, test, start the dev server, drive the browser
box$ exit

$ h5i box diff fix-auth              # the change, against the pinned base
$ h5i box export fix-auth --out ./review
  wrote ./review/patch.diff, ./review/report.md, ./review/receipt.json

$ git apply --3way ./review/patch.diff  # after you have read report.md

h5i box . is the short form of h5i box create and takes the same flags. Where the code comes from decides the shape of the box, and the difference matters more than the syntax suggests.

Point it at this repository and you get a real git worktree on its own branch, sharing the object store, which is what makes h5i box apply able to land the work back locally. Point it at a URL, a pull request, or --new and you get a detached box: a repository of its own inside its directory, your repository neither read nor written after creation, and the inherited origin remote dropped so the box cannot reach a network handle nobody granted it. On a detached box apply and rebase refuse and point at export. External code should always arrive in that shape.

~/my-project
$ h5i box --pr 1234                  # a pull request; needs only git
$ h5i box https://github.com/o/r     # an external repository, detached
$ h5i box --new                      # empty; the agent builds from nothing

The policy is resolved before the box exists

A box's policy is resolved at creation, written to policy.resolved.toml, and hashed. All three happen before any state is created on disk, so a request the host cannot satisfy fails closed instead of leaving half a box behind. The base revision is frozen at the same moment and pinned immutably, which is why "what changed" is always measured against a fixed point rather than a branch that moved under you.

That digest is the part worth dwelling on. Every receipt the box produces records the digest of the policy that was actually in force when the command ran. A run and the rules that governed it cannot drift apart, and "what was enforced" stops being a matter of anybody's word.

Profiles come from .h5i/env.toml, or from four built-ins that need no file at all. default is fail-closed build and test confinement: system paths read-only, $WORK read-write, no network. agent is the agent-in-box surface scoped to whichever runtime H5I_AGENT names, and agent-claude and agent-codex pin one runtime each. browser is the agent profile plus headless Chrome and the agent-browser daemon.

Scoping a box to one runtime is not cosmetic. A Claude box that could read Codex's token would let a prompt-injected agent use the other runtime's credential against a host the allowlist permits, which is exactly the move the allowlist was supposed to stop.

Isolation is a tier, and the tier is honest

"Confined" means different things on different machines, so the policy names an isolation tier. auto, the default, picks the strongest tier the host can actually run. An explicit tier fails closed: ask for a level this host cannot provide and creation refuses rather than quietly giving you less.

TierWhat confines the codeEgress scoping
workspaceA separate worktree, no confinement. For code you already trust.none
processLandlock, seccomp and namespaces, with a supervisor and a private pid namespace.deny or host
supervisedEverything process has, plus a private netns, an nftables allowlist pinned to resolved IPs, DNS pinned by a hosts file, and a seccomp-notify gate on socket().L3/L4
containerRootless Podman on a portable image.L7 (CONNECT proxy)
microvmA guest with its own kernel, booted by microsandbox from the same OCI images.L3/L4, in the VM's netstack

Two drafts of the design got this backwards, so it is worth stating plainly: the container tier buys portability, not tighter network control. Its allowlist is a proxy, so it binds proxy-respecting tooling and nothing else. A program that opens a raw socket to a permitted IP walks straight through it. supervised enforces at L3/L4 and does not have that hole, and microvm turns its allowlist into default-deny plus one address rule per destination, evaluated by the guest's own network stack.

h5i box probe prints what this host can enforce, and it checks by running rather than by reading feature flags. On an AppArmor-restricted CI runner the Landlock and user-namespace bits are present and confined exec still does not work, so the probe executes a self-test before it lets a kernel tier be trusted. The full mechanism, allowlist by allowlist, is the design post.

The receipt is observation, not testimony

Confinement decides what the code can do. The receipt says what it did. Each box keeps one append-only JSONL log plus the raw payload of every record, and each record is generated from observation rather than from the agent's account of itself.

Two properties carry the weight. The log is sealed: the box's entire write window under its own directory is <box>/spool, and the receipt log and its payloads are siblings of that spool, outside every grant. The box stages a record and the host ingests it; there is no path from inside to a record the host has already written. And it is redacted at the boundary, with secrets scrubbed from the command and the payload before either is written, recorded by rule id rather than by value.

Every record carries the lane that observed it, so two very different kinds of evidence never blur into one:

LaneWho observed it
host-env-runh5i, host-side. Exits and resource usage from the supervisor's wait4, egress from the allowlist proxy's own log.
viewerh5i's viewer forward. The box supplies none of it.
tee-shimThe box's shell shim. Box-claimed.
inbox-captureStaged by the box. Box-claimed.

What h5i does not claim is as important. An agent can stage extra records, or stop writing them. Both are visible: a gap between host-observed exits and box-reported commands is itself a finding. That is the whole claim, and it stops there.

~/my-project
$ h5i box status fix-auth              # policy actually enforced, evidence, base drift
$ h5i box log fix-auth                 # the box's event log
$ h5i box inspect fix-auth --capture <id>  # one run's full record
$ h5i box capabilities fix-auth --json  # what this box actually got
$ h5i box compare fix-auth fix-auth-2   # two boxes side by side

There is also a screen for it. h5i ui draws the whole fleet: every box with its tier and status on the left, and on the right the policy that was enforced, the services it declares, its diffstat against the pinned base, and a flight recorder with one row per receipt across five lanes. Every route is a GET, so the console can watch boxes and never drive them.

Export is the only door

A box has no write access to anything outside itself, which means the interesting question is how work gets out. h5i box export is the answer, and it is deliberately a step a human takes.

FileWhat it is
patch.diffThe tree diff against the pinned base, path-validated: no symlink escapes, no nested .git, no agent-introduced gitlinks.
report.mdWhat ran, what the browser saw, who was at the controls, and the agent's own proposal.
receipt.jsonEvery observed execution, with the policy digest that was enforced.

Read report.md before you apply anything. Its ordering is an opinion about what a reviewer needs first: denied egress attempts at the top, because a box that tried to reach a host the policy refused is the single most interesting thing that can appear in a report; then every command with its lane and exit code; then what the page said back, meaning console errors, uncaught exceptions and failed requests that h5i collected itself rather than taking the agent's word for; then viewer sessions, including whether a human took the controls; and last, what the agent says it did.

Export refuses to overwrite a non-empty directory unless you pass --force, and secret redaction and size caps apply to all three files. Then you apply it wherever you want with git apply --3way. For the local case, where the box came from this repository and landing it here is exactly what you meant, h5i box apply still does that in one step.

Failure modes worth knowing before you hit them

  • The host cannot enforce your tier. An explicit --isolation fails closed and says why. Run h5i box probe first. The kernel tiers need a working user-namespace, Landlock and seccomp stack, and some CI and AppArmor setups do not allow one.
  • The base advanced under you. A long-lived box falls behind its parent branch. h5i box status reports the drift and h5i box rebase re-pins onto the current tip, refusing rather than producing a silently wrong base.
  • You expected the container tier's allowlist to be airtight. It is L7. Choose supervised or microvm when the boundary has to hold against a program that does not go through a proxy.
  • You expected containment to stop data leaving. It does not. The agent can put your private source in a model prompt, and no filesystem policy touches that. A self-hosted model or no model egress at all is the control for it, and h5i will not imply otherwise.
  • You expected a hardware boundary from a kernel tier. Podman and the kernel tiers share the host kernel. That is strong against a runaway agent and against careless dependency code, and it is not a claim against a targeted kernel exploit. microvm is the tier where the boundary is a hypervisor, and it needs msb, host virtualization, and a pre-pulled image.

One decision, at the end, with the evidence in front of you

The reason an agent is worth confining is the same reason its output is worth reviewing: you did not watch it work. A box makes those one object rather than two. The boundary that confined the work is the same boundary that produced the evidence and the same boundary you export from, and the patch you read is the patch that lands.

That is a narrower promise than "a sandbox" and a more useful one. It does not ask you to trust the agent and it does not ask you to babysit it either. It asks for one decision, at the end, with the receipt open, which is the decision you wanted to keep anyway.

FAQ

How is an h5i box different from running an agent in a git worktree?

A worktree isolates the checkout, not the process. The agent still has your filesystem, your network and your credentials, and its branch merges like any other. A box puts the code, the agent, its child processes, the build, the dev server and a browser inside one enforced boundary and gives that boundary a single exit: h5i box export, which writes a patch, a report and a receipt for a human to read.

Is the agent actually confined, or only isolated in a branch?

It depends on the tier your host can run. workspace is a worktree with no confinement. process and supervised use Landlock, seccomp and namespaces with a supervisor and a private pid namespace, and supervised adds a private netns with an nftables egress allowlist at L3/L4. container is rootless Podman with a proxy allowlist, and microvm boots a guest with its own kernel. h5i box probe reports what this host can enforce, and an explicit tier refuses rather than downgrading.

Why is export a separate human step?

Because the box has no write path to the host, and adding an automatic one would remove the property everything else rests on. Export is where the patch is path-validated against symlink escapes, a nested .git and agent-introduced gitlinks, where secrets are redacted, and where the report puts denied egress attempts first.

Can a box hold code from an untrusted pull request?

Yes, and that is the shape external code should always arrive in. h5i box --pr 1234 creates a detached box: its own repository, your repository neither read nor written after creation, and the inherited origin remote dropped. apply and rebase refuse there and point at export.

Does the box get my API keys?

No. The model API key stays on the host and a reverse proxy injects it into outbound requests from the box, scoped per runtime. Any other service works the same way, declared as an [[profile.X.auth]] grant naming a host, a host-side credential environment variable, and the base-URL variable the client reads. The per-box HOME state is a copy of your agent's config with credential-shaped entries stripped at any depth.
