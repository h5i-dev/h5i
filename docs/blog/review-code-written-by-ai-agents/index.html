Reviewing code an AI agent wrote

The instinct is to open the diff. On an agent's branch it is the third thing to open, and the agent's own summary is the last. Here is the order that puts the least trustworthy evidence at the bottom.

By Koukyosyumei Reading time 8 min Tags Review · Practice · Evidence
The reading order. Open report.md before patch.diff, and inside it read top to bottom, because it is deliberately sorted by how much you should trust each section. Refused comes first: destinations the egress allowlist blocked, seen host-side. Then observed: commands and exit codes from the supervisor. Then claimed: what the box's own shim reported. The diff is a separate reading job, and the agent's summary is the only section written by the thing under review.

A human's pull request comes with a person attached. You can ask them whether they ran the migration, and their answer is grounded in a memory of running it. That is the part of code review everything else rests on, and it quietly disappears when the author is a model that worked for forty minutes while you were in a meeting.

What is left is a diff and a summary, and the summary was written by the thing you are trying to evaluate. So the review has to be rebuilt around a different question: not "does the author say this is fine?" but "what did this actually do, according to something other than itself?"

Sort the evidence before you read it

An h5i box export gives you three files, and the useful move is to notice that they carry very different grades of evidence.

GradeWhere it comes fromHow much to trust it
RefusedThe egress allowlist proxy's own log, host-side. The box contributes nothing.As close to fact as this gets. A refusal happened outside the box's reach.
ObservedThe supervisor's wait4: exits, timings, resource usage. Lane host-env-run.High. h5i started the process and watched it end.
ClaimedThe box's shell shim, teeing commands into the spool. Lane tee-shim.Useful and not authoritative. This is the box's account of itself.
AssertedThe agent's proposal at the end of the report.Context only. Written by the subject.

Every record in the receipt is labelled with its lane precisely so you never have to guess which row you are in. A review that flattens these into "the log says" has thrown away the only thing that made the log worth having.

Read refused first, always

report.md leads with denied egress attempts, and that ordering is the single most opinionated thing in the export format.

A build that failed is a work item. A test that passed is expected. A box that tried to reach a host the policy refused is a question that has to be answered before anything else in the report matters, and burying it under a successful npm ci would be a design mistake. So it goes at the top, with a count.

What to do with a hit: find out what made the request. A dependency's postinstall script phoning a telemetry endpoint is boring and worth knowing. The same request from a branch that claims to fix a date-formatting bug is not boring at all. The receipt's ordering lets you walk backwards from the refusal to the command that was running when it happened.

One caveat worth internalising: an empty section is not always good news. At isolation=microvm the guest's network stack drops packets without reporting them, so a microvm receipt carries no egress summary at all. Stronger enforcement, thinner evidence. Check which tier produced the report before you read a blank section as a clean bill of health.

Then read what ran, looking for the gaps

The interesting thing in the command list is usually not any individual line. It is the relationship between the lanes.

h5i's honest claim about the receipt is narrow: an agent can stage extra records, or stop writing them, and both are visible. Visible means a discrepancy between host-observed exits and box-reported commands is itself a finding. If the supervisor saw a forty-second process and the shim reported nothing during it, that is worth a question. Not proof of anything, and worth a question.

The other pattern to look for is work that was never done. A report showing a build and no test run, under a summary that says the tests pass, is the cheapest catch in this entire workflow and it takes about four seconds.

Then read the diff, with the report in mind

Now the diff is useful, because you are reading it with context about what happened rather than as the whole story. Three things deserve disproportionate attention:

  • Anything the report says was edited but never exercised. A file that changed and never appeared in a command's blast radius is untested by construction.
  • Dependency and lockfile changes. The diff is a hyperlink to code nobody in the thread has read. Cross-reference against what the install step actually reached for.
  • Test changes that make a test easier. A weakened assertion and a fixed bug produce the same green run. The receipt cannot tell you which one you got.

The patch is path-validated at export against symlink escapes, a nested .git and agent-introduced gitlinks, so you can read it as a diff rather than as a potential filesystem trick. That is one class of worry off the list, and only that one.

Read the summary last, or not at all

The agent's proposal sits at the bottom of the report for the same reason a defendant's statement is not the first exhibit. It is useful for understanding intent, and intent is the thing you are least able to verify.

Reading it first is worse than not reading it, because a fluent summary primes you to interpret the evidence as confirming it. Read it after you have formed a view, and treat any place it disagrees with the report as the most interesting part of the review.

What this workflow does not give you

  • It does not tell you the change is correct. Everything above is about what happened, not about whether what happened was right.
  • It does not catch a payload that waits. Code that behaves inside a box and misbehaves in production is a known technique, and a clean report is evidence about one execution.
  • It does not make an unreviewed diff safe to merge. It reallocates your attention; it does not remove the need for it.

FAQ

What should I read first on an agent's pull request?

The denied egress section of report.md. It lists destinations the policy refused, observed host-side by the allowlist proxy rather than reported by anything inside the box, which makes it the highest-grade evidence in the export. Then what ran, then the diff, then the agent's own summary.

Why is the agent's summary at the bottom of the report?

Because it is the only section written by the thing under review. It is useful for understanding intent and it is a self-report, so reading it first primes you to read the evidence as confirming it. Read it after you have formed a view, and treat disagreements with the report as the most interesting part.

What is the difference between host-observed and box-claimed evidence?

Host-observed records come from outside the box: exits and resource usage from the supervisor's wait4, egress from the allowlist proxy's log. Box-claimed records come from the box's own shell shim. Every receipt record is labelled with its lane, so the two never blur, and a gap between them is itself a finding.

Does an empty denied-egress section mean nothing was attempted?

Not necessarily. At isolation=microvm the guest's network stack drops packets without reporting them, so a microvm receipt carries no egress summary at all. Check which tier produced the report before reading a blank section as a clean result.
