An audit you do not have to trust

Almost every agent tool logs. Very few produce evidence, and the gap between those two words is one design decision: whether the thing being described could have written the description.

By Koukyosyumei Reading time 9 min Tags Audit · Evidence · Design
The test. Point at any line in your agent's audit trail and ask one question: could the agent have written this? If yes, it is testimony. Testimony is useful and it is not an audit, because the case an audit exists for is the case where the subject is not cooperating. A workspace is auditable when its evidence is produced by something outside the workspace and stored somewhere the workspace has no write path to.

Every agent framework ships logging now. Sessions, tool calls, transcripts, timestamps, all of it structured and searchable. It looks like an audit trail, it is presented as an audit trail, and it is generated almost entirely by the process it describes.

That is fine for debugging, which is the use case it was built for. It is not fine for the use case people reach for it in, which is answering a question about work they did not watch.

Testimony and observation are different things

A record has a source, and the source determines what the record can be used for.

When an agent's SDK writes "ran npm test, exit 0" into a session log, that is the agent's account of itself. It is probably true. It is true in exactly the proportion of cases where you did not need an audit trail.

When a supervisor process calls wait4 on a child it started and records the exit status, that is an observation. The child had no involvement in producing it. The two records can contain identical text and be worth completely different amounts.

Most tooling flattens this distinction at write time, and once it is flattened no downstream analysis can recover it. That is why h5i makes the observing lane a required field on every receipt record: host-env-run and viewer are host-observed, tee-shim and inbox-capture are box-claimed, and the console labels every row so the grade travels with the event.

The second question: where does the record live?

Observation is necessary and not sufficient. A perfectly observed record written to a file the subject can edit is a perfectly observed record until someone edits it.

This is where most designs quietly fail, because the natural place to put a log is next to the work. h5i's answer is a filesystem-layout decision rather than a cryptographic one, and its plainness is the point:

A box's entire write window under its own directory is <box>/spool. The receipt log and the stored payloads are siblings of that spool, outside every grant. The box stages a record; the host ingests it.

There is no path from inside to a record the host has already written. Not because writes are signed or chained, but because the filesystem policy never granted the directory. A box that wanted to rewrite its history would first have to get out of the box, at which point the history is the least of the problems.

What "auditable" then means, concretely

Four properties, each of which is checkable rather than asserted:

PropertyHow it is achieved
Produced outside the subjectExits and resource usage from the supervisor's wait4; egress verdicts from the allowlist proxy's own log. The box supplies neither.
Stored outside the subject's reachThe receipt log is a sibling of the box's only writable directory, outside every grant in the resolved policy.
Bound to the rules that appliedEvery record carries the sha256 of the policy actually in force, so a run and its boundary cannot drift apart.
Honest about its own gapsBox-claimed records are labelled as such; a browser drain that could not reach a browser is recorded as unavailable rather than as a clean page.

The last property is the one people skip

An audit trail that cannot express its own uncertainty will eventually be read as more confident than it is, and the failure is always in the same direction.

Two concrete examples from the receipt format. A browser command with no browser to ask is recorded as unavailable, because nothing was looked at is a different claim from nothing was wrong and a reviewer has to be able to tell them apart. And when the per-record cap drops entries, truncated is set, so a flood of console errors is never silently rendered as a clean page.

The console does the same thing with colour. Grey means the evidence is weak, either because the tier was workspace and nothing was confined or because every record came from the in-box shim. A box that ran unconfined produces a clean-looking screen, since nothing was blocked because nothing was blocking, and without a grey state it would render identically to a box that passed through a real boundary with nothing to report.

What this design does not claim

Being precise here is not modesty, it is the difference between a claim you can rely on and one that fails silently when it matters.

  • The log is not complete. An agent can stage extra records or stop writing them. Both are visible, as a gap between host-observed exits and box-reported commands, and that gap being visible is the entire claim.
  • It is not tamper-proof against a host compromise. The record is protected from the box, not from someone with your machine.
  • It says nothing about correctness. A clean receipt and a subtle backdoor coexist comfortably.
  • It is not a chain of custody. There is no signing, no notarisation, no third party. It is a local file with a policy digest, and calling it more would be the exact overreach this post is about.

Apply the test to whatever you are using

You do not need h5i to run this check on your current setup. Open your agent's audit trail, pick a line that would matter in an incident, and ask the two questions: who produced this, and could the subject have edited it afterwards?

If the answers are "the agent" and "yes", you have a debugging log. That is a useful thing to have, and it is worth knowing which one you have before an incident rather than during.

FAQ

What makes a workspace auditable rather than just logged?

Two things. The evidence is produced by something outside the subject, such as a supervisor calling wait4 or an egress proxy writing its own log, and it is stored somewhere the subject has no write path to. A record the agent could have written is testimony, which is useful and is not an audit.

How does h5i stop a box editing its own audit log?

By filesystem layout rather than cryptography. The box's entire write window under its own directory is its spool, and the receipt log and payloads are siblings of that spool, outside every grant in the resolved policy. The box stages a record and the host ingests it.

Is the h5i receipt tamper-proof?

It is protected from the box, not from someone with your machine. There is no signing, no notarisation and no third party. It is a local append-only file with a policy digest on every record, and describing it as a chain of custody would be an overreach.

Can an agent simply stop writing records?

Yes, and so can it write extra ones. Both are visible as a gap between host-observed exits and box-reported commands, and that visibility is the whole claim. It does not extend to the log being complete.
