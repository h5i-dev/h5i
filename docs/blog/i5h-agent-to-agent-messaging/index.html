Watching a box's browser without giving it a port

A box's whole point is that it is not reachable. Then you want to watch the page inside it, which sounds like it requires punching a hole, and does not.

By Koukyosyumei Reading time 7 min Tags Design · Viewer · Security
How it works. The box's stream port is never published. It stays inside the box's private network namespace. h5i enters that namespace by pid, connects from inside, and hands the socket back out. The forward then binds loopback only, on a port h5i chose, and every connection carries a per-box token minted at creation and never written anywhere the box can read. The terminal viewer, --term, binds nothing at all.

The obvious implementation is to publish the port. The box runs a stream on 7331, you map it to the host, you open a browser. Ten minutes of work and it functions.

It also means anything on your machine can now reach a listener inside a box you built specifically because you did not trust what was in it. On macOS, where the box shares the host's loopback, that includes any local process. The convenience and the boundary are the same hole.

Reach in instead of letting out

h5i inverts the direction. The stream port stays inside the box's private network namespace, unpublished and unreachable. To watch it, h5i enters the namespace by pid, connects from inside, and hands the resulting socket back out to the host process.

The distinction is the whole design. Publishing a port makes the box reachable by anything. Entering a namespace makes it reachable by the one process that had the authority to enter, which is h5i, which is the thing that created the boundary in the first place.

What is then exposed is h5i's own forward, on h5i's terms:

  • It binds loopback only, on a port h5i chose.
  • Every connection carries a per-box token, minted at creation and never written anywhere the box can read. The box cannot mint a URL to itself.
  • Cross-origin WebSocket handshakes are refused, so a page you have open in another tab cannot reach a running box.
  • Frames flow out always; input flows in only for the control-lock holder. Watching and driving are separate authorities.

The terminal viewer binds nothing

h5i box view <name> --term draws the page in the terminal you are already in, next to the agent. It also works over SSH, which the browser viewer does not without forwarding a port.

Its security story is shorter than the browser viewer's, and the shortness is the feature. There is no port, no token, and no page. The viewer runs inside the command you just typed, enters the box the same way the forward does, and holds the socket itself. Nothing else on the host can connect to it, so there is nothing to authenticate.

It needs a terminal that speaks the Kitty graphics protocol. kitty, Ghostty, WezTerm and Konsole all do. When yours does not, h5i says so and points at the browser viewer rather than filling your screen with base64.

The direction people forget

Drawing a page in a terminal has a hazard that has nothing to do with networking, and it is worth stating because it generalises well beyond h5i.

A terminal's output is not text. An escape sequence can rewrite your clipboard, retitle the window, or ask the graphics protocol to read a file. A viewer that piped bytes from inside the box to your terminal would have handed the box a second control channel, pointed at you.

So the box never writes to your terminal. It supplies compressed pixels inside a WebSocket message, and every escape sequence you receive is generated by h5i. There is no untrusted byte stream to sanitize, because there is no untrusted byte stream.

Row one, and truncating from the left

The top row belongs to h5i. A page cannot draw on it or be clicked through it. It carries the box, the mode, who holds the control lock, the page's origin, the egress policy, and a count of console errors.

The origin is the field that never gets shortened at the expense of the truth. A long URL loses its path, and a host too long for the row is cut from the left, because shortening bank.example.evil.test from the right is the trick itself.

That is a two-line implementation detail and a real attack, and it is the kind of thing a status bar gets wrong by default.

Two modes, three keys

KeyDoes
iTake the control lock and start driving the page
Ctrl-]Hand control back and return to watching
qLeave

Watching is read-only and leaves the mouse to your terminal, so selection and scrollback still work. Driving takes the lock, because in a terminal viewer there is no second window to run h5i browser take in. Both transfers are recorded in the receipt, under the same lane the browser viewer uses.

Two limits, stated rather than discovered

  • Holding a key down does not work. A terminal reports key presses and not releases, so h5i sends a press and a release together. Typing works exactly; holding does not.
  • Clicks land at the resolution of a terminal cell. Fine for a form, coarse for a dense canvas.
  • The box has to be running, meaning a live h5i box shell or h5i box run, and its browser has to be streaming, which is agent-browser stream enable inside the box.

FAQ

How does h5i show a box's browser without publishing a port?

By reaching in rather than letting out. The stream port stays inside the box's private network namespace, and h5i enters that namespace by pid, connects from inside, and hands the socket back out. What is exposed is h5i's own loopback-only forward, not the box.

What stops another page on my machine connecting to a running box?

Three things. The forward binds loopback only on a port h5i chose, every connection carries a per-box token minted at creation and never written anywhere the box can read, and cross-origin WebSocket handshakes are refused outright.

Why does the terminal viewer need no authentication?

Because it binds nothing. There is no port, no token and no page: the viewer runs inside the command you typed, enters the box the same way the forward does, and holds the socket itself. Nothing else on the host can connect to it, so there is nothing to authenticate.

How does the terminal viewer avoid escape-sequence attacks?

The box never writes to your terminal. It supplies compressed pixels inside a WebSocket message and every escape sequence you receive is generated by h5i, so there is no untrusted byte stream to sanitize. The status row is h5i's and cannot be drawn on, and an over-long host is truncated from the left.

Which terminals support the graphics view?

Any terminal that speaks the Kitty graphics protocol, which includes kitty, Ghostty, WezTerm and Konsole. When yours does not, h5i says so and points you at the browser viewer rather than filling the screen with base64.
