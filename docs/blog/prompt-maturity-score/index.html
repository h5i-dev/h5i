Teaching an agent to use its own box

Documentation drift is annoying for humans and actively harmful for agents, because an agent will confidently run the command your docs describe and then report that your tool is broken. So the skill lives inside the binary.

By Koukyosyumei Reading time 6 min Tags Design · Agents · Documentation
The mechanism. skills/h5i/ is embedded in the binary at build time, so the skill cannot document flags the installed binary does not have. h5i skill install writes it out to ~/.claude/skills/h5i or the Codex equivalent, h5i skill show prints a page, and h5i skill path says where an install would write. This is also how the in-box agent gets it: nothing is baked into an image and nothing is copied from host to box.

Give an agent a tool and it will read whatever documentation it can find, then act on it without the hesitation a human would have. That difference in confidence is what makes documentation drift a different category of problem for agents than for people.

A human reading a stale flag tries it, sees an error, and goes looking for the real answer. An agent tries it, sees an error, tries three variations, and then tells you the tool is broken. You lose the run and get a bug report about a flag that was removed two releases ago.

Embed it, so it cannot be wrong about itself

The fix is structural rather than procedural. skills/h5i/ is compiled into the binary at build time. There is no version of h5i that can hand out a skill describing a different version of h5i, because the skill and the code were built together from the same tree.

~/my-project
$ h5i skill install         # write it into ~/.claude/skills/h5i (or ~/.codex)
$ h5i skill show            # print SKILL.md
$ h5i skill path            # where an install would write

$ npx skills add h5i-dev/h5i  # same bytes, if you do not have the binary yet

The same property covers the man page and the manual, which are generated from the CLI definition and diffed in CI, so a new flag that nobody documented fails the build rather than shipping.

The in-box agent gets it the same way

This is where the design earns its keep, and it is a small detail with a large consequence.

The obvious way to give an in-box agent the skill is to bake it into the container image, or to copy it from the host at box creation. Both create a second copy with its own lifetime, which is to say both reintroduce drift by a different route: an image built last month carries last month's skill.

Instead the in-box agent runs h5i skill install against the binary that is already there. One source, one lifetime, and no host-to-box copy at all, which also keeps the transfer surface at zero.

How an agent knows it is inside

An agent behaves differently in a box, so it needs to be able to tell. h5i sets a handful of environment variables inside, and the presence of one of them is the signal:

VariableMeaning
H5I_ENV_IDThe box's id. Its presence is how the skill decides you are inside.
H5I_ENV_POLICY_DIGESTThe digest of the policy actually enforced.
H5I_ENV_CAPTURE_SPOOLThe box's only write window for staging receipt records.

These are set by h5i and are not for you to set yourself. Read them to detect a box; setting one by hand tells the skill a lie about where it is running.

What the agent does with that knowledge is mostly about not wasting time. Inside a box there is no point asking permission to run a build, because the boundary already decided what a build can do. There is no point trying to reach a host outside the allowlist. And there is no point attempting to write outside $WORK, which will fail in a way that reads like a filesystem problem and is a policy one.

What the skill deliberately does not do

It documents h5i and stops there. Driving the browser is agent-browser's job, and its own --help is the verb table; wrapping forty automation verbs in a second layer of documentation would guarantee exactly the drift this whole design exists to prevent.

It also does not try to make the agent behave well. A skill is context, not enforcement. An agent that ignores every word of it is contained by the policy just the same, and that ordering matters: the containment does not depend on the agent having read anything.

The general version

If you ship a tool that agents will use, the thing worth stealing here is not the specific command. It is the idea that the documentation an agent reads should be an artefact of the build, not a file that travels separately and rots at its own pace.

Humans tolerate stale docs because they hedge. Agents do not hedge, so the cost of drift lands differently, and it is worth spending a build step to remove it.

FAQ

How do I give Claude Code or Codex the h5i skill?

Run h5i skill install, which writes it into ~/.claude/skills/h5i or the Codex equivalent. npx skills add h5i-dev/h5i installs the same bytes if you do not have the binary yet. h5i skill path prints where an install would write.

Why is the skill embedded in the binary?

So it cannot document flags the installed binary does not have. An agent acts on documentation without the hesitation a human would have, so a stale flag costs you a run and produces a bug report about something removed two releases ago. Embedding makes the skill and the code one artefact.

How does an agent know it is running inside a box?

By the presence of H5I_ENV_ID. h5i also sets H5I_ENV_POLICY_DIGEST for the policy actually enforced and H5I_ENV_CAPTURE_SPOOL for the box's only write window. These are set by h5i; setting one by hand tells the skill a lie about where it is running.

How does the in-box agent get the skill?

It runs h5i skill install against the binary that is already in the box. Nothing is baked into an image and nothing is copied from host to box, so there is no second copy with its own lifetime and no host-to-box transfer surface.

Does the skill make the agent behave safely?

No, and it is not meant to. A skill is context, not enforcement. An agent that ignores every word of it is contained by the policy just the same, and that ordering is deliberate: containment does not depend on the agent having read anything.
