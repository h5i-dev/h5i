Pinning what was actually enforced

Three small orderings decide whether the sentence 'this ran under that policy' is a verifiable fact or somebody's recollection. All three are about doing something before something else.

By Koukyosyumei Reading time 7 min Tags Design · Policy · Determinism
Three orderings. The policy is resolved, serialized to policy.resolved.toml and hashed before any state exists on disk, so an unsatisfiable request fails closed rather than leaving half a box behind. The base revision is frozen at creation and pinned immutably, so "what changed" is measured against a fixed point. And the digest is stamped on every receipt record rather than once per box, so a run and the rules that governed it cannot drift apart.

"This ran under that policy" is a sentence tools say constantly, and it is almost always a claim about the present tense applied to the past. The config file says X now. The run happened then. The gap between those is where every confusing incident lives.

Closing it takes three decisions, and all three are about ordering rather than about mechanism.

One: resolve and hash before creating anything

The obvious implementation creates the box, then applies the policy. It is obvious because it matches how you would do it by hand, and it has a failure mode that gets worse the more it happens.

When the policy turns out to be unsatisfiable, and it will, because a profile asking for isolation=microvm on a host with no virtualization is a normal Tuesday, you are left with a half-created box. Some state on disk, some not. The next command has to decide what that means, and every subsequent bug report starts with "well, it depends what happened last time."

So h5i resolves the policy, serializes it to policy.resolved.toml, and hashes it, before any state is created. An unsatisfiable request fails closed with nothing to clean up. There is no partial state to reason about, because the step that could fail happens while there is nothing to leave behind.

Resolution also fails closed on an explicit tier rather than downgrading. That is the same principle at a different scale: a sandbox that silently gives you less than you asked for produces a record attesting to a boundary the run never had, which is worse than no sandbox at all.

Two: freeze the base at creation

A box pins its base revision immutably at creation. Nothing re-resolves it later, which sounds like a small convenience and is actually what makes "what changed" a well-defined question.

Measure a diff against a moving branch and the answer changes underneath you. Your colleague merges something, and the box's diff silently grows to include their work, and the patch you reviewed is not the patch you apply. Pin it, and h5i box diff means one thing forever.

The cost is drift, and drift is handled explicitly rather than hidden. h5i box status reports how far the box has fallen behind its parent, and h5i box rebase re-pins onto the current tip or refuses if that would conflict. The refusal is the feature: producing a silently wrong base would be the one outcome worse than making you deal with it.

Three: stamp the digest on every record

This is the one that looks redundant and is not.

Storing the policy digest once, in the box's manifest, describes the box. Storing it on every receipt record describes each execution. Those differ whenever a box's configuration changes across its life, and a record carrying no digest is a claim about an execution with the rules detached from it.

With the digest inline, any record can be read on its own and still answers "under what rules?" And policy.resolved.toml sits beside the log to be verified against it, so the question is settled by comparison rather than by trust.

~/my-project
$ h5i box status fix-auth
  base      a3f9c2b  (pinned at create; parent is 4 commits ahead)
  isolation supervised
  policy    sha256:9f2c…  · policy.resolved.toml verified
  limits    mem 4G  procs 256  wall 30m

Enforced, not requested

One more distinction that falls out of all this. h5i box status reports the policy actually enforced, which is not always the policy written down.

On macOS at the kernel tiers, mem and procs cannot be held. Darwin has no cgroups, does not enforce RLIMIT_AS against the mmap'd heap every modern runtime uses, and scopes RLIMIT_NPROC to the whole user rather than to one box, so applying it would cap your machine instead of the box. h5i declines to apply a limit it cannot hold, and marks the value with * with an explanation underneath rather than listing it as enforced.

A status screen that showed the requested policy would be showing you a wish. The whole point of hashing the resolved policy is that there is a difference, and that you can see it.

What this is not

  • Not reproducibility. Pinning the base and the policy does not make the run repeatable. Package registries move, clocks differ, and the model is not deterministic.
  • Not a signature. The digest is a hash sitting next to the file it hashes. It detects drift; it does not prove authorship.
  • Not a guarantee the policy was wise. A profile that grants a credential and allows broad egress is faithfully recorded and still wrong.

FAQ

Why does h5i hash the policy before creating the box?

So an unsatisfiable request fails closed with nothing to clean up. Creating first and applying the policy second leaves a half-created box whenever resolution fails, and every later command then has to decide what that partial state means.

Why is the base revision pinned immutably?

Because a diff measured against a moving branch changes underneath you: a colleague's merge silently grows the box's diff, and the patch you reviewed is not the patch you apply. Pinning makes what changed a well-defined question. Drift is surfaced by status and handled by rebase, which refuses rather than producing a silently wrong base.

Why is the policy digest on every record instead of once per box?

Because the manifest describes the box and a record describes an execution, and those differ whenever configuration changes across a box's life. A record with no digest is a claim about an execution with its rules detached, so it cannot be read on its own.

Does pinning make a run reproducible?

No. Pinning the base revision and hashing the policy record what applied; they do not make the run repeatable. Package registries move, clocks differ, and the model is not deterministic. The claim is about knowing what happened, not about repeating it.
