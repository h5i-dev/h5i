How to track what Claude Code actually ran

Recording prompts feels like the obvious thing to log, and it is close to the least useful. The prompt is one sentence upstream of a hundred model decisions. The commands are the part with consequences.

By Koukyosyumei Reading time 7 min Tags How-to · Observability · Receipts
The short answer. Run the agent inside a box and the tracking is automatic: h5i box log <name> for the event log, h5i box status <name> for the policy actually enforced plus base drift, h5i box inspect <name> --capture <id> for one run's full record, and h5i box export for the whole thing as three files. Nothing needs the agent's cooperation, because none of it is a hook.

The usual approach to agent observability is to hook the tool loop: capture the prompt on submit, capture the edit on tool use, capture the transcript on stop. It produces a lot of data, and the data has two problems that are easy to miss while you are enjoying the volume.

It is configuration, so whoever can edit the config decides whether it happens. And it is upstream of the interesting part: a prompt is a sentence, a hundred model decisions happen after it, and what you actually wanted to know is what came out the other end and touched something.

Track execution instead

Inside an h5i box, two mechanisms watch, and neither is a hook the agent can turn off.

The supervisor watches from the host. Exits and resource usage come from wait4 on the process h5i started; denied egress comes from the allowlist proxy's own log. The box contributes nothing to either, and these records carry the host-env-run lane.

A shell shim watches from inside. The box's shell tees each top-level, non-interactive command into the box's spool, so an open-ended session leaves a record without the agent agreeing to anything. These carry the tee-shim lane, and they are the box's own account of itself, which is why they are labelled differently.

The four commands

~/my-project
$ h5i box log fix-auth                  # the box's event log
$ h5i box status fix-auth               # policy enforced, evidence, base drift
$ h5i box inspect fix-auth --capture <id>  # one run, in full
$ h5i box diff fix-auth                 # the change against the pinned base

status is the one worth running first and the one people skip. It reports the policy that was actually enforced, not the one requested, which matters because resource limits are not uniformly enforceable. On macOS at the kernel tiers, mem and procs cannot be held, so h5i declines to apply them and marks them with * rather than listing them as enforced. A tool that showed you the requested policy would be showing you a wish.

It also reports base drift. A long-lived box falls behind its parent branch, and h5i box rebase re-pins onto the current tip or refuses rather than producing a silently wrong base.

Getting it out

~/my-project
$ h5i box export fix-auth --out ./review
  wrote ./review/patch.diff, ./review/report.md, ./review/receipt.json

receipt.json is the machine-readable form: every observed execution with the policy digest that was in force. report.md is the same material sorted for a human, leading with denied egress attempts. Secret redaction and size caps apply to both, and the redaction is recorded by rule id rather than by value, so a reviewer can see that a secret was involved without seeing it.

Why the log cannot be edited from inside

This is the property that makes the record worth keeping, and it is a filesystem-layout decision rather than a clever one.

A box's entire write window under its own directory is <box>/spool. The receipt log and its stored payloads are siblings of that spool, outside every grant the policy hands out. The box stages a record; the host ingests it. There is no path from inside to a record the host has already written, so the log is append-only in the strong sense rather than by convention.

What is honestly not covered

  • An agent can stage extra records, or stop writing them. Both are visible as a gap against host-observed exits, and that is the entire claim. It does not extend to "the log is complete".
  • Interactive sessions are not recorded line by line. The shim deliberately skips a TTY session, so an interactive shell shows up as one host-observed process rather than as its contents.
  • A microvm receipt has no egress summary. The guest's netstack drops packets without reporting them. Stronger enforcement, less to read.
  • None of this records intent. If you want to know why, that is still the commit message's job.

FAQ

How do I see what commands an agent ran?

Run it inside a box. h5i box log <name> shows the event log, h5i box inspect <name> --capture <id> shows one run's full record, and h5i box export writes the whole receipt out as JSON alongside a human-readable report. Nothing needs the agent to cooperate.

Why not just log the prompts?

Because a prompt is one sentence upstream of a hundred model decisions, and it tells you almost nothing about what happened afterwards. Prompt logging is also configuration, so whoever can edit the config decides whether it happens. The commands are the part with consequences.

Can the agent delete its own log entries?

No. The box's write window under its own directory is exactly its spool, and the receipt log and payloads are siblings of that spool, outside every grant. The box stages a record and the host ingests it, so there is no path from inside to a record the host has already written.

Why does h5i box status mark some limits with an asterisk?

Because it reports the policy actually enforced rather than the one requested. On macOS at the kernel tiers, memory and process-count limits cannot be held, since Darwin has no cgroups and scopes RLIMIT_NPROC to the whole user, so h5i declines to apply them and marks them rather than claiming enforcement it does not have.
