Who is driving the browser?

Put an agent and a human in front of the same page and you have invented a concurrency problem with a pointer. h5i has four verbs for it and three rules, and the third rule is the interesting one.

By Koukyosyumei Reading time 6 min Tags Design · Browser · Handoff
The four verbs. h5i browser status says who holds control and whether the agent's page references are stale. h5i browser take gives a human the pointer. h5i browser release hands it back. h5i browser url prints the viewer URL with its token. Driving the browser itself is agent-browser's job, run inside the box. What h5i owns is arbitration, because nothing upstream does it.

The browser in a box exists so an agent can actually check its work: open the app, read the accessibility tree, click, fill, screenshot, notice the console error it just caused. That is the loop that makes autonomous front-end work possible at all.

Then a human watches it through h5i box view, sees the agent about to do something wrong, and reaches for the mouse. Now two things want the pointer, and somebody has to have decided in advance what happens.

Rule one: the agent holds control by default

A box exists to let an agent work. Making it request the pointer before every click would be ceremony around the normal case, and the normal case is that nobody is watching.

So control starts with the agent and stays there until somebody takes it.

Rule two: a human takes control, never asks for it

This is the rule that a naive design gets backwards, usually by implementing a request-grant handshake because that is what you would build between two programs.

But the two parties are not symmetric. Someone reaching for the viewer wants the pointer now, generally because something is going wrong. The agent is a program, and a program can wait. Asking a busy agent for permission to intervene inverts the priority exactly.

So h5i browser take is immediate. The agent's mutating verbs are then refused with a typed message rather than fighting for the pointer, and its read-only verbs keep working, because watching never collides with anything.

That last detail matters more than it looks. An agent that loses control can still snapshot and observe, so it can tell that the page changed and describe what it now sees, rather than going blind and reporting an error.

Rule three: handing control back invalidates what the agent knew

Here is the one that is easy to miss.

agent-browser works by taking a snapshot of the accessibility tree and handing back references like @e2 and @e3. The agent then acts on those references: click @e2, fill @e3 "test@example.com".

While a human held the pointer, the page moved. They navigated, submitted a form, dismissed a modal. Every @ref from the agent's last snapshot may now point somewhere else entirely, and the agent has no way to know that from inside its own model of the page.

So releasing control marks those references stale. The agent must re-snapshot before acting, and acting first is refused rather than mis-clicked.

A refusal is a recoverable event that the agent can reason about. A click on the wrong element is a silent wrong action on a page a human was just using, which is the worst outcome available and the one an implementation gets by default if nobody thinks about it. h5i browser status reports the staleness, so it is inspectable rather than implicit.

What h5i deliberately does not do

Four verbs is a suspiciously small surface, and it is a decision.

Driving the browser is agent-browser's job, and its --help is the verb table. Wrapping forty automation verbs behind a second CLI would buy nothing and guarantee drift as upstream changes. h5i owns the one thing nothing upstream owns: deciding who is allowed to act.

Both sides of every transfer land in the receipt, under the viewer lane, so the export can say whether a human took the controls during a run. That turns out to be one of the more useful lines in a review of agent work.

The residual worth knowing

  • The viewport is not a desktop. The screencast shows the page. Native dialogs, browser chrome and anything outside the tab are invisible to both of you.
  • Chrome runs with its own sandbox off. On Linux h5i's seccomp deny-list blocks the namespace syscalls Chrome's sandbox needs. The box is the boundary; Chrome's own is not available inside it, which is one layer fewer than a browser on your host has.
  • AI chat is refused inside the box. agent-browser chat sends page content to an external gateway, which inside a box is an exfiltration path with a friendly name. The gateway credential is never injected, and its absence is the mechanism.

FAQ

Who controls the browser in an h5i box by default?

The agent. A box exists to let an agent work, so making it request the pointer before every click would be ceremony around the normal case. Control stays with the agent until a human runs h5i browser take.

Why does a human take control rather than request it?

Because the two parties are not symmetric. Someone reaching for the viewer wants the pointer now, usually because something is going wrong, and an agent is a program that can wait. Asking a busy agent for permission to intervene inverts the priority.

What happens to the agent's page references when control is handed back?

They are marked stale. While the human held the pointer the page moved, so every @ref from the agent's last snapshot may now point somewhere else. The agent must re-snapshot before acting, and acting first is refused rather than mis-clicked, because a refusal is recoverable and a wrong click is not.

Why does h5i only have four browser verbs?

Because driving the browser is agent-browser's job and its own help is the verb table. Wrapping forty automation verbs behind a second CLI would buy nothing and guarantee drift. h5i owns the one thing nothing upstream owns: arbitration between the agent and a human.
