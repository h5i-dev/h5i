Triaging a fleet of agent boxes

Reading one export carefully is a solved problem. Deciding which of thirty to read carefully is the actual job, and the obvious solution, a risk score, is the one that quietly stops working the week after you ship it.

By Koukyosyumei Reading time 8 min Tags Audit · Triage · Honesty
The position. h5i ui draws every box on one screen with a flight recorder across five lanes: filesystem, network, process, resources and page. It counts receipts. It does not score them. Red makes exactly one claim, that the egress allowlist refused a destination and the proxy observed it. Amber means look at this. Grey means the evidence is weak. Nothing on the screen is a number you can rank by, and that is a decision rather than an omission.

The first agent branch gets a careful review. So does the second. By the time a team is running boxes in parallel across a backlog, careful review of everything has stopped being a plan and started being a thing people say in retrospectives.

Which makes the real question one of allocation. You have a fixed amount of attention and a growing number of exports. What signal decides where it goes?

The obvious answer and why it fails

Every version of this problem invites the same solution: compute a risk score per box, sort descending, review from the top. It is easy to build, it demos well, and it fails in a specific and predictable way.

A score is a compression of several incomparable signals into one number, using weights somebody guessed. Nobody can audit the weights, so nobody trusts a surprising result, so a high score becomes something to explain away rather than something to investigate. Meanwhile a low score gets read as an all-clear, which is the worst possible outcome, because the score never had the information to make that claim.

h5i shipped a scoring module once. It was deleted, and it stayed deleted.

Counting instead of scoring

What replaced it is arithmetic over receipts. The console groups each box's records into five lanes and shows one row per receipt:

LaneWhat lands there
FSFilesystem activity within the policy's grants.
NETEgress, including every destination the allowlist refused.
PROCCommands, their exit codes, and the lane that observed each one.
RESResource usage against the profile's limits, including a wall-clock kill.
PAGEWhat the in-box browser reported: console errors, uncaught exceptions, failed requests.

A count is auditable in a way a score is not. Seven refused connections means seven refused connections, and clicking the row shows the rendered receipt, the same text h5i box inspect prints. There is no weighting step to disagree with, because there is no weighting step.

The colours are narrower than they look

The one place a UI could smuggle a judgement back in is the colour palette, so the palette is constrained on purpose.

Red makes exactly one claim about the boundary: the egress allowlist refused a destination, host-observed by the proxy. Nothing else is ever red. Not a failing test, not a crash, not a suspicious-looking command.

Amber means something is worth looking at and says nothing about containment: a run exited non-zero, the wall-clock limit killed one, or the in-box browser reported errors. Useful, and not a security signal.

Grey is the one people misread, and it is the most interesting. Grey means the evidence is weak: either the tier was workspace and nothing was confined, or every receipt came from the in-box shim and so is the box's own account of itself. Grey is not "fine". It is "you cannot tell from here", which is a different and more useful thing for a dashboard to be able to say.

Each run row is separately labelled host-observed or box-claimed for the same reason.

The console cannot do anything

Every route in h5i ui is a GET. There is no button that runs a command, applies a patch, or removes a box. shell, run, export, propose, apply and rm stay in the CLI, where a human types them.

That is a smaller product and a much smaller attack surface. A read-only server has no mutating surface to guard and cannot be turned into a remote control for somebody's boxes. It binds 127.0.0.1 and nothing else, the URL carries a token minted for the session and kept in memory so no box can read it, and requests from another origin are refused outright.

A triage order that survives contact

With counts rather than a score, the ranking is something you do yourself, which means you can state it and change it. A reasonable default:

  1. Any red. A refused destination is the only thing on the screen making a claim about the boundary. Investigate all of them, every time.
  2. Grey on an untrusted source. A box holding external code that produced only box-claimed evidence is the combination where you know least about the thing you trust least.
  3. A gap between lanes. More commands reported than exits observed, or a long host-observed process with nothing claimed during it.
  4. Amber with a browser. Console errors on a changed user-facing flow are cheap to check and often real.
  5. Everything else, by diff size, which is the weakest signal in the list and is fine once the four above are clear.

What this does not give you

  • It is not a security verdict. Counting boundary events tells you where to look. It does not tell you whether what you find is malicious, careless, or entirely normal.
  • A quiet box is not a safe change. The most dangerous diff in a release can come out of a box that did nothing unusual at all.
  • It does not scale to inattention. Triage reallocates review; it does not remove it. A team that reads nothing gets no benefit from a better order.

FAQ

Why does h5i's console not show a risk score?

Because a score compresses incomparable signals using weights nobody can audit, which makes a high score something to explain away and a low score an all-clear the number never had the information to give. h5i shipped a scoring module once and deleted it. The console counts receipts instead, and a count is checkable.

What do the colours in the h5i console mean?

Red makes exactly one claim: the egress allowlist refused a destination, observed host-side by the proxy. Amber means something to look at, such as a non-zero exit, a wall-clock kill, or browser errors, and says nothing about containment. Grey means the evidence is weak, either because the tier was workspace or because every receipt came from the in-box shim.

Can the console run commands on a box?

No. Every route is a GET. Shell, run, export, propose, apply and remove all stay in the CLI, where a human types them, so there is no mutating surface to guard and no way to turn the console into a remote control for someone's boxes.

What are the five lanes?

Filesystem, network, process, resources and page. Each receipt lands in one, and each row is separately labelled host-observed or box-claimed so the grade of the evidence stays visible next to the event.
