Making boxes start in seconds, not minutes

A disposable environment is only disposable if creating one is cheap, and cold dependency install is what makes it expensive. The cache that fixes it has three rules, and each one exists because the obvious version is subtly wrong.

By Koukyosyumei Reading time 7 min Tags Performance · Caching · Design
Three rules. One cache per project and ecosystem, keyed by a digest of that ecosystem's lockfiles; a cache whose key no longer matches is listed as stale and never handed to a box. Mounted read-only into an agent box, which costs nothing because every package manager falls back to fetching what it cannot find. Written only by h5i box cache refresh, which runs the install step alone, with egress narrowed to the registry hosts and no agent inside.

The pitch for disposable environments assumes creating one is cheap. If a fresh box costs four minutes of npm ci, people stop making fresh boxes, and the property that made the design safe quietly stops being used.

So warm caches are in scope. The interesting part is not that they exist. It is that a shared mutable cache between boxes would undo most of the isolation, and each of the three rules below is what stops it.

Rule one: keyed by the lockfile, and stale means unused

~/my-project
$ h5i box cache ls          # caches for this project, and whether they are stale
$ h5i box cache mounts      # exactly what a box would get
$ h5i box cache refresh npm  # populate one
$ h5i box cache rm npm

One cache per project and ecosystem, keyed by a digest of that ecosystem's lockfiles. When the lockfiles change, the key no longer matches, and the cache is listed as stale and never handed to a box.

Not "refreshed automatically", not "used with a warning". Unused. Packages resolved for a different dependency set are a silent, hard-to-explain wrong answer, the kind that produces a build that works on one machine and fails on another for reasons nobody can reconstruct. A slower box is a much better outcome than a mystery.

Rule two: read-only, which costs nothing

The cache is mounted read-only into an agent box. That sounds like it should break the package manager, and it does not, for a reason worth stating because it makes the whole design cheap: every package manager falls back to fetching what it cannot find.

So a read-only cache is a pure accelerator. On a hit it saves the download; on a miss the tool does what it would have done anyway. There is no correctness cost to pay for the isolation.

What it buys is the important half. A writable shared cache is a mutable surface two boxes can both reach, which means one box can plant something the next one picks up. That is a cross-contamination channel between environments whose entire point is not having one, and it would be reintroduced purely to save a second write.

The general rule underneath: no mutable surface is ever shared between an agent box and anything else.

Rule three: written only by a box with no agent in it

If agent boxes cannot write the cache, something has to. That something is h5i box cache refresh, and it is deliberately not a normal box.

It runs the install step alone, with egress narrowed to the registry hosts and nothing else, and with no agent inside. The thing that populates a shared artefact is the most constrained process in the system, which is the correct way round and the opposite of how these things usually evolve.

It also refuses rather than guesses. refresh needs a project-declared profile whose egress is the registry hosts and nothing more, and when there is not one it prints that profile ready to paste instead of creating a box whose fetch could not have worked.

That last behaviour is a small thing that changes how the feature feels. The failure mode of a strict tool is usually an error you have to go and research. Here the error is the fix.

What this does not solve

  • The first box is still cold. Somebody pays for the initial refresh, and after a lockfile change somebody pays again.
  • It is per project. Two projects on the same ecosystem do not share, which is the same isolation argument costing you disk.
  • A poisoned package is cached like any other. The cache accelerates fetching; it makes no claim about what was fetched. That is the egress allowlist's job on the way in and the receipt's job afterwards.
  • Container and microvm tiers still pull an image. Images are pre-pulled and runs never pull, so that cost lands at setup rather than at box creation.

FAQ

How does h5i speed up box creation?

A warm dependency cache, one per project and ecosystem, keyed by a digest of that ecosystem's lockfiles and mounted read-only into agent boxes. Cold dependency install is the difference between a twenty-second box and a four-minute one.

What happens when the lockfile changes?

The cache key no longer matches, so the cache is listed as stale and never handed to a box. Not refreshed automatically and not used with a warning. Packages resolved for a different dependency set are a silent wrong answer, and a slower box is a better outcome than a mystery.

Why is the cache read-only?

Because a writable shared cache is a mutable surface two boxes can both reach, so one box could plant something the next picks up. Read-only costs nothing in correctness, because every package manager falls back to fetching what it cannot find, so a hit saves the download and a miss behaves normally.

What writes the cache if agent boxes cannot?

h5i box cache refresh, which runs the install step alone with egress narrowed to the registry hosts and no agent inside. It needs a project-declared profile with exactly that egress, and when there is not one it prints the profile ready to paste rather than creating a box whose fetch could not have worked.
