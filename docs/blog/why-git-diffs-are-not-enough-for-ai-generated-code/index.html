Why a diff is not enough for AI-generated code

A diff is a photograph of a room after everyone has left. It is useful and it is not a record of what happened, and for code an agent wrote unattended, the difference between those two things is the whole review.

By Koukyosyumei Reading time 7 min Tags Review · Evidence · Opinion
The claim. A diff is a complete description of a change and a very incomplete description of an event. For human-written code that gap was covered by the author: a person who could explain what they tried, what they ran, and what they decided against. When the author is an agent that worked unattended for forty minutes, that cover is gone, and the diff is left carrying weight it was never built for. What fills the gap is a record of execution: what ran, with which exit code, observed by whom, and what a boundary refused.

Start with what a diff is good at, because it is good at something. It is an exact, minimal, reviewable description of how one tree differs from another. It composes, it merges, it bisects. Thirty years of tooling assume it. None of that is in question.

The question is what happens when you use it as the sole evidence for a decision it was never designed to support: is this change safe to take?

Four things a diff structurally cannot show

Not "usually does not". Cannot, because the information is not in the artefact.

What ran. A diff that adds a test file does not tell you the test was run, or passed, or was written to pass by weakening the assertion. A diff that adds a dependency does not tell you what its install script did on the way in. The tree at the end looks the same whether the work was verified or asserted.

What was reached for. A process that read ~/.ssh and decided not to use it leaves no diff. A process that tried to POST somewhere and was refused leaves no diff. Every unsuccessful attempt, which is exactly the category a security reviewer cares most about, is invisible in a comparison of two trees.

What was considered and dropped. Human diffs used to carry this in the commit message, badly but nonzero. An agent's abandoned branch of reasoning leaves nothing at all.

Proportion of effort to risk. A one-line diff can be the most dangerous change in a release and a two-thousand-line diff can be a formatter run. A reviewer's attention is allocated by diff size because diff size is the only signal the artefact offers, and it is close to uncorrelated with the thing you actually want to weight.

Why this got worse rather than newly true

None of the above is new. It was survivable because a diff was always accompanied by a person who had the missing information in their head. The review was a conversation with someone who could answer "did you run this?" and "why not the other approach?" The diff was an index into a human's memory of the work.

Agent-written code removes the index's referent. The author can produce fluent prose about its own work on request, and that prose is a self-report generated by the same system that produced the code, with no obligation to mention the test it skipped or the file it edited without reading. It is more confident than a human's account and less grounded.

So the gap that was always in the artefact stopped being covered, all at once, across a growing fraction of every codebase.

What actually fills it

Not a better diff viewer. The missing information is about execution, so it has to be collected during execution, by something other than the thing being observed.

That is what an execution receipt is: an append-only record of every observed command, its exit code, its resource usage and the destinations a boundary refused, written by the host rather than by the workload. Two properties make it worth reading rather than merely voluminous.

It is sealed. The box's write window under its own directory is exactly its spool. The receipt log and the stored payloads are siblings of that spool, outside every grant the policy hands out. The box stages a record; the host ingests it. There is no path from inside to a record the host has already written.

It labels its own reliability. Each record carries the lane that observed it. host-env-run means h5i watched from outside: exits and resource usage from the supervisor's wait4, egress from the allowlist proxy's own log. tee-shim means the box's shell reported it, which is box-claimed. A review that cannot tell those apart is treating testimony as observation.

The honest limits of the receipt

A record that over-claims is worse than none, so: an agent can stage extra records, or stop writing them. Both are visible, since a gap between host-observed exits and box-reported commands is itself a finding, and that is the whole claim. It does not extend to "the log is complete."

The receipt also says nothing about whether the code is correct. A clean run and a subtle backdoor coexist comfortably. This is not an argument that execution evidence replaces reading the diff. It is an argument that reading the diff was never the complete review, and that we only got away with it because a human used to be standing next to it.

What to do with this

Read the diff. Then read what ran, starting with what was refused. If your tooling cannot tell you what was refused, notice that you are reviewing the residue and calling it the record.

FAQ

What can a git diff not tell you about AI-generated code?

Four things, none of which are in the artefact: whether anything was actually run, what the process reached for and was refused, what approaches were considered and dropped, and how much risk the change carries relative to its size. Every unsuccessful attempt in particular is invisible, because a diff compares two trees and a refused connection changes neither.

Why did this become a problem only recently?

It did not become newly true, it stopped being covered. A diff was always an incomplete record of an event, and it was survivable because the author was a person who held the missing information and could be asked. An agent's account of its own work is a self-report from the same system that produced the code.

What is an execution receipt?

An append-only record of every observed command in a box, with its exit code, its resource usage, and the destinations the egress allowlist refused, written by the host rather than by the workload. Each record carries the lane that observed it, so host-observed evidence and box-claimed evidence stay distinguishable.

Does a receipt mean the code is correct?

No, and nothing about it suggests otherwise. A clean run and a subtle backdoor coexist comfortably. A receipt tells you what happened during execution; whether the resulting change is correct is still a reading problem.
