What is inside an execution receipt

A log format is a set of decisions about what someone will be able to prove later. Here is h5i's, field by field, including the three fields that exist only so a reviewer cannot mistake missing evidence for clean evidence.

By Koukyosyumei Reading time 8 min Tags Reference · Receipts · Schema
The shape. One append-only JSONL file per box, one record per observed execution. Every record carries an id, a sortable timestamp, the env_id, the policy_digest that was in force, and a source naming the lane that observed it. Then the execution itself: cmd, cwd, exit_code, wall_ms, cpu_ms, max_rss_kb, timed_out. Then two optional sub-objects, egress and browser, when there is something to say.

Most agent logging formats are shaped by what was easy to collect. This one is shaped by a single question: what does a reviewer need so as not to have to trust the box? Several of the fields below exist for no other reason.

The identity fields

FieldWhat it is
idA short stable handle, so h5i box inspect <name> --capture <id> can pull one record's full detail from a report that only summarised it.
timestampRFC3339 UTC at microsecond precision, chosen to be lexically sortable. Sorting a log should not require parsing it.
env_idWhich box this is evidence for, e.g. env/claude/fix-auth.
policy_digestA sha256 of the resolved policy in force when this ran. Not the requested policy. The enforced one.
sourceThe lane that observed the record. This is the field that decides how much the rest of the record is worth.

policy_digest on every record rather than once per box is deliberate. A box can be reconfigured across its life, and a record that carried no digest would be a claim about an execution with the rules detached. With the digest inline, a run and the boundary that governed it cannot drift apart, and policy.resolved.toml sits beside the log to be verified against it.

The lane is the trust field

source is one string and it carries most of the format's design.

sourceWho observed itGrade
host-env-runh5i, host-side. Exits and resource usage from the supervisor's wait4; egress from the allowlist proxy's own log.Host-observed
viewerh5i's own viewer forward, including whether a human took the controls.Host-observed
tee-shimThe box's shell shim, teeing commands into the spool.Box-claimed
inbox-captureStaged by the box.Box-claimed

A format that merged these into a single stream would be quietly asserting that a box's account of itself and a supervisor's wait4 are the same kind of fact. They are not, and no amount of downstream tooling can recover the distinction once it has been dropped at write time. So it is a required field, and the console labels every row with it.

The execution fields

receipt.json (one record)
{
  "id": "c4a91f",
  "timestamp": "2026-08-07T09:14:22.481930Z",
  "env_id": "env/claude/fix-auth",
  "policy_digest": "sha256:9f2c…",
  "source": "host-env-run",
  "cmd": "npm ci",
  "cwd": "/work",
  "exit_code": 0,
  "wall_ms": 38214,
  "cpu_ms": 51907,
  "max_rss_kb": 412880,
  "git_tree": "a3f9c2b…",
  "egress": {
    "allowed": 214,
    "denied": 7,
    "hosts": [ … ]
  }
}

cmd is secret-redacted before it is written, and the scrub is recorded by rule id rather than by value, so a reviewer can see that a secret was involved without seeing it. timed_out is a separate boolean rather than a magic exit code, because "the wall-clock limit killed the process group" and "the program exited 137" are different facts and only one of them is about your policy. git_tree pins which tree the run was taken against.

The egress sub-object

egress carries allowed and denied counts plus per host:port verdicts. denied is the single highest-fidelity signal in the whole format: the proxy refused an off-allowlist destination, host-observed, and the box supplies none of it.

The host list is deduplicated and bounded, and when the bound is hit hosts_truncated is set. That flag matters more than it looks: a probing loop hitting a thousand hostnames would otherwise produce a clamped list that reads like a complete one, which is exactly the shape of a mistake you would not catch.

The browser sub-object

When a run drove the in-box browser, the record carries what the page said back: console messages at error and warning level, uncaught errors, and failed_requests, meaning HTTP 400 and above or no status at all, which is what a request blocked by the egress allowlist looks like from inside the page.

Ordinary log and info chatter is deliberately not carried. It is not evidence, and including it would bury the two lines that are.

Two flags here exist purely to stop a reviewer drawing a false conclusion from an empty list:

  • truncated is set when the per-record cap dropped entries, so a flood is never silently rendered as a clean page.
  • unavailable is set when the drain could not reach a browser at all, because the daemon was not running or the run closed it. "Nothing was looked at" is a different claim from "nothing was wrong", and a format that cannot distinguish them will eventually let someone ship on the wrong one.

If you take one idea from this format, take that one. Most logging schemas represent absence with an empty array and leave the reader to guess whether that means clean or uninspected.

What the format does not do

  • It is not a transcript. There is no prompt, no model output, no reasoning. Those were removed on purpose: they came from the subject and could not be observed from outside.
  • It is not complete. An agent can stage extra records or stop writing them. Both are visible as a gap against host-observed exits, and that is the whole claim.
  • Interactive sessions are one record, not many. The shim skips a TTY session by design, so an interactive shell appears as a single host-observed process.
  • A microvm receipt has no egress at all. The guest's netstack drops packets without reporting them, so there is nothing to summarise.

FAQ

What format is an h5i execution receipt?

Append-only JSONL, one file per box, one record per observed execution, with the raw payload of each record stored alongside. receipt.json in an export is the same material; report.md is it sorted for a human.

What does the source field mean?

It names the lane that observed the record, which decides how much the rest of the record is worth. host-env-run and viewer are host-observed; tee-shim and inbox-capture are the box's own account of itself. Merging them at write time would destroy a distinction no downstream tool can recover.

Why does every record carry a policy digest?

Because a box can be reconfigured across its life, and a record without a digest is a claim about an execution with the rules detached. With the digest inline, a run and the boundary that governed it cannot drift apart, and policy.resolved.toml sits beside the log to be verified against it.

Why are there separate truncated and unavailable flags?

So an empty list is never ambiguous. truncated means entries were dropped by the per-record cap, so a flood is not rendered as a clean page. unavailable means no browser could be reached at all, because nothing was looked at is a different claim from nothing was wrong.

Does the receipt include prompts or model output?

No. Those were deliberately removed. They came from the subject of the record rather than from observation, and a format that mixes observed facts with self-reported ones makes the observed half less useful rather than the self-reported half more.
