Claude Code Hooks vs Git Hooks

Git hooks fire on repository operations; Claude Code hooks fire in the agent tool loop. They see different things and carry different trust guarantees, so well-run AI repos layer both rather than picking one.

Published 2026-06-03 · updated 2026-08-07 Reading time 10 min read Tags Claude Code · Git hooks · Automation
Key takeaways
  • A Git hook sees a repository event; an agent hook sees an agent event; each is structurally blind to the other's layer.
  • Layer them: agent hooks give you tool-loop context while the agent works; Git hooks and CI enforce at the commit and push boundary.
  • Ask "who can turn it off?" Client-side Git hooks fall to --no-verify, agent hooks fall to whoever can edit the config, and only observation below the agent survives both.

AI agents now author a growing share of the commits in many repositories, which makes one question routine: what produced this change, and was it checked before it landed? The answer lives in two automation layers that look alike (both are hooks, both run your scripts at a defined moment) but fire on different lifecycles. Git hooks run when Git performs a repository operation: commit, merge, applypatch, push. Claude Code (and Codex) hooks run inside the agent's tool loop: a prompt arrives, a tool runs, a turn ends. Because they observe different lifecycles, they see different things, fail in different ways, and carry different trust guarantees. They are complementary, not interchangeable, and the useful way to reason about them is by asking who can switch each one off.

Git hooks: repository lifecycle

The official Git hooks documentation says hooks are programs placed in a hooks directory, usually $GIT_DIR/hooks or a path configured with core.hooksPath. Git invokes them at specific moments in Git operations. A pre-commit hook can block a commit. A commit-msg hook can validate the message. Server-side hooks can inspect pushes.

Git hooks are excellent for repository policy: formatting, linting, secret checks, commit-message conventions, and push-time enforcement.

Claude Code hooks: agent lifecycle

Anthropic's Claude Code hooks reference describes hooks as user-defined commands, HTTP endpoints, or prompt hooks that execute at lifecycle events. Events include SessionStart, UserPromptSubmit, PreToolUse, PostToolUse, Stop, and others. Command hooks receive JSON context on stdin.

That makes Claude Code hooks useful for agent-aware automation: inject context at session start, inspect tool calls before execution, record edits after tool use, summarize state when a turn stops, or add deterministic feedback after a file change.

What each layer can and can't see

The two layers are blind to each other by construction. A Git hook is handed a tree and a set of refs; it never learns which prompt motivated the change or which files the agent read before writing one. An agent hook is handed the prompt and the tool call; it never sees a teammate who commits from a plain terminal, or a force-push from CI. Read down the two halves and the asymmetry is the whole point. The Git rows are tree- and ref-centric and blind to intent; the agent rows are intent- and tool-centric and blind to any repository operation that happens outside the session. Use only Git hooks and you know a commit landed but not which prompt caused it or what the agent inspected first; use only agent hooks and you have rich session context but no gate at the final commit or push.

Where h5i moved its observation, and why

h5i used to wire agent hooks. It stopped, and the reason is the same trust question this post is built on.

A hook is a request. PostToolUse fires because the runtime chose to fire it, at a moment the runtime chose, with the fields the runtime chose to pass. That is fine when you are instrumenting your own work and want context. It is the wrong foundation when the point is to observe code you do not trust, because every part of that chain is configuration, and configuration is editable by whoever has the config.

So h5i moved observation underneath the agent instead. Inside a box, two things watch, and neither is a hook:

  • The supervisor, host-side. Exits and resource usage come from wait4 on the process h5i started, and denied egress comes from the allowlist proxy's own log. The box contributes nothing to either. In the receipt these land in the host-env-run lane.
  • A shell shim, in-box. The box's shell tees each top-level non-interactive command into the box's spool, so an open-ended session leaves a record without the agent agreeing to anything. This is box-claimed evidence, and the receipt labels it tee-shim for exactly that reason.

The two are labelled separately on purpose. Host-observed and box-claimed are different grades of evidence, and a gap between them, more commands reported than exits observed or the reverse, is itself a finding. h5i's claim stops there: an agent can stage extra records or stop writing them, and both are visible.

The one config h5i does still pin

There is a residual even when observation lives below the agent. If the agent can rewrite the file that configures its own tooling, it can change what happens on the next run. So a box mounts .claude/settings.json and .codex/config.toml read-only over their place in the workspace. $WORK is writable; those two paths are not.

That is a small rule with a general shape, and it is the same shape as moving a Git check from pre-commit to pre-receive: the thing being watched does not get to edit the watcher's configuration. Put the rule somewhere the subject cannot reach, or accept that it is advisory.

A worked layering: agent hooks and Git hooks together

Wiring both is mechanical. The agent hooks record intent and trace while the agent works; the Git hooks gate the result when it tries to land. Here is a minimal pairing with two scripts of your own. The agent side declares them in .claude/settings.json:

{
  "hooks": {
    "UserPromptSubmit": [
      { "hooks": [{ "type": "command", "command": "./scripts/log-prompt.sh" }] }
    ],
    "PostToolUse": [
      { "matcher": "Edit|Write|Read",
        "hooks": [{ "type": "command", "command": "./scripts/note-edit.sh" }] }
    ]
  }
}

The Git side is two ordinary scripts. A .git/hooks/pre-commit gate runs before the snapshot is written:

#!/bin/sh
# block a failing or secret-bearing tree before it becomes a commit
cargo test --quiet || exit 1
if git diff --cached | grep -nE 'AKIA|BEGIN [A-Z ]*PRIVATE KEY'; then
  echo "secret-like content staged" >&2
  exit 1
fi
exit 0

…and a .git/hooks/pre-push gate enforces policy at the boundary refs cross:

#!/bin/sh
# refuse a direct push to the protected branch
if [ "$(git rev-parse --abbrev-ref HEAD)" = "main" ]; then
  echo "direct push to main blocked" >&2
  exit 1
fi
exit 0

What each catches that the other can't: the UserPromptSubmit handler records the prompt verbatim; the pre-commit hook will never see it. The pre-commit hook blocks a failing or secret-bearing tree for everyone, including a teammate who never opened an agent, and no agent hook can reach that path. Run them together and the final review has both halves: the agent trace (prompt → reads → edits) and the conventional Git verdict (tests passed, no secrets, branch policy held). Both halves stay yours to own, and both are advisory in the same way: a contributor can skip the Git hook with --no-verify, and an agent that can edit .claude/settings.json can drop the handler.

Trust and determinism: advisory vs enforced

The two layers do not offer the same guarantee, and conflating them is the costliest mistake. The right question for any hook is not "does it run?" but "who can turn it off?"

Git hooks are local and advisory. They live in $GIT_DIR/hooks (or a path set by core.hooksPath) and are not tracked in the repository by default, so a fresh clone has none of them until each contributor installs them. Any of them is bypassable in one flag: git commit --no-verify skips pre-commit and commit-msg; git push --no-verify skips pre-push. A client-side Git hook is therefore a convenience for the cooperative, never a control against the determined. The only Git hook that enforces for everyone is a server-side one, pre-receive or update on the remote, or an equivalent required CI check, because the client cannot opt out of it.

Agent hooks inherit the trust of the config that declares them. A .claude/settings.json or .codex/config.toml hook is exactly as binding as that file: whoever can edit the config, or pass disableAllHooks, can switch it off. That is fine for observability you control, and inadequate when the point is to observe code you don't trust.

h5i closes that gap by not depending on a hook at all. The supervisor observes from the host and the shell shim observes from below the agent's tool loop, so disableAllHooks has nothing to disable. The agent's own config file is separately pinned read-only, which removes the one remaining way it could change what watches it next time. The general rule is the one worth carrying away: an observation mechanism the subject can configure is a courtesy, and only a mechanism outside the subject's reach is a control.

Failure modes worth knowing

  • The hook silently never fires. Usually the wiring isn't installed (a clone with no scripts in $GIT_DIR/hooks) or the matcher doesn't match (a PostToolUse matcher of Edit alone won't catch Write). Neither case errors; the automation just doesn't happen. Verify the wiring, don't assume it.
  • Double capture when two observers overlap. Anything that both wraps a command and tees it records it twice. The rule that avoids it is to give each observer a disjoint skip list rather than trusting them to notice each other. h5i's shim skips h5i's own invocations, nested shells (it marks its own environment), and interactive sessions, so a TTY shell is not recorded line by line.
  • Bypass at the boundary. --no-verify defeats any client-side Git hook. If a rule must always hold, mirror it server-side or in a required CI check; a local hook alone is an honor system.
  • An agent disabling its own hooks. With write access to its config an agent can drop a hook. Two things resist that: pinning the config read-only, and not putting the security-relevant observation in a hook to begin with.

Layer, and know which layer holds

Treat this as a layering decision rather than an either/or. Use agent hooks for the things you want while working on your own code: session context, a reminder after an edit, a summary when a turn ends. Use Git hooks, with a server-side check or a required CI job behind them, to gate the tree and the refs where the rule has to hold for every contributor and every tool.

Then be clear with yourself about which of those is a control and which is a convenience. Both hook layers are configuration, and configuration bends to whoever holds the config. When the code is not yours, put the boundary somewhere else entirely: a box whose policy was hashed before the agent started, watched by a supervisor the box cannot see.

FAQ

Can a Git hook capture Claude Code prompts?

Not reliably by itself. Git hooks run at Git operations and do not naturally receive Claude Code session context.

Can a Claude Code hook replace pre-commit?

It can run checks, but repository enforcement still belongs at Git boundaries if you want the policy to apply to all contributors and tools.

Which one should I install first?

For enforcement that holds for everyone, a server-side Git hook or a required CI check. Agent hooks come second, for the ergonomics of your own sessions. If the code is untrusted, neither layer is the answer and containment is.

Can an agent disable its own hooks?

If it can edit the config that declares them, yes, and that includes passing disableAllHooks. That is why h5i does not put security-relevant observation in a hook. Inside a box the supervisor observes exits and egress from the host, a shell shim observes commands from below the tool loop, and the agent's config file is mounted read-only so it cannot change what watches it next run.
