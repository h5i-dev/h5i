Prompt injection: contain it, because you cannot detect it

Every prompt-injection defence that works by reading the attacker's text is a filter the attacker can read back. The control that survives contact is the boring one: bound what a compromised agent can reach, and keep a record of everything the boundary refused.

By Koukyosyumei Reading time 11 min Tags Security · Prompt Injection · Containment · OWASP LLM
In one paragraph. Prompt injection has no reliable detector, because a detector is a classifier over text written by someone who can see the classifier. So do not put the security claim there. Put it in a boundary the attacker's text has no vote in: a filesystem allowlist the agent's instructions cannot widen, an egress allowlist enforced at L3/L4, credentials that never entered the box, and an output gate a human passes through. Then the question stops being "was this injected?" and becomes "what could an injected agent have done here?", which has an answer you can write down in advance.

Prompt injection is the LLM-era version of SQL injection. Untrusted input reaches a control channel, the control channel obeys it, and the system does something nobody asked for. OWASP ranks it LLM01:2025, and the indirect variety is the one that matters for coding agents: the payload arrives in a README, a dependency's changelog, a test fixture, a web page the agent fetched, or an issue comment. Nobody typed it at the agent. The agent read it, because reading things is the job.

The industry's first instinct was to scan for it. That instinct is worth examining before you build on it.

Why detection cannot carry the weight

A pattern matcher over "ignore previous instructions" and its cousins is high precision and low recall by construction. It catches the phrasings you thought of. It has nothing to say about a payload phrased as a helpful code comment, spread across three files, or written in a language your rules do not cover. Every published bypass technique starts from the same observation.

A model-based classifier catches more, and it introduces a problem the regex did not have: its input is the attacker's text, so the attacker can address it. A payload that argues with the classifier is a payload aimed at your defence rather than at your agent, and it is not a hard one to write.

This is not an argument against running a scanner. A cheap deterministic pass over what an agent read is useful triage, and a flagged run is worth looking at first. It is an argument against letting the scanner be the thing you rely on. The question a detector answers is "does this look like an attack?" The question a boundary answers is "what happens if it was one?" Only the second has a stable answer.

What a boundary bounds

Assume the injection worked. The agent is now pursuing someone else's goal with your tools. Write down what it can reach.

Inside an h5i box, that list is the policy, and the policy was resolved and hashed before the box existed. The agent's instructions are not an input to it. Concretely:

What the injection wantsWhat it meets
Read ~/.ssh, ~/.aws, a neighbouring repositoryThe filesystem allowlist. Those paths were never granted, and Landlock is allowlist-only: there is nothing to widen from inside.
POST the source tree to an attacker's hostThe egress allowlist. At supervised that is default-drop nftables in a private netns with DNS pinned by a hosts file, so an IP literal fails the same way a hostname does.
Steal an API token from the environmentNothing to steal. The model API key stays on the host and a reverse proxy injects it into outbound requests; the per-box HOME state is a copy with credential-shaped entries stripped at any depth.
Use the other runtime's credential against an allowlisted hostRuntime scoping. agent-claude grants only Claude's HOME state and Anthropic egress; agent-codex only Codex's. This one is not tidiness, it is the specific laundering move the allowlist would otherwise permit.
Write a backdoor into your working treeThe box has no write path to the host. h5i box export writes a patch to a directory you name, path-validated against symlink escapes and nested .git, and you apply it.
Turn off the thing watching itThe agent's own config file is mounted read-only over its place in the workspace. $WORK is writable and that one path is not.

None of those rows depends on recognising the payload. That is the whole point. The containment story is boring in exactly the way a security control should be: it does the same thing whether the injection was clever or clumsy, in English or in Base64, novel or six years old.

The attempt is evidence, and the proxy is the witness

A blocked exfiltration is more interesting than a successful build. When the egress allowlist refuses a destination, the refusal is observed host-side, by the proxy's own log, and lands in the box's receipt under the host-env-run lane. The agent does not report it and cannot suppress it: the box's write window under its own directory is its spool, and the receipt log is a sibling of that spool, outside every grant.

That is why report.md puts denied egress attempts at the very top, above what ran and above what the browser saw. A box that tried to reach a host the policy refused is the single most interesting line that can appear in a review, and burying it under a build log would be a design mistake.

~/my-project
$ h5i box export review-pr-1234 --out ./review
$ head -20 ./review/report.md

# Denied egress
  paste.example.invalid:443   refused (not in net.egress)   x3

# What ran
  ✔ npm ci                  exit 0   host-env-run
  ✔ npm test                exit 0   host-env-run
  ? curl -sX POST …         exit 6   host-env-run

Read that top section first, always. Three refused connections to a host nobody declared is not a build problem.

One honest caveat about which tier produced the evidence. The container tier's proxy sees every CONNECT and counts allows and denies. The microvm tier drops packets in the guest's netstack without reporting them, so its receipt carries no egress summary at all. Stronger enforcement, thinner evidence, and worth knowing which trade you picked.

The second injection: escape sequences aimed at you

There is a related attack that has nothing to do with models, and it gets missed because it targets a different victim. A terminal's output is not text. An escape sequence can rewrite your clipboard, retitle the window, or ask the graphics protocol to read a file. Any pipeline that renders untrusted bytes into a human's terminal has handed the attacker a second control channel, one that does not need an LLM to obey it.

h5i's terminal viewer, h5i box view --term, closes this by construction rather than by filtering: the box never writes to your terminal. It supplies compressed pixels inside a WebSocket message, and every escape sequence you receive is generated by h5i. There is no untrusted byte stream to sanitize, because there is no untrusted byte stream.

The status row follows the same logic. Row one is h5i's, and a page cannot draw on it or be clicked through it. It carries the box, the mode, who holds the control lock, the page's origin, the egress policy, and a count of console errors. The origin is the field that never gets shortened at the expense of the truth: a long URL loses its path, and a host too long for the row is cut from the left, because shortening bank.example.evil.test from the right is the trick itself.

That last detail is the one worth stealing for your own tooling. Truncation is a rendering decision that becomes a security decision the moment the truncated string is a host name.

What is not mitigated

Being specific here matters more than the rest of the post, because a containment claim that over-reaches is worse than none.

  • The agent can send your source to the model API. Containment stops the agent touching the host. It does not stop it putting private code in a prompt. That is a separate control, a self-hosted model or no model egress at all, and h5i will not imply otherwise.
  • An injected agent can still write wrong code. A subtle backdoor in the patch is a review problem, not a containment problem. The receipt tells you what ran; it does not tell you the diff is correct.
  • A careless policy opens the channel by hand. Grant a credential, allow egress to a general-purpose endpoint, and the boundary is doing what you told it. No tier makes a bad profile safe.
  • Four of the five tiers share the host kernel. Strong against a runaway agent and careless dependency code, not a claim against a targeted kernel exploit. microvm is where that changes.
  • Detection stays low-recall. Nothing above improves it. If you run a scanner, run it as triage and label it as triage.

The question worth asking instead

"Was this run injected?" is a question you cannot answer reliably, which is why it produces so much anxious tooling. "What could an injected run have done here?" is a question you answer by reading a config file, and you can answer it before the run rather than after.

That is the whole trade. You give up the fantasy of catching the payload, and in exchange the blast radius becomes something you wrote down on purpose, and the attempts to exceed it become something you can read.

FAQ

Can you detect prompt injection reliably?

No. A detector is a classifier over natural language written by someone who can read the detector. Pattern matching catches the phrasings you thought of. A model-based classifier catches more and can itself be talked out of a verdict, because its input is the attacker's text. Run detection as cheap triage and put the security claim somewhere the attacker's text has no vote.

What does containment actually stop?

Reading paths the filesystem allowlist never granted, reaching hosts outside the egress allowlist, using a credential that never entered the box, and writing anything on the host, since a box has no write path out. It does not stop the agent putting your source in a model prompt.

Why does runtime scoping matter here?

Because a credential the box holds for one purpose is a credential an injected agent can spend on another. agent-claude grants only Claude's HOME state and Anthropic egress, agent-codex only Codex's. Without that split, an injected Claude session could read the other runtime's token and use it against a host the allowlist already permits.

How does the terminal viewer avoid escape-sequence injection?

By never letting the box write to the terminal. h5i box view --term receives compressed pixels in a WebSocket message and generates every escape sequence itself. The status row is h5i's and cannot be drawn on, and an over-long host is truncated from the left so the suffix stays visible.

Does h5i solve prompt injection?

No, and nothing does. It changes what a successful injection is worth. The agent's authority is the policy hashed before the box existed, and every destination the allowlist refused is recorded by the proxy rather than by the agent.
