Review a pull request by running it

A diff review is a reading exercise. It tells you what somebody wrote, in a format that flatters small changes and hides large ones, and it tells you nothing about what the branch does when it executes. h5i box --pr gives the branch a disposable machine to execute on, and gives you a report of what it did there.

By Koukyosyumei Reading time 9 min Tags Pull requests · Review · Containment
In one paragraph. h5i box --pr 1234 fetches refs/pull/1234/head into a detached box: its own repository, your repository untouched after creation, and the inherited origin remote dropped. Nothing of your machine goes in. You, or an agent, build it, test it, start its dev server and drive a browser against it, all inside the boundary. Then h5i box export writes a report whose first section is every destination the egress allowlist refused.

Here is the uncomfortable thing about reviewing a pull request from someone you do not know. You are being asked to decide whether code is safe by reading it, and reading is the weakest tool you have for that question. A build script that phones home is three characters of difference from one that does not. A dependency bump is a hyperlink to a hundred thousand lines nobody in the thread has read. A minified fixture is unreadable by construction. The review UI shows you a tidy green and red column and quietly implies that looking at it constitutes diligence.

The reason we review this way is not that it works well. It is that the alternative used to be dangerous. Checking out an untrusted branch and running npm install && npm test hands its lifecycle scripts your shell, your SSH agent, your cloud credentials and your network. So we read instead, and hope.

A box removes that trade. Running the branch stops being the risky option.

The loop

~/my-project
$ h5i box --pr 1234
  created box pr-1234 · detached · isolation: supervised · origin remote dropped

$ h5i box shell pr-1234
box$ npm ci && npm test        # lifecycle scripts run in here, not on your machine
box$ npm run dev &
box$ agent-browser open http://localhost:3000
box$ exit

$ h5i box export pr-1234 --out ./review
$ $EDITOR ./review/report.md    # read this before you approve anything

--pr takes a number, a #number, or a URL, and needs only git: it fetches refs/pull/<n>/head and pins it as the base revision, immutably, at creation. Nothing re-resolves it later, so what you reviewed is what you reviewed.

Why detached is the whole point

A box created from your repository is a real git worktree sharing the object store, which is what lets h5i box apply land the work back locally. That is the right shape for your own work and the wrong shape for somebody else's.

So a pull request gets a detached box instead, and the difference is worth spelling out because each clause closes a specific door:

  • It gets a repository of its own, inside its own directory. Not a worktree of yours, so there is no shared object store, no shared refs, and nothing it can write that your repository would later read.
  • Your repository is neither read nor written after creation. The copy happens once and then the connection is over.
  • The inherited origin remote is dropped. A remote is a network handle with credentials attached; leaving it in place would mean the box arrived holding a door nobody decided to open.
  • apply and rebase refuse and point you at export. There is no command that turns "I reviewed this" into "this is now in my tree" by accident.

External code should always arrive in that shape, whether it came from a pull request, a clone URL, or a tarball somebody sent you.

What the report leads with

h5i box export <name> --out ./review writes three files: the path-validated patch.diff, the human-readable report.md, and receipt.json with every observed execution and the digest of the policy that was enforced. It refuses to overwrite a non-empty directory unless you pass --force, and secret redaction and size caps apply to all three.

The ordering inside report.md is an opinion, and it is the most useful thing in this post:

OrderSectionWhy it is there
1Denied egress attemptsThe branch tried to reach a host the policy refused. Observed host-side by the proxy, not reported by the box. Nothing else in a review is more interesting.
2What ranEvery command, its lane, its exit code.
3What the browser sawConsole errors, uncaught exceptions and failed requests, collected by h5i right after the command rather than summarised by the agent.
4Viewer sessionsWhether a human watched, and whether a human took the controls.
5The agent's proposalLast, because it is the only section written by the thing being reviewed.

That last row is the design principle in miniature. An agent's account of its own work is useful context and it is not evidence, so it sits underneath the things h5i watched itself. A review surface that leads with the author's summary is a review surface that has quietly inverted its own trust model.

./review/report.md
# Denied egress
  telemetry.vendor.invalid:443    refused (not in net.egress)   x7

# What ran
  ✔ npm ci              exit 0    host-env-run   38.2s
  ✔ npm test            exit 0    host-env-run   12.7s
  · node scripts/postinstall.js   exit 0    tee-shim

# What the browser saw
  ! 2 console errors on http://localhost:3000/checkout

Seven refused connections to a telemetry host nobody declared, from a branch whose description says it fixes a date-formatting bug. That is not a line you would have found by reading the diff, and it is the first thing the report shows you.

Where the agent fits

Most of the time you will not be the one typing in the box. h5i box shell inherits stdio, so Claude Code or Codex runs inside the boundary rather than wrapping each call it makes, and everything it spawns is contained by construction. Give it the branch and let it build, test, exercise the app and write up what it found.

The agent is scoped to one runtime while it does this. The agent-claude profile grants Claude's own config state and Anthropic egress and nothing else; agent-codex the same for Codex. A prompt-injected reviewer cannot reach for the other runtime's token, which matters more than usual here because the whole premise is that the code being reviewed might be hostile.

If the branch changes a user-facing flow, add the browser. Chrome and a fresh profile live in the box, the agent drives them through agent-browser, and h5i box view pr-1234 puts the same viewport on your screen so you can watch, or press i and take the controls yourself. Both are recorded, and the report says which.

How this sits next to CI

They answer different questions and neither replaces the other. CI answers whether the checks you declared in advance pass, for every contributor, on a runner nobody can reconfigure from the branch. That is a gate, and it should stay one.

A box answers the question that comes up when CI is green and something still feels wrong. What did this actually do while those checks ran? What did it try to reach? Can I open a shell in the same environment and poke at it without thinking about my SSH keys? CI cannot express that, and a box is not trying to be a gate.

What this does not do

  • It does not tell you the code is correct. A subtle logic bug survives a clean report. Running the branch adds evidence to a review; it does not replace reading it.
  • It does not stop a payload that only fires later. Code that behaves in a box and misbehaves in production is a real technique. What you get is the record of what happened this time.
  • It does not contain a targeted kernel exploit at the shared-kernel tiers. For code you actively suspect, use isolation=microvm, where the boundary is a hypervisor.
  • An empty denied-egress section is not proof of nothing. At isolation=microvm the guest's netstack drops packets without reporting them, so a microvm receipt carries no egress summary at all. Stronger enforcement, thinner evidence.

Read what it did, not what it says

The reason to run a pull request instead of only reading it is not that reading is worthless. It is that reading is the only tool most reviewers have, and it happens to be blind to the exact category of problem that matters most: what the code does when nobody is looking at the diff.

A box makes running it the cheap option. Everything after that is just reading a report that the author did not write.

FAQ

Why is a detached box the right shape for a pull request?

Because a pull request is code you have not read yet. The box gets a repository of its own, your repository is neither read nor written after creation, and the inherited origin remote is dropped so the box arrives holding no network handle. apply and rebase refuse there and point at export.

Does this need GitHub credentials in the box?

No. Fetching the head uses whatever access you already have, host-side. Nothing goes in: no SSH key, no GitHub token, no model API key, no cloud credential. Where an in-box client does need an authenticated host, declare a [[profile.X.auth]] grant and a host-side proxy injects the credential into the request.

What does the report tell me that the diff does not?

Which destinations the egress allowlist refused, observed by the proxy rather than reported by the box. Every command with its exit code and the lane that saw it. What the page said back if a browser was driven. Whether a human took the controls. And, last, what the agent claims it did.

Can an agent do the review inside the box?

Yes, and it is the ordinary case. h5i box shell drops Claude Code or Codex in with the branch checked out, scoped to one runtime's credentials, under the same policy as everything else in the box.

How is this different from CI?

CI answers whether declared checks pass, for everyone, as a gate. A box answers what the branch did while they ran, and lets a human open a shell in the same environment. Use both.
