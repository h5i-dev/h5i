What is a contained agentic development environment?

Sandboxing one command was the right idea applied at the wrong scale. An agent's work is not one command: it is a shell, a package manager, a build, a test run, a dev server and a browser, all of which have to be inside the same boundary or the boundary is decorative.

By Koukyosyumei Reading time 8 min Tags Explainer · Containment · Definitions
Definition. A contained agentic development environment is a disposable environment that holds everything a coding agent needs to do real work, the code, the agent process, the toolchain, the dependencies, the dev server and a browser, inside a single enforced boundary. Nothing of the host machine is inside it: no SSH key, no cloud credential, no personal browser profile. Nothing leaves it except through one deliberate step, which produces a patch, a report and a record of what actually ran. h5i is one implementation, and it calls the unit a box.

Most sandboxing tools were designed for a smaller problem: run this untrusted command safely. That framing works when the untrusted thing is a single process with a beginning and an end. It breaks the moment the untrusted thing is a coding agent, because an agent's work is not a command. It is an open-ended sequence of them, chosen at runtime, some of which start long-lived processes.

Wrap each command and you have built something that depends on the agent choosing to be wrapped. Wrap the shell instead, and everything the session spawns is inside by construction. That shift, from confining a command to confining a workspace, is the whole category.

What has to be inside the boundary

Five things, and the value is in their sharing one boundary rather than in any of them individually.

PartWhat it means in practice
A disposable workspaceThe code is copied in, along with everything it pulls. No host directory is mounted read-write into the agent's reach, so there is no path from a bad edit to your working tree.
A sandboxed agentClaude Code or Codex, its child processes, its MCP servers, its package managers, builds, tests and dev server, all under the same policy. A runaway agent stays inside.
A credential and network brokerNo SSH key, GitHub token, model API key, cloud credential or personal browser profile goes in. A host-side proxy authenticates the calls the policy allows; egress is an allowlist.
A browser, with two interfacesChrome and a fresh profile live inside. The agent drives it; a human can watch the same viewport and take the controls. The host browser never connects to the app under test.
An output gateA patch, a report and an execution receipt, after inspection. The agent has no direct write path to the host.

Why each of the obvious alternatives falls short

Every team reaching for this arrives having already tried one of three things, and each fails in a different place.

A git worktree isolates the checkout and nothing else. The agent still runs with your filesystem, your network and your credentials, and its branch merges like any other. A worktree answers "where do the edits go?" and has nothing to say about "what else can this process touch?"

A container you exec into isolates the process and usually stops there. The dev server ends up on the host or on a published port, the credentials get passed in as environment variables because that was easiest, and the record of what happened is whatever the agent wrote in the chat transcript. It contains the process without containing the workflow.

A permission prompt is not a boundary at all. It asks a human to approve a tool call, which is a useful workflow control and depends entirely on a person catching the right moment. Once a command is approved, or once untrusted text has steered the agent toward approvable-looking commands, the prompt has nothing left to enforce.

Everything rests on the output gate

If you take one structural idea from the category, take this one: the environment has no write path to the host, and getting work out is a step a human performs.

That single constraint is what makes the rest coherent. Because there is no automatic path out, there is no need to decide which automatic paths are safe. Because export is explicit, it has somewhere to put the things a reviewer should see before deciding: the path-validated patch, a report whose first section is every destination the boundary refused, and a receipt of every observed execution stamped with the digest of the policy that was in force.

An environment with an automatic write-back is a different category with a different name. It is a build system.

What it is not

  • Not a provenance system. The question is what the code can reach and what it did, not who wrote which line.
  • Not a defence against a targeted kernel exploit, unless the tier is a microVM with its own kernel. Shared-kernel containment is strong against a runaway agent and careless dependency code, and that is a different claim.
  • Not a control on what the agent tells the model. Containment stops the agent touching your machine. It does not stop it putting private source in a prompt, and any tool implying otherwise is overselling.
  • Not a review. A clean report and a correct patch are unrelated properties.

How to tell a real one from a label

The category is new enough that the phrase will get attached to things that are not it. Four questions separate them, and all four have short answers:

  1. Where does the dev server run? If it runs on the host, or on a published port, the boundary has a hole shaped exactly like the thing you were testing.
  2. What happens when the host cannot enforce the requested boundary? The only acceptable answer is that it refuses. A silent downgrade produces a false claim you will later rely on, which is worse than no sandbox.
  3. Who wrote the record of what happened? If the log is the agent's account of itself, it is testimony. Ask which parts were observed from outside.
  4. How does work get out? If the answer is "it commits for you", the gate is not a gate.

FAQ

What is a contained agentic development environment?

A disposable environment that holds the code, the coding agent, the toolchain, the dependencies, the dev server and a browser inside one enforced boundary, with nothing of the host machine inside it and one deliberate, human-operated exit that produces a patch, a report and a record of what ran.

How is it different from running an agent in a container?

Scope. A container isolates the process; the category isolates the whole workflow. In practice the difference shows up in three places: the dev server runs inside rather than on a published host port, the credentials never enter at all rather than being passed as environment variables, and there is no automatic write path back to the host.

Is a git worktree enough?

No. A worktree isolates the checkout, not the process. The agent still runs with your filesystem access, your network and your credentials. A worktree answers where the edits go and says nothing about what else the process can touch.

Does containment stop the agent leaking my code?

Not to the model. Containment stops the agent touching your machine and stops it reaching hosts outside the egress allowlist. It does not stop it putting private source into a model prompt, which needs a separate control: a self-hosted model, or no model egress at all.

What should the environment do if the host cannot enforce the boundary I asked for?

Refuse. A sandbox that silently downgrades produces a security claim the run never had, which is worse than no sandbox, because the record then attests to a boundary that was not there. h5i fails closed on an explicit tier and probes functionally rather than trusting capability bits.
