Git worktrees vs h5i boxes

Both give an agent its own directory to work in. That is where the similarity stops, and the difference is not one of degree: they are solving different problems that happen to look the same from the file manager.

By Koukyosyumei Reading time 7 min Tags Comparison · Worktrees · Containment
The verdict. A git worktree separates checkouts, so two agents editing the same repository do not trample each other. An h5i box separates authority, so a process cannot read what it was not granted, reach a host that was not allowlisted, or write anything on your machine. Use a worktree for parallelism with code you trust. Use a box when the answer to "what else could this process touch?" matters.

Worktrees deserve their reputation. git worktree add ../feature-x feature-x is one command, needs nothing installed, costs almost nothing, and solves a real problem cleanly: two pieces of work on one repository without a stash-and-switch dance.

When agents arrived, worktrees were the obvious first answer, and for a lot of use they are still the right one. The failure is specific rather than general, so it is worth being precise about where it starts.

What a worktree isolates, exactly

A worktree gives you a separate working directory, index and HEAD, sharing the object store. That is a complete list. It is a statement about where files live.

It says nothing about the process that edits them. An agent running in a worktree has your user's filesystem access, your network, your environment variables, your SSH agent and your cloud credentials. It can cd anywhere. It can read ~/.aws. A postinstall script in a dependency it just added runs with all of that.

And the branch merges like any other branch. There is no gate between "the agent finished" and "this is in main" other than the one you remember to apply.

The relationship is layered, not opposed

A box created from your repository is a real git worktree on its own branch, sharing the object store, which is what lets h5i box apply land the work back locally. The worktree is the substrate; the policy is what is added.

Code from outside gets a different shape, and the difference is worth knowing before you need it. A box created from a URL, a pull request or --new is detached: it gets a repository of its own, your repository is neither read nor written after creation, and the inherited origin remote is dropped so it arrives holding no network handle. apply and rebase refuse there and point at export.

That distinction has no worktree equivalent, because a worktree is definitionally part of your repository.

When a worktree is the right call

Often, and saying so is not a hedge:

  • Your own code, your own agent, a task you are watching. The threat model is a mess, not an adversary, and a worktree contains a mess perfectly well.
  • Parallel edits where the only conflict is the working tree. This is what the feature was built for.
  • A host that cannot enforce anything better. h5i's workspace tier is exactly a worktree with no confinement, and it is labelled that way rather than dressed up. The console greys it out to say the evidence is weak.

When it quietly stops being enough

The line is not "when the code is malicious", because almost nobody thinks their code is malicious. It is earlier than that:

  • The moment you install dependencies you did not audit. A lockfile is a hyperlink to code nobody in the review read, and its install scripts run as you.
  • The moment the agent reads text you did not write. A README, an issue comment, a fetched page. A worktree has nothing to say about a prompt-injected agent, because the injection does not need to escape a directory.
  • The moment you stop watching. The whole value of an agent is that you are doing something else, and that is exactly when "I would have noticed" stops being true.
  • The moment the code came from someone else. A pull request from a stranger in a worktree is that stranger's code with your credentials.

The thirty-second version

Ask what happens if the process in that directory does something you did not intend. If the answer is "I get a messy diff", a worktree is correct and a box is overhead. If the answer involves your credentials, your network, or the rest of your filesystem, the directory was never the boundary you needed.

FAQ

Is a git worktree a sandbox?

No. A worktree gives you a separate working directory, index and HEAD, sharing the object store. That is a statement about where files live. The process still runs with your user's filesystem access, your network, your environment and your credentials.

Does an h5i box replace worktrees?

No, it builds on them. A box created from your own repository is a real git worktree on its own branch sharing the object store, which is what lets h5i box apply land the work back locally. The worktree is the substrate; the enforced policy is what is added on top.

When is a worktree still the right choice?

When it is your own code, your own agent, and a task you are watching, where the threat model is a mess rather than an adversary. Also when the host cannot enforce anything stronger, which h5i models honestly as the workspace tier and greys out in the console to say the evidence is weak.

What is a detached box?

A box created from a URL, a pull request or --new. It gets a repository of its own, your repository is neither read nor written after creation, and the inherited origin remote is dropped so the box arrives holding no network handle. apply and rebase refuse there and point at export.
