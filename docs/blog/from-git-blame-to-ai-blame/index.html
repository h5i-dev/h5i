We built AI blame, then deleted it

For a while h5i could tell you which model wrote a line, from which prompt, and whether the tests passed when it landed. It worked. We cut it anyway, and the reason is more interesting than the feature was.

By Koukyosyumei Reading time 8 min Tags Retrospective · Provenance · Design
What happened. h5i began as a provenance system: git notes carrying the prompt, the model and the agent per commit, a blame overlay that annotated each line with them, an audit pass, and a multi-agent orchestra on top. All of it is gone. What replaced it is containment plus an execution receipt, and the short version of why is that who wrote this line turned out to be a question people ask when they cannot ask what did this process do.

The pitch was clean, which should have been a warning. git blame gives you a name and a date. For a line a model wrote, you want the prompt, the model, the agent and the test result. So we recorded those at commit time, keyed by commit, and taught blame to show them. It worked, and there is a version of this post that is a happy feature announcement.

Here is what went wrong with it instead.

Problem one: the data was only as honest as the recorder

Every field came from the agent's own session. The prompt was what the agent reported as the prompt. The test result was what the agent reported as the test result. The model was whatever the runtime said. None of it was observed from outside the process being described.

That is fine when the agent is cooperative and useless exactly when it is not, which is the case the feature existed for. A provenance record generated by the subject is a record of what the subject chose to say. We had built a system for annotating trustworthy work with trustworthy metadata, which is a real thing to want and not a security property.

Problem two: attribution answers the wrong question

Think about when you reach for git blame. Something is broken and you want the context that explains it. The name and date are a proxy: you are really trying to find a person who remembers, or a commit message that explains, or a ticket that motivated it.

For agent-written code we assumed the same shape held, so we filled in a richer proxy: the prompt instead of the name. But the prompt turns out to be a poor explanation of a change. It is upstream of a long chain of model decisions, and knowing that someone typed "add exponential backoff" tells you almost nothing about why the code looks the way it does or whether it was exercised.

Meanwhile the questions people actually had in front of an agent's branch were about execution. Did the tests run, or were they written and never invoked? What did the install step reach for? Was anything refused? Not one of those is a per-line question, and none of them is answerable from a commit annotation.

Problem three: the feature's cost was structural

Per-line provenance needs the metadata to survive every operation that rewrites history, and git has many. Rebase, squash, cherry-pick, filter-branch. Each one either carries the notes forward correctly or silently drops them, and "silently drops them" is the default. We spent a lot of engineering on making annotations survive, which is engineering spent on the durability of data whose accuracy problem from section one we had not solved.

There is a general lesson in that ordering. Making unreliable data durable is a way of converting a small problem into a large one.

What replaced it

The receipt is deliberately narrower, and each of the differences is a direct response to something above.

AI blameThe receipt
Recorded by the agent, about itself.Generated from observation. Exits from the supervisor's wait4, egress from the allowlist proxy's log.
Attached to commits, so it lived and died with history rewriting.Attached to a box, append-only, and never rewritten by anything.
Answered "who wrote this line?"Answers "what ran, with what exit code, and what did a boundary refuse?"
All fields equally trustworthy on the page.Every record labelled with the lane that observed it, so host-observed and box-claimed never blur.
Could be omitted by an uncooperative agent, invisibly.Can be omitted, and the omission is visible as a gap against host-observed exits.

The receipt also sits somewhere the subject cannot reach. A box's write window under its own directory is exactly its spool; the receipt log is a sibling of that spool, outside every grant. The box stages a record and the host ingests it. That structural detail is the whole difference between a log and evidence, and it was not available to a design that wrote its records into git refs the agent could touch.

What we gave up, honestly

Cutting a feature always loses something real, and pretending otherwise is how retrospectives become marketing.

  • There is no longer a per-line answer. If you want to know which model touched a specific function six months later, h5i will not tell you. That is a genuine capability, gone.
  • Intent is no longer recorded at all. The receipt says what ran, not why anybody wanted it. The commit message is back to being the only place intent lives, exactly as before.
  • Nothing accumulates across commits. A box's record is about a box. There is no longitudinal view of a repository's AI history, because the thing that produced one was the part we could not make trustworthy.

The trade we took: a narrower claim that holds against an uncooperative subject, over a broader claim that only held when nobody was trying. If your agents are cooperative and you want rich annotation, the old design was better and you should build it. If you are containing code you have reason to doubt, annotation was never going to be the thing.

FAQ

Does h5i still have AI blame or per-commit provenance?

No. The git-notes provenance, the blame overlay, the audit pass and the multi-agent orchestra were all removed. What remains is containment and the execution receipt: what ran inside a box, with what exit code, observed by whom, and which destinations the egress allowlist refused.

Why was per-line AI attribution the wrong question?

Because the questions people had in front of an agent's branch were about execution, not authorship. Did the tests actually run? What did the install step reach for? Was anything refused? None of those is a per-line question, and none is answerable from a commit annotation.

What made the old provenance data untrustworthy?

It came from the agent's own session. The prompt was what the agent reported as the prompt; the test result was what the agent reported as the test result. Nothing was observed from outside the process being described, which is fine for cooperative work and useless for the case the feature existed for.

What did the pivot give up?

Three real things: there is no per-line answer any more, intent is no longer recorded at all, and nothing accumulates across commits into a longitudinal view of a repository. The trade was a narrower claim that holds against an uncooperative subject, over a broader claim that only held when nobody was trying.
