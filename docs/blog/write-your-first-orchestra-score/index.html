Write your first box profile

Built up one field at a time, with the failure each field prevents. Everything is fail-closed, so the fastest way to learn the file is to start from nothing and add the grant each error asks for.

By Koukyosyumei Reading time 9 min Tags Tutorial · Policy · Configuration
Where this goes. .h5i/env.toml, checked in, at the repository root. It is versioned with the code it governs, hashed into every box's manifest, and read at creation. Four built-in profiles need no file at all, so start by checking whether default, agent, agent-claude/agent-codex or browser already does what you want.

The fastest way to understand this file is to build one from nothing and let it fail. Every list is fail-closed, so an unset field grants nothing and the error tells you which grant is missing. That is a much better teacher than a reference table.

The target: a Node project whose agent needs to install dependencies, run tests, start a dev server, and point a browser at it.

Step 1: a name and a tier

.h5i/env.toml
[profile.web]
isolation = "supervised"

Five tiers are available: workspace, process, supervised, container and microvm. Omit the field and you get auto, which picks the strongest tier this host can actually run.

Name one and it fails closed instead of downgrading. That is the behaviour you want in a checked-in file: a profile that quietly ran with less confinement on a colleague's laptop would put a claim in the record that the run never had. Run h5i box probe to see what this host can satisfy before you commit a tier.

supervised here because we want a real egress allowlist, which is the first thing that will bite.

Step 2: the filesystem grants

.h5i/env.toml
[profile.web.fs]
read  = ["~/.npm"]     # the npm cache, read-only
write = []             # $WORK is already writable; nothing else needs to be

$WORK is writable already, so write stays empty and should stay empty most of the time. Every entry you add there is a path a confused or injected agent can modify.

There is also a deny list, and one lint about it worth internalising now: a denied path may not sit under a granted one. Landlock is allowlist-only and cannot subtract a child from a granted parent, so h5i refuses the profile rather than accepting a rule it cannot enforce. The fix is always to narrow the grant, never to add a deny.

Step 3: the egress allowlist, and the lint that catches you

.h5i/env.toml
[profile.web.net]
mode   = "deny"
egress = ["registry.npmjs.org"]   # a non-empty allowlist supersedes `mode`

Try this with isolation = "process" and h5i refuses the profile. The process tier's network namespace is all-or-nothing: it can give you deny or host and cannot honour a domain allowlist, so accepting the field would write a claim into the manifest that nothing enforces.

That refusal is the most useful error in the file. It is the difference between a tool that helps you write a policy and one that helps you write a policy you believe in.

Which tier you pick decides what the allowlist means. supervised enforces at L3/L4 with default-drop nftables in a private netns and DNS pinned by a hosts file. container enforces at L7 with a CONNECT proxy, which binds proxy-respecting tooling and nothing else. microvm evaluates it in the guest's own network stack.

Step 4: the dev server

.h5i/env.toml
[service.web]
command = "npm run dev"
port    = 3000

Services are declared at the top level rather than inside a profile, and driven with h5i box service start, service status, service logs and h5i box ports for the per-box port map.

One caveat, stated plainly because it will otherwise confuse you: services are supported at the workspace and process tiers in v1. At supervised and container the network namespace belongs to a single session, so run the dev server inside the same h5i box shell as everything else. If your workflow needs long-lived declared services, that is a reason to pick process.

Step 5: resource limits

.h5i/env.toml
[profile.web.resources]
mem   = "4G"
procs = 256
wall  = "30m"

wall is enforced everywhere and is the one that saves you: a confined command can never run unbounded, and there is a default if you set none.

mem and procs are not enforced at the kernel tiers on macOS. Darwin has no cgroups, does not enforce RLIMIT_AS against the mmap'd heap every modern runtime uses, and scopes RLIMIT_NPROC to the whole user rather than to one box, so applying it would cap your machine. h5i declines to apply a limit it cannot hold, and h5i box status marks the value with * and says so. Use container or microvm where you need a real ceiling.

Step 6: let the browser in

On Linux the box has its own network namespace and its loopback is private, so nothing more is needed. On macOS the box shares the host's loopback, so h5i denies outbound to it wholesale, otherwise a box could reach a database or a dev server belonging to your machine.

.h5i/env.toml (macOS)
[profile.web.net]
loopback = [3000]      # exactly this port; everything else on loopback stays denied

An undeclared port fails with net::ERR_ACCESS_DENIED inside Chrome, which reads like a page problem and is a policy one. The port a declared [service] is running on is granted automatically while that service is alive, so this is only needed for a server you started by hand.

The finished profile

.h5i/env.toml
[profile.web]
isolation = "supervised"

[profile.web.fs]
read  = ["~/.npm"]
write = []

[profile.web.net]
mode   = "deny"
egress = ["registry.npmjs.org"]
unix   = false

[profile.web.resources]
mem   = "4G"
procs = 256
wall  = "30m"

[service.web]
command = "npm run dev"
port    = 3000
~/my-project
$ h5i box . --profile web
$ h5i box status <name>    # confirm what was actually enforced

Three things people get wrong first time

  • Adding to write to fix a permission error. Usually the tool wants a cache directory, which belongs in read. Check which before you widen the writable set.
  • Setting net.egress on the process tier. Refused, on purpose. Move to supervised or accept mode = "host" and know what you took.
  • Expecting unix = true to be the default. It is off, because SCM_RIGHTS passes file descriptors, which is authority smuggling. The browser profile sets it because the agent-browser daemon's control socket needs it.

FAQ

Where does the box profile live?

In .h5i/env.toml at the repository root, checked in and versioned with the code it governs. It is read at box creation, resolved against the host, serialized to policy.resolved.toml and hashed before any state is created on disk.

Why does h5i refuse a net.egress allowlist on the process tier?

Because the process tier's network namespace is all-or-nothing: it can offer deny or host and cannot honour a domain allowlist. Accepting the field would put a claim in the manifest that nothing enforces, so h5i refuses the profile and tells you to move to supervised, container or microvm.

Can I run a declared dev server at any tier?

Not in v1. Services are supported at the workspace and process tiers. At supervised and container the network namespace belongs to a single session, so run the dev server inside the same h5i box shell as everything else.

Why can a denied path not sit under a granted one?

Because Landlock is allowlist-only and cannot subtract a child from a granted parent, so the deny rule would not be enforced. h5i refuses the profile rather than accepting a rule it cannot hold, and the fix is always to narrow the grant.
