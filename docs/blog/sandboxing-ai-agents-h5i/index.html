Sandboxing AI Agents, Part 4: h5i's tier ladder and policy model

h5i's sandbox is not one box. It is a five-rung ladder, from a bare worktree to a guest with its own kernel, that lets you match confinement to how much you trust the run and to what the host can actually enforce. Every rung is fail-closed, and every run lands in a receipt the box cannot edit.

By Koukyosyumei Reading time 16 min Tags h5i box · Isolation tiers · Policy · Egress
The short version. h5i resolves a declared policy against the host and either enforces it or refuses. There are five tiers: workspace, process, supervised, container and microvm. Three of them can hold a domain egress allowlist, and they hold it at different layers, which is a difference in the claim and not a difference in the wording. The whole policy is one checked-in .h5i/env.toml, hashed at creation, and that hash is stamped on every receipt record the box produces.

An AI agent that can edit your tree and run shell commands is, for the length of a task, a process executing instructions you did not write and cannot predict. Those instructions can be redirected by a poisoned dependency, a hostile file in the repository, or a prompt-injected web page. The usual reflexes answer half the question each. "Run it in a container" applies one fixed boundary to every run regardless of trust. "Review the diff afterwards" tells you what changed in the files and nothing about what the process reached for: which paths it read, which hosts it tried to call, which limits it hit. The design question is not whether it is in a box. It is whether the box is matched to how much you trust this run, whether this host can actually enforce that box, and whether what happened is written down somewhere the box cannot reach.

What you already know, and what h5i adds

If you have sandboxed a build before, the primitives are familiar: namespaces, Landlock and seccomp on Linux, Seatbelt on macOS, cgroups and rlimits, rootless containers, an egress proxy. h5i invents no kernel mechanism. What it adds is the part usually left to a pile of shell scripts and tribal knowledge: one declared policy that selects among those mechanisms, a resolver that refuses a claim the host cannot meet, and a binding from the enforced policy to a record a reviewer can read. The discipline is the product, not the syscalls.

The tier ladder

h5i does not pretend every host supports every boundary, and it does not pretend every run needs the strongest one. Each rung adds enforcement and adds host requirements. Each is fail-closed, so a run that asks for more than the host can deliver is refused rather than weakened.

TierFilesystemNetworkEnforced byHost requirement
workspace A worktree on the host filesystem, no confinement The host's Worktree separation only None
process Landlock allowlist on Linux, a Seatbelt profile on macOS: $WORK writable, selected paths read-only, home excluded by default deny or host. No domain allowlist Landlock, a seccomp deny-list and namespaces, or Seatbelt; a supervisor and a private pid namespace; cgroup v2 or rlimits Landlock-capable kernel, unprivileged user namespaces and seccomp, or macOS Seatbelt
supervised Same as process deny, host, or an L3/L4 allowlist The process stack plus a private netns, an nftables allowlist pinned to resolved IPs, DNS pinned by a hosts file, and a seccomp-notify gate on socket() Process-tier requirements plus rootless nftables and slirp4netns
container A portable image: read-only rootfs, private /tmp, $WORK bind-mounted read-write deny, host, or an L7 proxy allowlist Rootless Podman: capabilities dropped, no new privileges, no docker socket, host-side CONNECT proxy Rootless Podman and a container.image
microvm The same OCI images, inside a guest Default-deny plus one address rule per destination, L3/L4 in the guest's netstack microsandbox (msb): a hardware-isolated guest with its own kernel msb 0.6+, host virtualization, and a pre-pulled image

Read the ladder by trust. workspace is for a run you already trust, where all you want is parallel-edit separation. process is the everyday default for agent build and test work: it keeps a confused or prompt-injected command away from your home directory and the network without a container's weight. supervised is for a run that legitimately needs the network but only to named hosts, enforced at the packet layer. container is for a run that needs a packaged toolchain, and it trades the L3/L4 claim for portability. microvm is for the case where the workload itself might be an adversary.

auto is the default and picks the strongest tier this host can run. An explicit tier never downgrades.

Ask the host first

Because the ladder is host-dependent, h5i ships a probe. It does not stop at checking that the kernel bits exist. The Landlock, seccomp and userns features can all be present while a hardened kernel or an AppArmor profile still denies exec under the full stack, so the probe runs a functional self-test before it reports a tier as runnable.

h5i box probe
$ h5i box probe
── Host isolation capabilities ──
  os           = linux
  mechanism    = landlock+seccomp
  landlock_abi = 3
  userns       = true
  seccomp      = true
  tty-injection= blocked at the kernel tiers, possible at isolation=workspace
  container    = podman
  microvm      = none

  claim workspace  satisfiable = yes
  claim process    satisfiable = yes
  claim container  satisfiable = yes (needs rootless Podman + profile container.image)
  claim microvm    satisfiable = no (needs microsandbox `msb` + host virtualization + profile container.image)
  process tier runnable = yes

Two lines there repay a second look. microvm reports which of its three prerequisites is missing, because installing a package and enabling nested virtualization are different problems and a single "no" would hide which one you have.

And tty-injection is h5i measuring something it declines to assert. An interactive h5i box shell hands the box the terminal you launched it from, which is what makes job control and every TUI work, and a terminal is a two-way device. Whether a box can push characters into that terminal's input queue is not h5i's call: on Linux it is your kernel's dev.tty.legacy_tiocsti setting, the same at every tier, and upstream defaults it open. On macOS it is the Seatbelt profile that subtracts the ioctl, so it holds at the kernel tiers and not at isolation=workspace. So the probe measures it, prints one of three verdicts, and tells you how to close it when anything is open.

When a requested claim is not satisfiable, creation fails with the specific reason. Refusing is the point. A sandbox that downgrades itself silently is worse than no sandbox, because the policy digest would then attest to a boundary the run never had.

The policy model: one checked-in file

A profile is a small versioned TOML block in .h5i/env.toml. It is the single place that selects a tier and declares the filesystem, network, resource, environment and secret surface for a run. Four built-ins need no file at all: default for build and test work, the agent family for an agent in the box, and browser for the agent profile plus headless Chrome. Everything is fail-closed: an unset list grants nothing.

.h5i/env.toml
# Checked in, versioned, and hashed into the box's manifest.
[profile.ci]
isolation = "supervised"          # workspace | process | supervised | container | microvm

[profile.ci.fs]
read  = ["~/.cargo", "~/.rustup"] # extra read-only grants ($WORK is already writable)
write = []                        # extra writable paths beyond $WORK
deny  = []                        # lint: a denied path may not sit under a grant

[profile.ci.net]
mode   = "deny"                   # deny (no network) | host
egress = ["crates.io", "static.crates.io", "github.com:443"]
                                  # a non-empty allowlist supersedes `mode`: only these
                                  # hosts, enforced at L3/L4 here (supervised)
unix   = false                    # AF_UNIX sockets, off by default

[profile.ci.resources]
mem   = "2G"
procs = 256
wall  = "10m"

The lints are where this earns its keep. h5i refuses a profile that sets net.egress below the supervised tier, because the process tier's network namespace is all-or-nothing: it can offer deny or host and cannot honour a domain allowlist, and accepting the field anyway would put a lie in the manifest. It likewise refuses a granted path that contains a denied child, because Landlock is allowlist-only and cannot subtract a child from a granted parent. The fix is to narrow the grant, not to hope a deny rule catches it.

Resource limits get the same treatment. wall is enforced everywhere, but mem and procs are not enforced at the kernel tiers on macOS: Darwin has no cgroups, does not enforce RLIMIT_AS against the mmap'd heap every modern runtime uses, and scopes RLIMIT_NPROC to the whole user rather than to one box, so applying it would cap your machine instead. h5i declines to apply a limit it cannot hold. h5i box status marks such a value with * and says so underneath rather than listing it as enforced.

Secrets are brokered rather than passed through. A grant names a secret and how to source it (env:VAR, file:/abs/path, or a host-side command: extractor, which is gated off by default because it runs arbitrary host code) and how to inject it. The value never appears in the policy, the digest, or any receipt. h5i box secrets dry-runs the resolution and reports a fingerprint, never a value, so a reviewer can see that a secret was involved without seeing it.

The agent profiles are runtime-scoped: agent-claude grants only Claude's own HOME state and Anthropic egress, agent-codex only Codex's state and OpenAI egress. A Claude box cannot read Codex's credentials or reach the other vendor's API. That is not tidiness. It stops a prompt-injected agent from laundering one runtime's authority through another against a host the allowlist already permits.

Three egress mechanisms, three honest claims

The network is where the tiers differ most, and where the difference decides your threat model.

supervised enforces at L3/L4. It runs the workload in a private network namespace with a user-space uplink, installs a default-drop nftables ruleset, resolves the allowlisted hosts once and pins them through a private hosts file, and opens no general DNS path. The remaining escape would be policy mutation, so the seccomp-notify gate on socket() denies AF_NETLINK along with raw and packet sockets. nft and ip cannot open the control channel they would need.

supervised egress behaviour
curl https://crates.io           # allowed: crates.io is in net.egress
curl https://example.invalid     # blocked: not in the pinned hosts file, no DNS route
curl https://1.1.1.1             # blocked: nftables default-drop at L3/L4
nft flush ruleset                # blocked: AF_NETLINK denied by the seccomp gate

container enforces at L7. A non-empty net.egress spawns a host-side DNS-pinned CONNECT proxy and points the container at it. That gates proxy-respecting tooling cleanly and cannot stop a process that ignores the proxy environment and opens a raw socket to whatever IP the rootless NAT permits. Two drafts of the design got this backwards, so it is worth saying flatly: the container tier buys portability, not tighter network control.

microvm turns the allowlist into default-deny plus one address rule per allowed destination, evaluated by the guest's own network stack, so a raw socket to an unlisted IP is dropped rather than merely un-proxied. It pays for that with thinner evidence. The container tier's proxy sees every CONNECT and records allow and deny counts; a netstack filter drops packets without reporting them, so a microvm receipt carries no egress summary. Stronger enforcement, less to read afterwards. It also refuses a profile that declares [[profile.X.auth]] grants, because those hand the box a base URL on the host's loopback and a guest cannot dial that.

The receipt is a sibling of the spool, not a file in it

Confinement decides what the code can do. The receipt says what it did, and the interesting design question is why the box cannot rewrite it.

Each box keeps one append-only JSONL log plus the raw payload of every record. The box's entire write window under its own directory is <box>/spool. The receipt log and the stored payloads are siblings of that spool, outside every grant the policy hands out. The box stages a record and the host ingests it. There is no path from inside to a record the host has already written. Secrets are scrubbed from the command and the payload before either is written, and the scrub is recorded by rule id rather than by value.

Every record carries the lane that observed it, so host-observed evidence and box-claimed evidence never blur: host-env-run is h5i itself, with exits and resource usage from the supervisor's wait4 and egress from the allowlist proxy's own log; viewer is h5i's viewer forward; tee-shim and inbox-capture are the box's own account of itself.

h5i ui draws that as one screen across five lanes: filesystem, network, process, resources and page. The colours are deliberately narrow. Red makes exactly one claim about the boundary, that the egress allowlist refused a destination and the proxy observed it. Amber is something to look at, a non-zero exit or a wall-clock kill or browser errors, and says nothing about containment. Grey means the evidence is weak, either because the tier was workspace and nothing was confined or because every receipt came from the in-box shim. Nothing on the screen is a score.

The honest ceiling

Four of the five tiers share the host kernel. They are strong against accidental damage, against many prompt-injection effects, against ordinary untrusted build scripts, and against casual exfiltration. A binary with a working host-kernel exploit is outside their claim, and microvm is the tier where that changes: a kernel exploit inside the box meets the hypervisor rather than the kernel it just subverted.

No tier makes a careless policy safe. A profile that grants a credential and permits egress to a general-purpose endpoint has opened a channel by hand. And containment does not stop the agent putting your private source in a model prompt; that is a separate control, and h5i says so rather than implying otherwise.

The ceiling is the shared kernel, until you leave it. The process, supervised and rootless-container tiers are strong local containment and not a substitute for separate-kernel isolation when the workload itself is a determined adversary. That is what microvm is for, and it needs a host with virtualization to give it to you.

A ladder, not a box

h5i exposes five tiers instead of one because trust is not constant across agent runs and what a host can enforce is not constant across machines. A single fixed box forces you either to over-confine routine work or to under-confine the run that finally reaches the open internet. A ladder lets the policy say how much authority a run should have, lets the resolver refuse whatever the host cannot deliver, and lets the manifest record which boundary actually applied.

That last clause is what separates running an agent in a container from running agent work in a box. The container may well be isolated; you still take its isolation on faith and reconstruct what happened from logs it could have written. A box binds the enforced policy to a sealed record, so "what was this process allowed to do, and what did it try?" has an answer you did not have to trust it for.

Frequently asked questions

Which tier should I use by default?

Leave it on auto, which picks the strongest tier this host can run. When you want to be explicit: process for everyday agent build and test work, supervised when the run needs specific hosts enforced at the packet layer, container when it needs a packaged image, and microvm when the code itself is the threat. Run h5i box probe to see which are satisfiable on your machine.

Can the process tier restrict the network to specific domains?

No. The process tier offers net.mode = deny or host and nothing between them, because its network namespace is all-or-nothing. A net.egress allowlist needs supervised, container or microvm, and h5i refuses a profile that sets it below supervised rather than silently ignoring the field.

Is the container tier's egress allowlist airtight?

It is honest L7 scoping. The host-side CONNECT proxy gates proxy-respecting tooling, and a process that ignores the proxy environment and opens a raw socket reaches any IP the rootless NAT permits. Use supervised or microvm for packet-level enforcement.

Is an h5i box as safe as a VM?

At microvm it is one: microsandbox boots a guest with its own kernel. At the other four tiers, no, because they share the host kernel. They are designed for a runaway agent, prompt-injection effects and ordinary untrusted build scripts, not for a determined adversary's binary.

What does macOS lose compared to Linux?

Two things, both measured rather than assumed. There is no syscall filter, because Darwin has no seccomp equivalent, and there is no memory or process-count cap at the kernel tiers, for the cgroups and rlimit reasons above. Seatbelt is default-deny across filesystem, network, mach and sysctl in one policy, and unlike Landlock it can subtract a child from a granted parent. h5i box probe names the mechanism and the gaps.
