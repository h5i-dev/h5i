What a box copies from your Claude Code config, and what it strips

Your agent keeps its settings, its session history and its credentials in one directory, because that was convenient. A box has to take the first, can skip the second, and must not take the third.

By Koukyosyumei Reading time 7 min Tags Reference · Credentials · Configuration
The rule. A box gets its own writable copy of the agent's HOME state, seeded once from the real one and never written back. The default is copy: two lists subtract from it. Known-large session and transcript trees are pruned for size, and credential-shaped entries are dropped by shape at any depth, including anything ending .pem, .key, .p12, _rsa or _ed25519. Copy-by-default matters: a new credential file the runtime invents is seeded rather than silently dropped, and caught by shape rather than by a stale name list.

An agent in an empty box is useless. It has none of your settings, none of your project config, none of the preferences that make it behave the way you expect. So a box has to bring some of your agent's HOME in with it.

That directory is also where the runtime keeps its API token, and where a dozen other tools have helpfully dropped credentials over the years because it was a convenient place to put them. So "bring the HOME in" is not one decision. It is a filter, and the filter's defaults decide what a compromised box gets to steal.

Copy, do not mount

The first decision is that the box gets a copy, seeded once, never written back.

Bind-mounting the real directory would be simpler and it puts your live agent config in a writable path inside a box you may not trust. It also means two boxes running at once are racing each other's session state. A per-box copy removes both problems: the real HOME is only ever read, and each box scribbles in its own.

The size list: what gets pruned and why it is not security

Some of what lives in an agent's config directory is enormous and useless to a fresh box. Conversation transcripts (projects/ for Claude, sessions/ for Codex), per-session todo lists, feature-flag caches, shell-environment snapshots, edit-history backups, REPL history, host logs and plugin temp caches.

Pruning these is a size decision that happens to be strictly more private, since less host data goes in. It is matched by exact name at the seed root only, and it is explicitly not the security control. That is the next list.

The credential list: by shape, at any depth

This one is the security decision, and it is matched by shape rather than by location, because a key does not become safe by being in an unexpected folder.

CategoryDropped
Cloud and VCS credentialscredentials, credentials.json, credentials.toml, .netrc, netrc, gh_token, github_token
SSH materialid_rsa, id_ed25519, id_ecdsa, known_hosts
Generic secret stores.env, secrets.json, secrets.toml, keyring
By extension, anywhereanything ending .pem, .key, .p12, _rsa, _ed25519

The extension rules do most of the work. A name list catches what somebody thought of; a suffix rule catches deploy-prod_ed25519 and acme-staging.pem, which nobody put on a list.

Copy-by-default is the interesting choice

The filter could have been built the other way round: an allowlist of files known to be safe. That sounds more cautious and is worse here.

Agent runtimes add files constantly. Under an allowlist, every new settings file the runtime invents is silently missing from the box, and the agent misbehaves in a way that looks like a bug in your project. Under copy-by-default with a shape-based subtraction, a new settings file is seeded automatically and a new credential file is caught by its shape.

The failure directions are different, and that is the whole argument. An allowlist fails toward broken agents, which people fix by widening it until it is not a list. A shape-based deny fails toward a caught credential, and when it misses, it misses one file rather than the category.

The one credential that stays, and why

The runtime's own API token is deliberately not dropped. The agent cannot function without it, and the profile already scopes egress to that runtime's API, so the token can only be spent where it was always going to be spent.

That trade is why runtime scoping is not cosmetic. agent-claude grants Claude's own HOME state and Anthropic egress; agent-codex grants Codex's state and OpenAI egress. If a box got both, a prompt-injected Claude session could read the other runtime's token and spend it against a host the allowlist already permits, which is exactly the laundering move the allowlist was meant to prevent.

Everything else authenticates through the host-side proxy instead, which never lets the credential into the box at all. A [[profile.X.auth]] grant names a host, a host-side credential environment variable, and the base-URL variable the client reads.

Limits worth knowing

  • Symlinks are not followed during the seed. A symlinked config directory does not arrive, which is occasionally surprising and is the safe direction.
  • The token really is in the box. Scoped, and there. A box that can reach the model API can send it your source code, and no filesystem policy touches that.
  • Shape matching is heuristic. A credential in a file named notes.txt is copied in. The auth proxy exists because file filtering is a floor, not a ceiling.
  • Nothing is written back. A setting the agent changes inside a box stays there. That is deliberate and it means in-box preference changes do not persist.

FAQ

Does a box get my Claude Code credentials?

It gets a filtered copy of your agent's HOME. Credential-shaped entries are dropped by shape at any depth: cloud and VCS credential files, SSH material, generic secret stores, and anything ending .pem, .key, .p12, _rsa or _ed25519. The runtime's own API token is kept, because the agent cannot function without it and the profile scopes egress to that runtime's API.

Why copy the config instead of mounting it?

Two reasons. A bind mount puts your live agent config in a writable path inside a box you may not trust, and two boxes running at once would race each other's session state. A per-box copy means the real HOME is only ever read and each box scribbles in its own.

Why is the filter a deny list rather than an allow list?

Because the two fail in different directions. An allowlist fails toward broken agents whenever the runtime adds a file, which people fix by widening it until it stops being a list. A shape-based deny fails toward a caught credential, and when it misses it misses one file rather than the category.

Do changes an agent makes to its config inside a box persist?

No. The seed is one-way: copied in once and never written back. An in-box preference change stays in that box and disappears with it.

Why do agent-claude and agent-codex exist as separate profiles?

So a box holds one runtime's credentials rather than both. If a box got both, a prompt-injected Claude session could read the other runtime's token and spend it against a host the allowlist already permits, which is exactly the laundering move the allowlist was meant to prevent.
