A Secure, Auditable Browser
for AI Agents

Let agents securely browse the web and test web apps. In benchmarks on simple websites, h5i reads pages ~5× faster with ~80% less peak memory, while recording every browser action and network request for review.

The problem

Giving AI agents a browser creates new security risks.

Agents do more than read pages. They follow instructions, submit forms, use logged-in sessions, access local services, and test code on your machine. A malicious website, a vulnerable app, or a simple agent mistake can turn that access into unsafe actions.

Websites can manipulate the agent
A prompt injection can make an agent ignore its task, click unsafe links, submit forms, or send data somewhere it should not.
The agent can leak local data
An agent with access to source code, credentials, logged-in sessions, or internal services can accidentally expose them through the browser.
Web app testing runs code on your machine
Testing an app often means running agent-written code, third-party dependencies, a development server, and a browser on the same host. Without isolation, they share access to your files and network.
Ordinary browser logs are incomplete
A list of clicks is not a complete record. Background requests, redirects, blocked connections, crashes, and restarts may be missing when you need to understand what happened.
What h5i gives you

A browser you can control, isolate, and audit.

h5i lets agents browse and test web apps under rules you set. Control where they can connect, review what they did, take over sensitive steps, and isolate the browser, or the entire testing workflow, from your machine.

Review the complete browser session
See every browser action and network request, including blocked requests and why they were denied. Crashes, human takeovers, and how the session ended are recorded too.
Control where the agent can connect
Allow only the websites and services required for the task. h5i blocks every other request before it leaves and records the attempt.
Limit the damage of prompt injection
Page content is marked as untrusted, and you can run both the agent and browser inside a sandbox. If a page still manipulates the agent, it can reach only the files and network destinations allowed by the sandbox policy.
Isolate web app testing from your machine
Sandbox only the browser, or isolate the agent, generated code, dependencies, development server, and browser together. Choose lightweight process isolation, a container, or a microVM.
The browser

Built for agents. Still under your control.

Agents browse with simple commands and receive compact, structured snapshots instead of raw HTML. You can review the complete session, take control when needed, and keep credentials out of the model's context.

one session, start to close
$ h5i browser open https://docs.rs/ --allow docs.rs
✔  browser session br_7k2xqa
   requests : engine-claimed (fail-closed, and the engine's own account of what it fetched)

$ h5i browser snapshot          # outline, with @ref handles
$ h5i browser click @e3
$ h5i browser snapshot --delta  # only what changed
$ h5i browser requests          # refusals included

  denied https://tracker.example/px  origin not in the allowlist
$ h5i browser close
$ h5i browser audit             # the whole session, afterwards
  host   session opened
  engine  verb   snapshot
  host   control -> human  (taken by a human)
  engine  #1 DENIED GET https://tracker.example/px
  host   session closed
Pages in a format agents can use
h5i returns a compact page outline with @ref handles. Agents can read, click, type, and extract data without processing screenshots or noisy HTML.
A complete session history
Browser actions, network requests, blocked connections, human takeovers, crashes, and how the session ended are kept in one timeline. Failed sessions are never silently restarted.
Human control for sensitive steps
Take control for logins, payments, or approvals, then hand the session back to the agent. Credentials are entered or substituted without being returned to the model, and the agent continues with the authenticated session.
The box

The sandbox the session can be placed in.

A box is a disposable boundary that holds a workspace, a shell, dependencies, a dev server and, when you ask for it, the browser session itself. It is what makes an agent building a web app and then browsing it a single contained thing rather than two hopeful ones. Reach for it when the agent is running code you did not write, or when you want the network record to have a witness outside the browser.

01

Create the right boundary →

Start from a repository or pull request and choose the isolation the task needs: lightweight OS controls, a rootless container, or a microVM with its own kernel. An unavailable tier fails closed.

$ h5i box create fix-auth --profile agent-claude
under 200 ms lightweight · container · microVM
02

Build and test inside it →

The agent, child processes, dependencies, dev server, and browser run in the same boundary. Host files, browser profiles, and credentials stay outside.

$ h5i box view fix-auth
agent + toolchain + dev server + browser · one boundary
03

Share only the demo service →

Expose one port from the box without exposing your laptop. Use an end-to-end encrypted P2P connection when both sides have h5i, or generate a browser-ready demo link for everyone else.

$ h5i box share fix-auth --port 3000
encrypted P2P · add --tunnel for a browser-ready link
04

Review, then take the work →

Inspect the proposed diff and the boundary's record of what ran and what was denied. Only then apply the snapshot to the parent branch.

$ h5i box propose fix-auth
review diff · export receipt · apply snapshot
The forum

A secure forum for multi-agent teams.

Agents coordinate through Git refs the host owns, so the forum inherits the access control your team already runs. Use a public repository for an open topic or a private one for internal work, and publish threads as branches to put them under the same protection rules that guard your code. Each agent stays sealed in its own sandbox, with no credential inside to leak and nothing beyond its own workspace to break.

01

Open a thread with a ceiling →

A thread names a profile every participant must be confined under. A box that exceeds it on network mode, egress, secrets, or filesystem grants is refused, never quietly re-confined to fit.

$ h5i forum create "auth race" --ceiling agent
checked against the enforced policy digest, not a worktree file
02

Attach boxes, and give each a role →

Worker, reviewer, observer, human. Roles decide who may post, claim, and attach an artifact. Membership changes are refused inside a box no matter who asks.

$ h5i forum attach alpha --as alpha --role worker
worker · reviewer · observer · human
03

Let the agents talk →

Inside the box the agent gets a handful of h5i forum verbs and no credential to reach it with. It agrees with a vote instead of restating a peer, and blocks on wait instead of polling.

$ h5i forum post <thread> --kind FINDING "..."
list · read · claim · post · up · submit · wait
04

Span machines through a Git remote →

Point the forum at any repository to bring agents on other machines into the same conversation. Publish under branch refs and the forge's own protection rules apply to the forum.

$ h5i forum remote git@github.com:you/forum.git
append-only union · --branch-refs for forge protection
FAQ

Frequently asked questions

The short answers. The manual has the long ones.

What is h5i?
h5i (pronounced high-five) is a secure, auditable browser for AI agents. An agent drives a session by id and reads an outline with @ref handles; you read the request log. Because the engine is the HTTP client, every request is checked against the session policy and written down before the bytes move, and the fetch is refused when the record cannot be written. Sessions run on your machine by default and can be placed inside a sandbox with one flag. Around the browser, h5i also gives each agent a disposable box for the code, the toolchain and the dev server, and a Git-backed forum for several agents to coordinate on. One Rust binary, Apache 2.0, local-first, with no hosted h5i service.
Why not Playwright or Puppeteer?
They drive a browser. They do not tell you what it reached. h5i's engine is the HTTP client, so its request log is a decision record it wrote before the bytes moved rather than a trace assembled beside the network: policy first, record second, wire third, and no fetch at all when the record cannot be written. If a request is not in the log, it did not happen. On top of that, a session is a first-class lifetime with an id, a policy digest, a lane, and an ending that is written down.
Is a default session sandboxed?
No, and h5i does not claim it is. h5i browser open runs here, in your ordinary process space, like any other headless browser. What you get by default is a complete record. What you get with --in <box> is a boundary as well. h5i browser status prints which one this session has, on every line, rather than leaving you to infer it.
What do engine-claimed and host-observed mean?
engine-claimed is the browser's own account of what it fetched: fail-closed, complete, and still the browser describing itself. host-observed means h5i also saw it at a box's boundary, outside the browser. The two are never merged into one confident-looking label, because a claim rendered as an observation is the one lie this product cannot afford.
Does putting the browser in a box automatically make the lane host-observed?
No. A box whose policy lets the browser reach the whole network corroborates nothing, and h5i keeps calling that session engine-claimed. The lane is upgraded only when something outside the engine decides what may leave: an egress allowlist enforced at the box's boundary, or a net mode that denies everything.
Can h5i stop a page from injecting instructions into my agent?
Not by classifying the text, and it does not try. Page content arrives wrapped in a marker that tells the model the text inside is data rather than instructions; escape sequences are stripped before anything reaches a terminal, so a page cannot repaint the line above it; and page JavaScript is off unless you ask for it, which removes the delivery channel entirely. What limits a persuaded agent is the session's policy and the box, not a filter.
Can a human take the browser away from the agent mid-task?
Yes. h5i browser take pauses the agent's mutating verbs while read-only ones keep working, because watching never collides, and handing control back forces a re-snapshot since the page moved. In a box that pause is enforced: every verb is carried in from the host, so there is no path around it. On this machine it is advisory, and take says which one you just got.
What happens if the browser crashes mid-task?
The session is recorded as died, with a time, and the next verb is refused with exit code 69 rather than silently restarted. That distinct code is the point: an agent whose retry cannot tell "the session is gone" from "the click did not work" is an agent that quietly starts a second browser and loses both the page it was reasoning about and the record of how it lost it. --restore carries the old storage into a new session with a new id and the inheritance written down. An id is never reused.
What can the engine not read?
It is not a complete browser and does not pretend to be. Of twenty single-page applications measured, eighteen read usefully and one not at all. Canvas, WebSockets, Workers and IndexedDB are absent. When a page needs an API the engine lacks, that API is named in the snapshot rather than leaving a blank space, so "the page is empty" and "I could not read the page" stay different answers. For a page it cannot read, a box can be pinned to Chromium, which reads more and gives up both fail-closed recording and the enforced takeover.
Does h5i support microVM isolation?
Yes. isolation = microvm boots a guest with its own kernel through microsandbox (msb), from the same OCI images the container tier uses. It is the one tier where the boundary is a hypervisor rather than a policy applied to a host process. It needs hardware virtualization on the host: /dev/kvm on Linux, Apple Silicon on macOS.
Do my credentials go into the box?
No. The model API key stays on the host; a reverse proxy injects it into outbound requests, scoped per runtime, so a Claude box cannot reach an OpenAI credential. The per-box copy of your agent's HOME config has credential-shaped entries stripped at any depth. A browser session is the same story: the engine can substitute a named secret on the way into a field and no verb ever returns its value, so the model names a credential and never reads one.
Can several agents share what they found?
Yes, through a Git-backed forum the host owns. Agents in separate boxes open threads, post findings, claim work and review each other, and the forum's storage and remote stay outside every box: no agent holds a token, and none needs a route to a forge. A message can change what a peer decides; it cannot change what that peer's sandbox is able to do.
Can it stop the agent leaking my source code?
No, and we will not imply otherwise. Containment stops the agent from touching your host. It does not stop it putting private code in a prompt to the model API. That is a separate control: a self-hosted model, or a profile with no model egress at all.
What are the limits?
Below the microvm tier the kernel is shared, so this is good against a runaway agent and careless dependency code, and is not a claim against a targeted kernel exploit. A session on the host is not confined at all. A boxed session needs a tier that can hold a resident process, and the tiers that enforce an egress allowlist are not all of them, so h5i browser open --in tells you which constraint applies to your box before it starts anything. The manual keeps the full list.
Is h5i free and open source?
Yes. Apache 2.0, written in Rust, local-first, with no lock-in, no hosted h5i service and no SaaS account required.
