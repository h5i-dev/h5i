Disposable Development
Environments for AI Agents

Give a coding agent full autonomy inside a throwaway box, and give your machine nothing to lose. The code, the toolchain, the tests, the dev server and the agent all run inside one boundary.

What h5i is

A contained agentic development environment.

h5i (pronounced high-five) is a throwaway box that holds the code, the agent, the toolchain, the dev server and a real browser. Your host directories are not mounted into it, your credentials never enter it, and the only thing that comes out is a patch you reviewed, next to a receipt of everything that ran. One Rust binary. No server, no daemon, no SaaS.

A disposable workspace
The code is copied in: a pull request, a repository, or nothing at all. No host directory is mounted read-write into the agent's reach.
A sandboxed coding agent
Claude Code or Codex, its child processes, package managers, builds, tests and dev server all inside the same boundary. A runaway agent stays in the box.
Credentials that stay outside
No SSH key, API key or browser profile enters the box. A host-side proxy authenticates the calls the policy allows, and egress is an allowlist.
A browser in the box
Chrome and a fresh profile live inside. The agent drives it through a CLI and reads the accessibility tree; you can watch the same viewport and take over.
An output gate
A patch, a report and an execution receipt, after inspection. The agent has no direct write path to your repository.
Receipts, not testimony
Exit codes and resource use come from the supervisor. Denied egress comes from the proxy. Console errors come from the page. None of it is the agent's account of itself.
The problem

Full autonomy is the point.
Your laptop is the risk.

An agent that has to ask permission for every command is an agent you are babysitting. An agent that does not is one running with your SSH keys, your cloud credentials, your browser session and write access to everything you own. The usual answer is to narrow what the agent may do. h5i narrows where it is instead, so it can have the run of the place.

The loop

Fill a box, let it work, read what came out.

1 · Fill it
h5i dev . for this repository, h5i dev 1234 for a pull request, h5i dev <url> to clone something you do not trust, h5i dev --new to start from nothing. External code always arrives detached: your repository is never touched.
2 · Work in it
h5i dev shell <name> is the agent-in-box. Everything the session spawns is contained by the box, not by the agent choosing to wrap each call. h5i dev status tells you the policy that was actually enforced, never the one that was requested.
3 · Get it out
h5i dev export <name> writes patch.diff, report.md and receipt.json for a human to read. Nothing reaches your repository without that step. Apply it wherever you want with git apply --3way.
The browser

The agent can see the app it just changed.

A browser box runs headless Chrome and the agent-browser daemon alongside the agent, so the dev server is on localhost for both of them. The agent reads an accessibility tree rather than HTML, clicks and fills by handle, and screenshots what it sees.

Watch it, then take over
h5i dev view <name> streams the viewport to loopback and lets you drive. The box's port is never published: h5i reaches into its private network namespace instead, behind a per-box token, refusing cross-origin connections.
One driver at a time
Nothing upstream arbitrates between an agent and a human clicking at the same moment, so h5i does. You take control rather than asking for it; the agent waits, then re-snapshots, because the page moved underneath it.
The page's own answer
Console errors, uncaught exceptions and failed requests land in the receipt, collected right after each command. "I clicked Submit and it worked" is a sentence; the export carries what actually happened next to it.
FAQ

Frequently asked questions

The short answers. The manual has the long ones.

What is h5i?
h5i (pronounced high-five) is an open-source contained agentic development environment. It gives a coding agent a disposable box holding the code, the toolchain, the dev server and a real browser, confined by a pinned, fail-closed policy, and gives you back a reviewed patch plus a receipt of everything that ran. One Rust binary, Apache 2.0, no hosted control plane.
How is this different from just running the agent in a container?
A container is one of the four tiers h5i can use, and on its own it is the weakest at the thing that matters most here. Its egress allowlist is an HTTP proxy, so it only binds tooling that respects proxy settings. h5i's supervised tier puts the box in a private network namespace and enforces the allowlist with nftables rules pinned to resolved IPs, plus a seccomp gate on socket(): a program that ignores proxy settings still cannot reach an off-list address. On top of that you get the copy-in workspace, the credential broker, the browser, and the output gate, which a bare container does not give you.
Do my credentials go into the box?
No. The model API key stays on the host; a reverse proxy injects it into outbound requests, scoped per runtime, so a Claude box cannot reach an OpenAI credential. Any other service works the same way as a policy entry rather than a feature. The per-box copy of your agent's HOME config has credential-shaped entries stripped at any depth, keeping only the runtime's own token, which it cannot function without.
Can the agent tamper with the receipt?
It cannot rewrite what is already recorded. The box's only write window under its own directory is a staging spool; the receipt log and the stored payloads are siblings of that spool, outside every grant it has. The box stages a record, the host ingests it, and ordering and timestamps are the host's. What an agent can still do is stage extra records or stop writing, and both are visible: a gap between host-observed exits and box-reported commands is itself a finding. We do not claim more than that.
Can it stop the agent leaking my source code?
No, and we will not imply otherwise. Containment stops the agent from touching your host. It does not stop it putting private code in a prompt to the model API. That is a separate control: a self-hosted model, or a profile with no model egress at all.
Does it need root, or a VM?
Neither. h5i uses Landlock, seccomp and unprivileged user namespaces, adding rootless Podman if you have it. h5i dev probe reports what your host can actually enforce. An explicitly requested tier that the host cannot satisfy fails closed — h5i never silently downgrades.
What are the limits?
The kernel is shared, so this is good against a runaway agent and careless dependency code, and is not a claim against a targeted kernel exploit. Chrome runs with its own sandbox off, because h5i's seccomp policy denies the namespace syscalls it needs — the box is the boundary, not Chrome. The viewport is a page, not a desktop. And it is Linux first: rootless Podman on Linux and WSL2, with macOS needing a VM layer. The manual keeps the full list.
Is h5i free and open source?
Yes. Apache 2.0, written in Rust, no lock-in and no hosted service.
What happened to the provenance features?
h5i began as a provenance system: prompt versioning, AI-aware blame, an audit scan, a multi-agent orchestra, a dashboard. Those are gone. The boundary was always the part worth having, and the product is being rebuilt around it. ROADMAP.md is the plan of record: what stays, what was cut, and what is still coming.

Let the agent off the leash. Somewhere else.

Full autonomy inside a box that holds nothing of yours, and a reviewed patch on the way out. Apache 2.0. No SaaS, no lock-in.
