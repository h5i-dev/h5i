Export a reviewable patch from a box

A box has no write access to anything outside itself, so getting work out is one command and one deliberate decision. Here is the whole path from finished box to applied change.

By Koukyosyumei Reading time 5 min Tags Export · Review · Patches
The gotcha up front. export refuses to write into a non-empty directory. That is deliberate, so a second export never quietly overwrites a review you had open. Pass --force when you mean to replace it.

1. Check what changed

Before exporting, look at the diff against the pinned base.

~/my-project
$ h5i box diff fix-auth
$ h5i box status fix-auth   # policy enforced, evidence, base drift

2. Export

~/my-project
$ h5i box export fix-auth --out ./review
  wrote ./review/patch.diff, ./review/report.md, ./review/receipt.json
FileWhat it is
patch.diffThe tree diff against the pinned base, path-validated: no symlink escapes, no nested .git, no agent-introduced gitlinks.
report.mdWhat ran, what the browser saw, who was at the controls, and the agent's own proposal.
receipt.jsonEvery observed execution, with the policy digest that was enforced.

3. Read the report before the patch

report.md is ordered by how much you should trust each section, so read it top to bottom. Denied egress attempts come first, because a box that tried to reach a host the policy refused is the most interesting line a review can contain. Then every command with its lane and exit code, then what the page said back, then viewer sessions, then the agent's proposal last.

~/my-project
$ $EDITOR ./review/report.md

4. Apply it where you want

~/my-project
$ git apply --3way ./review/patch.diff

For the local case, where the box came from this repository and landing it here is exactly what you meant, h5i box apply fix-auth does it in one step. That refuses on a detached box, meaning one created from a URL, a pull request or --new, and points you back at export. External code should never land by momentum.

Redaction and caps apply to all three files. Secrets are scrubbed before anything is written, and the scrub is recorded by rule id rather than by value, so a reviewer can see that a secret was involved without seeing it.

FAQ

Why does export refuse to write into a non-empty directory?

So a second export never quietly overwrites a review you had open. Pass --force when replacing it is what you meant.

What is path validation on the patch?

The tree diff is checked for symlink escapes, a nested .git, and agent-introduced gitlinks before it is written, so you can read it as a diff rather than as a potential filesystem trick.

Why does h5i box apply refuse on a detached box?

Because a detached box holds code you did not write, fetched from a URL, a pull request or nothing at all. Landing it has to be a deliberate act, so apply refuses and points at export, and you run git apply --3way yourself.
