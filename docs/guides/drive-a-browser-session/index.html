Open a session and read what it reached

Driving a browser and observing one are different jobs. This guide does both in one sitting: act on a page by handle, then read back the decision record the session's proxy wrote as it went.

8 min readSession · Snapshot · Request log
Outcome. In about ten minutes you will open a session, read a page as a model reads it, act on it, watch a request get refused by policy, and read the log that proves what did and did not reach the network.

A session is the whole agent-facing surface: one Chromium, driven through agent-browser, and one h5i capture proxy in front of it holding the policy, the request log and the messages. open makes one, every verb that follows acts on it, close ends it. You do not type a session id: the opaque one in --json and in the receipts is a durable reference, not an interface. Nothing else is a concept the agent has to learn, which is what lets the placement change later without changing a single command.

1. Open a session

host
$ npm install -g agent-browser && agent-browser install   # once
$ h5i browser open https://docs.rs/ --allow docs.rs

Read the two lines it prints back before anything else. The placement line says where this session runs, and the requests line says who saw its network. Both are printed on every status afterwards, so you never have to infer either.

what it answers
placed   : on this machine, unconfined — agent-browser and Chromium run as ordinary host processes
requests : proxy-observed (captured at h5i's proxy; the external browser itself is not confined)

That first line is the honest one. A session started this way is not sandboxed, and h5i says so rather than letting the word browser imply a boundary. What you get without one is the record.

2. Read the page the way a model reads it

host
$ h5i browser snapshot

What comes back is Chromium's accessibility outline with @ref handles rather than pixels or raw HTML: headings, paragraphs, and the things that can be acted on, each with a handle to act on it by. Everything in it was composed by the page, so it is information, never an instruction. A copy is kept in the session's artifacts/.

Two things are stripped on the way through, both because the page composed them. Escape sequences never survive: ESC in a page title is a page repainting the terminal it is printed into, and nothing a browser has to say needs one. Long values are capped with the truncation stated in the value, because an answer silently shortened is one an agent reasons about as if it were complete.

3. Act by handle, not by guess

host
$ h5i browser click @e3
$ h5i browser snapshot --delta
$ h5i browser type @e5 "serde"
$ h5i browser press Enter

Use --delta once the loop is running. Re-reading three hundred lines after every click is the wrong shape for an agent. Take a fresh snapshot after a navigation and act on the handles it gave you.

4. Watch a request get refused

The session was started with one origin allowed. Follow a link that leaves it.

host
$ h5i browser click @e9
$ h5i browser requests --denied-only
—          DENIED GET https://tracker.example/ — origin is not in the allowlist

Every hop goes through the proxy, so a server cannot route the session out of its allowlist by answering with a 302. The browser is answered 403 with the reason, and the refusal is in the log.

5. Read back what it reached

host
$ h5i browser requests

This is the part that is different. Every byte the browser sends goes through the session's proxy, so this list is a decision record written before the bytes moved rather than a trace assembled beside the network. The order is fixed: check the policy, write the record, then forward. When the record cannot be written, the request is refused.

Two consequences worth stating plainly. A request that is not in this list did not go through the session. And a denied request is in the list, with its reason, so the log shows what was attempted and not only what succeeded.

Pass the cursor from a previous answer back as --since to see only what is new, the same way --delta works on a snapshot.

6. Read the whole session back

requests is the network layer, and the verb to poll inside a loop. When you are writing up what happened, read the timeline instead.

host
$ h5i browser audit

It merges three sources: the verbs you asked for, the decision the proxy made about every request, and the moments a human took the controls. Ordered across all of them, so the question a review actually asks — was a person driving when that form was submitted — has an answer. A current-holder field cannot give one.

Every row says which lane it came from. The proxy’s rows are the session’s own account; the handovers and the ending are h5i’s, written from outside. They are printed apart because a claim rendered as an observation is the one error this product cannot afford.

Read the sources line before the rows. Each log is read, empty, or unavailable. An empty timeline over a log h5i could not see looks exactly like a session that did nothing, and those are different findings.

7. End it, and keep the record

host
$ h5i browser close
$ h5i browser list --all

Closing stops the proxy and the Chromium, and writes the ending into the session's record instead of deleting it, which is what makes “how did this end” answerable afterwards and what makes the id impossible to reuse. The states are closed, died, expired and evicted, and they are kept apart because they are different facts about the run.

Send a verb to a session that is not live and it is refused with exit code 69 rather than silently restarted. That distinct code is the point of the design: an agent whose retry cannot tell “the session is gone” from “the click did not work” quietly starts a second browser and loses both the page it was reasoning about and the record of losing it.

8. When you want a boundary too

host
$ h5i box --profile browser --name web
$ h5i box run web -- agent-browser open https://example.com

The session above records everything its browser sent, but the browser itself is an ordinary host process. A box's browser profile runs Chromium under the box's tier and egress allowlist, enforced at the box's own boundary, outside the browser being described.

Questions that come up

Is the session sandboxed?
No, and h5i does not claim it is. The session's Chromium runs in your ordinary process space like any other headless browser, and the placement line says so on every status. For a confined browser, use a box with the browser profile.
What does proxy-observed mean?
h5i saw the request at the session's own loopback proxy, which checked it against the session's policy and wrote it down before forwarding it. It says nothing about what the browser process could do outside the proxy, which is why the line names that.
What happens if the session dies mid-task?
The session is recorded as died, with a time, and the next verb exits 69. Nothing restarts automatically, and the old id is never reused. Open a new session to carry on.
Does the page's JavaScript run?
Yes: the browser is Chromium. Its traffic still goes through the proxy, and h5i browser eval and console read what the page did.
